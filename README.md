# 灵探（SpiritScout）渗透测试智能体系统

## 一、项目概述

### 1.1 项目背景
传统自动化渗透测试工具多为线性流水线架构，存在单路径卡壳、探索效率低、全局策略不可控、重复探测多等痛点；现有多智能体渗透方案普遍存在分布式决策混乱、资源浪费、路径不可审计等问题，且普遍缺乏漏洞深度核验、PoC/EXP 标准化产出、SRC 合规校验能力，输出结果误报率高、大量低价值配置问题冗余，无法直接满足专业渗透测试与漏洞提交场景需求。

本项目基于 **「集中式元决策 + 环形子Agent集群并行探索 + 专业化漏洞闭环 + 多模式自适应」** 的核心思路构建两级渗透测试智能体系统：
- 子Agent层为**对等环形汇聚结构**：所有子Agent并行执行不同维度探测任务，执行结果通过环形总线交叉共享并统一汇聚，再交由主Agent进行全局分析与决策，形成「执行→汇聚→决策→调度→执行」的闭环迭代；
- 在原有多路线并行探索基础上，新增漏洞复核、PoC/EXP 编写、误报排查、SRC 合规校验、标准化报告生成全链路能力；
- 内置 **CTF 专项突破模式**（不依赖端口扫描）与 **智能渗透赛专项模式**（根据赛方规则自适应发现并提交漏洞），覆盖安全竞赛全场景。

### 1.2 项目目标
1. 实现 **主Agent集中决策 + 环形子Agent集群并行探索** 的架构，子Agent对等并行、结果统一汇聚，默认每个子Agent生成3条测试路线，支持动态弹性调整；
2. 构建 **三级数据共享体系**：子Agent内部路线共享本地缓存、子Agent间通过环形总线实时共享、全局层面统一汇聚存储；
3. 基于DAG实现全局任务规划与迭代调度，结合环形汇聚的全局数据视图，支持实时策略更新与动态任务调整；
4. **全链路漏洞闭环能力**：每个探测类子Agent内置漏洞复核、PoC/EXP编写、误报排查、SRC合规校验能力，仅收录具备实际危害的漏洞；
5. **CTF 专项突破能力**：覆盖 Web / Pwn / Reverse / Crypto / Misc 五大方向，无需端口扫描，直接面向赛题入口与附件进行定向突破并自动提交Flag；
6. **智能渗透赛专项能力**：解析赛方规则，自适应识别赛制（Jeopardy / AWD / 渗透夺旗赛），动态调整探测与提交策略，按分值优先攻克高分题；
7. 独立 **报告生成子Agent**：接收所有通过核验的漏洞，自动生成符合行业标准与SRC提交规范的测试报告；
8. 内置分支健康度评估与自动剪枝机制，避免分支指数爆炸与资源浪费；
9. 全流程可追溯、可审计，符合红队作业合规要求与SRC漏洞提交规范。

### 1.3 核心设计理念
- **环形汇聚**：子Agent层为对等环形拓扑，无严格上下游依赖，所有结果统一汇聚，主Agent基于全局完整视图决策；
- **闭环迭代**：执行-汇聚-决策-调度形成完整闭环，每轮迭代持续优化策略，而非单一线性流程；
- **分级决策**：全局决策下沉到主Agent，局部决策下放到子Agent，破解集中式决策瓶颈；
- **漏洞闭环**：每个探测子Agent覆盖「发现→复核→验真→PoC/EXP→合规校验」全链路，输出即高质量有效漏洞；
- **合规优先**：内置主流SRC平台收录规则与赛方规则，从源头过滤低价值配置问题与误报，仅收录具备实际危害的漏洞；
- **模式自适应**：同一内核按运行模式动态装配能力——常规渗透模式侧重资产测绘与纵深利用，CTF模式关闭端口扫描、直击赛题入口，渗透赛模式按赛方规则动态调度；
- **专业产出**：独立报告生成子Agent统一输出标准化文档，漏洞详情、利用代码、危害分析、修复建议完整可直接提交。

## 二、总体架构设计

### 2.1 设计原则
1. **全局视野优先**：所有子Agent结果统一汇聚，主Agent掌握完整全局数据，决策无盲区；
2. **效率最大化**：子Agent对等并行无阶段瓶颈，无依赖任务全并行，共享数据全复用；
3. **容错鲁棒性**：单条路线、单个子Agent故障不影响全局任务推进，环形结构天然具备冗余能力；
4. **低特征暴露**：统一管控探测频率与流量特征，避免多路线并行导致的异常流量；
5. **高质量输出**：漏洞必须经过复现验证、误报排除、危害判定、合规校验四重关卡；
6. **可扩展性**：支持插件化扩展子Agent类型、渗透工具与攻击路线模板，环形集群可动态增减节点。

## 三、开源安全Agent调研与知识库/经验库设计

> 本章基于 2026-10-09 对 GitHub / Gitee / arXiv 等平台 **20+ 个主流开源网络安全 Agent 项目**以及**红队经验知识源**、**主流 SRC 平台官方规则**的系统调研编写，作为「全局共享知识库」（详见 4.1.3）的扩充设计依据。全章区分两类结论：**【已查证事实】**（信息来自官方仓库/官方文档/权威页面，附来源链接）与**【经验总结/一方观点】**（来自白帽社区、评测文章或本系统的设计推断，供参考）。完整调研笔记全文已整合进本文档 **附录A（开源安全Agent调研）/ 附录B（红队专家经验库）/ 附录C（SRC挖掘经验库）**，可直接作为知识库初始语料与审计依据。

### 3.1 调研范围与方法

- **调研对象**：开源渗透测试 Agent（PentestGPT、HackSynth、PentestAgent、ARTEMIS、PentAGI、AWE、MazeRunner、PenForge、Red-MIRROR 等）、LLM 安全工具链（BurpGPT、HexStrike、MITRE Caldera、CyberBattleSim 等）、红队知识源（HackTricks、PayloadsAllTheThings、LOLBAS、GTFOBins、Atomic Red Team、PTES 等）、主流 SRC 平台官方规则（阿里云 ASRC、腾讯 TSRC、字节 ByteSRC、补天、漏洞盒子、CNVD/CNNVD 等）；
- **方法**：以官方 GitHub README / 论文 / 官网为准，通过通用搜索交叉验证 + 精读关键页面；对无法核实的项目明确标注「未能核实」；
- **事实分级原则**：关键结论一律附可追溯来源链接；官方来源标注【已查证事实】，社区经验、评测与推断标注【经验总结/一方观点】。

### 3.2 主流开源安全Agent调研与对比

#### 3.2.1 调研线索修正

- 【已查证】**HackSynth（aielte-research/HackSynth）与 PentestAgent（GH05TCREW/pentestagent）是两个独立项目**，不存在"改名"关系：HackSynth 为学术项目（Planner+Summarizer，CTF 基准），PentestAgent 为黑盒/赏金向（集成 HexStrike）。来源：[HackSynth](https://github.com/aielte-research/HackSynth)、[PentestAgent](https://github.com/GH05TCREW/pentestagent)；

#### 3.2.3 关键项目要点详述

- **PentestGPT**【已查证，GitHub 15.2k★，USENIX Security'24】：将渗透过程建模为 Reasoning→Generation→Parsing 三段状态机，是"LLM 做渗透"的奠基工作。借鉴：任务状态机思想与本系统主 Agent DAG 状态机一致；其"人在回路"局限印证本系统全自动环形集群的必要性。
- **ARTEMIS**【已查证，斯坦福开源】：Supervisor 动态 spawn 无限子 Agent（Rust 编写的 Codex 环境），核心创新是 **Triage 三阶段（相关性判断→复现→定级）**，在真实企业网 8000 台主机上取得 82% 有效提交、9/10 战胜人类。借鉴：Triage 三阶段与本系统「初筛→复核复现→危害评估」核验链路高度同构，直接作为漏洞全链路核验模块的基线参照。
- **MazeRunner**【已查证，2026 论文】：三 Agent 分工「全局编排 / 重上下文执行 / 失败复盘」，持久化任务状态与证据，长程线索关联。借鉴：失败复盘 Agent 是本系统「分支健康度管理 + DAG 回退」的最直接对标——分支剪枝不是简单丢弃，而是复盘后切换路线。
- **PentAGI**【已查证，GitHub 22.2k★】：五角色分工 + Neo4j 知识图谱 + Docker 沙箱 200 个工具。借鉴：资产/漏洞/主机关系用知识图谱建模，可纳入资产库的关联查询设计；Docker 沙箱隔离为子 Agent 执行隔离方案。
- **Red-MIRROR**【已查证，2026 论文】：RAG + 共享循环记忆（SRMM）+ 双阶段反思。借鉴：跨 Agent 共享记忆与本系统环形总线数据共享同构；反思机制增强分支自评。
- **AWE**【已查证】：按漏洞类型绑定专用流水线 + 双层记忆 + 浏览器真实执行验证。借鉴：**3 条差异化路线应按漏洞类绑定流水线而非 LLM 自由发散**；浏览器执行验证是误报排查的有力手段。
- **Pentest-Swarm-AI**【已查证】：信息素黑板式去中心化蜂群协作。借鉴：去中心化协调机制为环形数据总线的消息路由提供参考。
- **MITRE Caldera**【已查证】：Adversary 编排的事实标准，Ability 抽象 + ATT&CK 矩阵 + Atomic 用例。借鉴：子 Agent 能力按 Ability 粒度封装；漏洞标准库按 ATT&CK 技术 ID 组织便于对齐。

#### 3.2.4 调研结论：对本系统的可借鉴设计点（15 条）

1. **主 Agent/DAG**：任务图必须运行时动态推断与重规划（Incalmo 刚性图 0 发现的反面教训），支持边探索边补节点；
2. **分支健康度剪枝**：引入独立「失败复盘」逻辑，分支切换保留长程线索（MazeRunner 直接对标）；
3. **3 条差异化路线**：按漏洞类绑定专用测试流水线（AWE），而非 LLM 自由发散；
4. **PoC/误报库**：「验证优于推测」——提交前经浏览器/差分真实复现（AWE + MAPTA + ARTEMIS）；
5. **核验链路**：初筛→复核→误报→SRC 合规→PoC 全链路直接映射 ARTEMIS Triage；
6. **Chroma 五库**：建立「漏洞类→工具→参数→PoC 模板」检索映射，缓解 PenForge 的"工具误用"问题；
7. **资产库**：双层记忆设计——短期会话态 + 长期跨目标绕过模式沉淀（AWE + PentAGI）；
8. **环形数据总线**：信息素黑板式去中心化读写，主 Agent 只做元决策（Red-MIRROR SRMM + Swarm-AI）；
9. **长任务**：会话切分 + 智能摘要 + 断点续跑（ARTEMIS），子 Agent 本地缓存（HackSynth）；
10. **工具层**：MCP/CLI/Docker 三态统一封装 + 结构化结果解析（HexStrike + PentestAgent）；
11. **执行隔离**：每子 Agent/任务 Docker 沙箱；CTF 模式网络隔离、不做端口扫描（PentAGI + HackSynth）；
12. **赛制规则库**：内置 Jeopardy/AWD/靶场规则与 Flag 自动提交；可用 CyberBattleSim 做 Agent 自训练底座；
13. **报告子 Agent**：按 CVSS + SRC 规则定级、ATT&CK 组织报告结构、中文整改建议（vibe-pentest + Caldera）；
14. **合规护栏**：分模式显式授权范围 prompt，既防 LLM 拒答又防越界（HackSynth + ARTEMIS）；
15. **成本剪枝**：按 token/工具调用/最近产出做分支预算治理（AWE 资源治理）。

#### 3.3.4 常见攻击路径模板（6 类）

【经验总结，方法学来源见 3.3.2 知识源表；每条路径含入口条件/步骤序列/分支决策/工具/验证方法，完整版本见 `research/02_红队专家经验库调研.md`】

1. **Web 打点→内网横向**：信息收集 → Web 漏洞确认（核验：最小 PoC）→ 拿初始 Shell（核验：whoami 回显）→ 反弹稳定 → 本机枚举 → 内网探测（fscan/cme）→ 提权 → 横向（PsExec/WinRM）。分支：无 RCE 转 SQLi 取凭据；有 SSRF 转云路径。
2. **Windows 域攻击链**：域枚举（BloodHound）→（可选）LLMNR 投毒+NTLM 中继 → **Kerberoasting**（GetUserSPNs + hashcat -m 13100）→ AS-REP Roasting（-m 18200）→ Pass-the-Hash → 转储 LSASS → **DCSync**（拿 krbtgt）→ **黄金票据**（伪造任意账户 TGT）。分支：SMB 签名强制则中继失败，退回 Kerberoasting；破解不出转 ACE/约束委派/AD CS。
3. **Linux 提权**：linpeas 枚举 → `sudo -l` 对照 GTFOBins → SUID（`find / -perm -4000`）→ cron 脚本可写 → SSH 私钥 → 内核 CVE（警告易崩系统）。分支：无提权面则靠窃取凭据横向。
4. **云环境攻击链**：确认 SSRF → 打元数据 `169.254.169.254`（阿里云 `100.100.100.200`）→ 拿临时凭据（IMDSv1）→ `aws sts get-caller-identity` 枚举 IAM → IAM 提权（PassRole/CreateAccessKey）→ S3 桶 → 容器逃逸（privileged/挂宿主目录）。分支：IMDSv2 强制则转找硬编码 AK/SK（T1552.001）。参考：Capital One 事件。
5. **钓鱼与凭据收割**（授权范围内）：仿冒页/附件准备 → 鱼叉投递（T1566）→ 凭据收割（核验：后台收到凭据）→ 落地执行 → 凭据验证转域路径。分支：MFA 强制转会话 cookie 复用（T1539）。
6. **数据外泄**：收集定位 → 打包 → 加密（T1048.001）→ 按出站策略选通道：经 C2（T1041）/ 替代协议（DNS 隧道 T1048.003）/ 合法云存储。分支：先测出网端口，全堵则降级证明"已打包待传"。

#### 3.3.5 Checklist 条目与攻击路径模板字段设计

**Checklist 条目字段**（对标 Atomic Red Team 并扩展，机器可检索）：

```text
entry_id            # 条目唯一编号，如 RT-WEB-001

category            # 分类（打点/提权/横向/凭据/外泄）
```

**攻击路径模板字段**：

```text

entry_conditions    # 入口条件布尔表达式，主 Agent 据此判断是否启用
step_sequence       # 步骤序列（关联 entry_id 列表，可含分支）
decision_points     # 决策点（如"SMB 签名是否强制"）
failure_handling    # 失败时的备选路径
related_tactics     # 关联战术列表
prerequisite_knowledge  # 需要的情报（如"存在域控 IP"）
```

**示例条目**（Kerberoasting 节选）【经验总结，工具用法参考 HackTricks/LOLBAS】：
- `entry_id: RT-CRED-003`；`technique_id: T1558.003`；`preconditions: [已获得域内普通用户凭据]`；`steps: [1) GetUserSPNs.py 域/用户:密码 -request 2) hashcat -m 13100 hash.txt wordlist]`；`verify_method: 破解出的明文可通过 rdp/winrm 登录验证`；`fail_handling: 破解失败转 AS-REP Roasting(T1558.004) 或约束委派`。

#### 3.3.6 检索、联动与更新机制

- **检索调用**：子 Agent 按「tactic_id + os_platform + preconditions 是否满足」三条件检索经验库；preconditions 是硬门槛（如 Kerberoasting 需"有域用户凭据"，不满足则不选）；
- **核验闭环**：条目的 `verify_method` 直接喂给漏洞全链路核验模块，通过才标记对应 DAG 节点完成；
- **DAG 联动**：主 Agent 按战术拆 DAG → 查询该战术下可用技术/路径模板 → 结合已掌握情报填充后续节点；横向/凭据步骤可反复回流（非线性）；
- **子 Agent↔战术映射**：侦察→TA0043；Web 漏洞→TA0001（T1190）；主机/后渗透→TA0004/TA0006/TA0005；内网横向→TA0007/TA0008；外泄→TA0009/TA0010；
- **更新机制**：ATT&CK 官方 ID 季度同步（注意战术拆分等版本变化）；HackTricks/PA/LOLBAS 等做 watch；每条带 `last_verified`，过期条目标记 deprecated 保留审计。

#### 3.4.2 漏洞类型优先级分级（P0~P4）

【经验总结，基于 3.4.1 各平台规则与白帽社区实践归纳；完整说明见 `research/03_SRC挖掘经验库调研.md`】

| 级别 | 漏洞类型 | 典型危害 | SRC 收录倾向 | 检测要点 |
|---|---|---|---|---|
| **P0**（严重/高危，冲单核心） | RCE/反序列化/SSTI；核心库 SQL 注入（须出数据）；主账号任意登录/密码重置 | 直接控制服务器/核心数据 | 各平台最高档 | 深挖利用链、组合漏洞 |
| **P1**（高危/中危，高产） | 水平/垂直越权（核心数据）；支付/优惠券/订单逻辑（0 元购、刷券、并发竞态）；SSRF 打内网/云元数据；文件上传 getshell | 越权操作/业务资损/内网穿透 | 高概率收录、奖励可观 | 双账号对照、禁真实支付、报备上传 |
| **P2**（中危，边界） | 未授权后台/接口；打管理员的存储 XSS；含敏感数据（≥3 字段）的信息泄露；二次验证绕过 | 敏感数据外泄/后台接管 | 视资产档位收录 | 敏感字段数判定阈值 |
| **P3**（低危，象征性） | 反射 XSS、普通 CSRF、JSONP/CORS、URL 跳转 | 危害有限 | 部分平台象征性收录 | 需结合具体场景 |
| **P4**（默认拒收） | 纯信息泄露（phpinfo/目录遍历）、配置建议、Self-XSS、无危害 CSRF、无数据报错、业务正常逻辑、不可复现、重复、测试数据、厂商已停维 | 无实际危害 | 一律不提交 | 合规校验引擎直接过滤 |

#### 3.4.3 常见挖洞思路模板（10 类）

【经验总结，来源含各平台规则与白帽社区实战文章；每类含前置条件/步骤/常见坑，完整版见 `research/03_SRC挖掘经验库调研.md`】

1. **资产收集与攻击面梳理**：子域/真实 IP/指纹识别/swagger/敏感文件/APP 与供应链组件枚举 → 建立资产与依赖清单（对应本系统资产库初始化）；
2. **登录认证绕过与任意密码重置**：验证码复用/不校验/爆破、token 可预测、JWT alg:none 等；
3. **支付/优惠券/订单逻辑**：金额改 0.01/负数、券叠加、并发竞态（**禁真实支付，只做无害验证**）；
4. **水平/垂直越权**：双账号对照改 id/Role 参数、核心数据遍历；
5. **SSRF 打内网/云元数据**：图片转存/webhook 功能 → `169.254.169.254`（AWS）/`100.100.100.200`（阿里云）→ 临时 AK/SK、gopher 扩展；
6. **文件上传绕过 getshell**：扩展名/Content-Type/图片马/二次渲染绕过（**字节等平台须提前报备**）；
7. **SQLi 绕 WAF**：JSON/HTTP 头注入、盲注、编码分块（**只注 1 条数据证明，不拖库**）；
8. **JSONP/CORS 配置**：callback 未校验、Origin 反射+凭据；
9. **SSO/联合登录**：redirect_uri 校验、state 缺失、token 失效；
10. **测试环境/内部系统/供应链 N-day**：test/uat 子域、oa/jenkins 未授权、组件对照 CVE 打 PoC（N-day 量产、0day 高价值深耕）。

#### 3.4.4 提交流程与报告撰写规范

【经验总结，参考 [Bug Bounty Playbook·Report Writing](https://bugbounty.info/Reporting/Report-Writing) 与各平台规则】

**标准流程**：确认授权范围 → 漏洞复现与留证 → 去重自查（平台搜索历史报告）→ 按平台模板提交 → 跟进审核与补料 → 修复确认。

**六段式报告结构**：

```text
1. 标题：[业务]+漏洞类型+影响对象（如"某接口越权导致任意用户订单信息泄露"）
2. 漏洞描述：业务危害一句话概括
3. 危害等级判定：对照目标平台资产档位与 CVSS 3.1
4. 复现步骤：编号步骤 + 完整请求包 + 带时间戳截图
5. 影响证明：敏感数据打码（≥3 字段）/ whoami 回显等实证
6. 修复建议：可落地的修复方案
```

**高频驳回原因与规避**：提交前查重复；必须给成功案例+危害量化；自己先跑通、不直接交 AI 草稿（字节已立规）；只交可利用的信息泄露；严格授权范围内、敏感测试先报备；不拖库、不下源码。

#### 3.4.5 经验库字段设计与更新机制

**SRC 规则库条目字段**：

```text
platform            # 平台：asrc/tsrc/bytesrc/butian/vulbox/cnvd/cnnvd...
rule_type           # 规则类型：收录/排除/降级/报备
accept_conditions   # 收录条件（漏洞类型+资产档+等级要求）
exclude_conditions  # 排除条件（黑名单清单）
severity_mapping    # 平台等级 ↔ CVSS 映射
auto_test_allowed   # 是否允许自动化测试（如字节禁自动化）
requires_approval   # 是否需前置报备（反弹shell/上传/逃逸）
source / updated_at # 来源链接 + 更新时间
```

**挖洞思路模板字段**：`scenario / preconditions / steps / tools / common_pitfalls / related_vuln_types`。

**报告模板库**：`template_id / platform / structure（六段式） / example`，报告生成子 Agent 按目标平台匹配。

**更新机制**：平台规则页 watch + 公告订阅（规则版本变化如 ByteSRC V4→V6 自动提醒）；每条带 `last_verified`；人工标注案例（平台判定结果回流）训练合规判定权重。

#### 3.4.6 与系统现有合规基线的差异对照（规则库升级清单）

【经验总结，基于 3.4.1 平台规则与本系统 3.1.3（现 4.1.3）既有合规基线对比】

1. 既有基线「仅收录中危及以上」比多数平台更严——平台普遍收低危但奖励极低，**保留该规则但默认不推荐提交低危**；
2. **补充弱口令**收录规则（漏洞盒子/补天明确收，重要系统管理员弱口令=高危）；
3. 信息泄露需补**敏感字段数阈值（≥3 字段）**才判定为"严重敏感信息"；
4. SQLi 需补**最小证明原则（注出 1 条数据）+ 同库去重（前 3 个，后续 2 个降级）**；
5. 补**同一漏洞源合并计 1 个**规则（同接口/同上传组件/同验证码失效多洞）；
6. 补 **auto_test_allowed 配置**（字节禁自动化扫描，补天禁高并发）；
7. 补**敏感测试前置报备**项（字节反弹 shell/容器逃逸/文件上传）；
8. 补 **AI 报告人工复现门**（字节 2026 年立规，AI 直接生成的报告不予收录）；
9. 补**环境有效性判定**（测试机/测试数据=无效）；
10. 补**资产 tier × 权重系数**字段（TSRC 核心/重点/边缘资产系数）。

### 3.5 知识库/经验库在本系统的落地（与全局共享知识库衔接）

- **总体结构**：在原有「资产库/漏洞标准库/误报特征库/PoC模板库/赛制规则库」五库基础上，新增 **红队专家经验库**（3.3）与 **SRC挖掘经验库**（3.4）两个经验库，形成"五库+两经验库"；漏洞标准库从通用基线升级为多平台可配置规则库（升级清单见 3.4.6）；
- **存储**：结构化条目（SQLite，字段见 3.3.5/3.4.5）+ 向量检索（Chroma，用于语义召回）+ 可选图谱（Neo4j，资产与漏洞关联，参考 PentAGI）；
- **检索调用**：主 Agent 按战术拆 DAG → 查询攻击路径模板；子 Agent 按「tactic_id + os_platform + preconditions」或「platform + 漏洞类型」检索经验条目；
- **核验联动**：经验条目的 `verify_method` 接入漏洞全链路核验模块（初筛→复核→误报→合规→PoC），通过才标记 DAG 节点完成；
- **更新机制**：ATT&CK 官方季度同步（3.3.6）+ SRC 平台规则 watch/公告订阅（3.4.5）+ 知识源 last_verified + deprecated 保留审计 + 实战结果回流训练；
- **引用规范**：条目级来源标注（URL+访问日期），官方来源标【已查证事实】，社区经验标【经验总结/一方观点】；完整调研语料存档于 `research/` 目录。

## 四、核心模块详细设计

### 4.1 主Agent（元规划决策层）

#### 4.1.1 全局元规划器
- 基于MITRE ATT&CK框架将渗透目标拆解为多轮迭代的DAG任务图谱，而非单一线性阶段；
- 每轮迭代生成任务包，通过环形总线分发给对应类型的子Agent并行执行；
- 维护全局任务状态机，根据每轮汇聚的结果，更新DAG节点状态，生成下一轮迭代任务；
- **模式感知**：根据运行模式（常规/CTF/渗透赛）动态裁剪任务图谱——CTF模式移除端口扫描与资产测绘节点，直接生成赛题突破任务；
- 统筹漏洞终审：对子Agent提交的存疑漏洞进行最终判定，决定是否收录与上报。

#### 4.1.2 任务调度与资源管理器
- 统一管理环形子Agent集群的生命周期：创建、启动、暂停、终止、动态扩缩容；
- 监控全局资源占用（算力、带宽、时间窗口），动态调整各子Agent的资源配额与任务优先级；
- 处理任务依赖：基于DAG依赖关系，当前置条件满足时，自动下发对应任务给子Agent；
- 调度报告生成子Agent的触发时机与输出格式。

#### 4.1.3 全局共享知识库
- **资产库**：存储全流程高价值共享数据：资产清单、服务版本、已验证漏洞、凭证信息、网络拓扑；
- **漏洞标准库**：内置CVSS评分标准、漏洞分级规范、主流SRC平台收录与拒收录规则；
- **误报特征库**：汇总常见误报场景、环境干扰特征、配置类问题判定标准；
- **PoC/EXP模板库**：按漏洞类型分类的标准化代码模板，支撑子Agent快速生成验证代码；
- **赛制规则库**：内置主流CTF赛事与渗透赛赛制规则、Flag格式、计分规则、提交接口规范；
- 内置去重与冲突校验机制，保证数据一致性；提供标准化读写接口，通过环形总线向所有子Agent开放。
- **红队专家经验库**：方法论分层（框架/战术/技术/路径/条目五层）、ATT&CK 战术-技术映射、常见攻击路径模板、checklist 条目（前置条件/步骤/验证方法/来源），设计详见第三章 3.3；
- **SRC挖掘经验库**：多平台收录规则要点、漏洞类型优先级分级（P0~P4）、挖洞思路模板、提交流程与报告撰写规范，设计详见第三章 3.4；
- 经验条目统一带来源 URL 与 last_verified 字段，经 Chroma 向量化，供子 Agent 按「战术+平台+前置条件」检索调用；规则与经验更新机制见第三章 3.5。

#### 4.1.4 全局分析与决策引擎
- 接收结果汇聚引擎提交的全量子Agent执行结果，进行全局关联分析；
- 每轮迭代完成后，自动复盘全局结果，优化下一轮的任务策略、资源分配与子Agent调度；
- 异常情况干预：当大面积路线失败时，触发全局策略重规划；当发现高危漏洞或疑似Flag时，优先调度资源深度利用；
- **赛制动态决策**：渗透赛模式下，实时解析赛况（已提交Flag数量、剩余时间、题目分值、被攻击情况），动态调整攻防资源配比。

### 4.2 环形数据总线与结果汇聚引擎

#### 4.2.1 环形数据总线
- 基于发布-订阅模式实现子Agent间的对等通信与数据共享；
- 子Agent可主动发布关键中间结果（如新发现资产、新端口、新服务、赛题突破口），其他相关子Agent可实时订阅获取，无需等待主Agent中转；
- 支持主题分区：按资产、漏洞类型、任务类型、赛题方向划分数据主题，子Agent按需订阅，减少无效数据传输；
- 内置流量控制与优先级调度，保障高价值数据实时传输。

#### 4.2.2 结果汇聚引擎
- 统一采集所有子Agent的执行结果、漏洞数据、状态信息，进行结构化标准化处理；
- 全局去重：对不同子Agent发现的重复漏洞、重复资产进行合并去重，保留最完整验证结果；
- 数据聚合：按资产、漏洞类型、危害等级多维度聚合，形成全局统一视图；
- 冲突校验：对不同子Agent的不一致结果进行标记，触发二次核验，保证汇聚数据准确性；
- 每轮迭代结束后，将完整的汇聚数据集提交给主Agent决策。

### 4.3 探测执行类子Agent（环形对等节点，通用设计）

所有探测类子Agent为对等节点，通用包含基础执行模块 + 漏洞全链路核验模块，同时接入环形数据总线。

#### 4.3.1 基础执行模块
**本地路线生成器**
- 基线配置：默认生成 **3条差异化并行测试路线**，覆盖不同技术路径与测试角度；
- 路线差异化策略：不同路线采用不同工具、不同参数、不同优先级，避免同质化探测；
- 动态调节：根据任务类型、阶段进度、资源配额自动扩展/收缩分支数量（1~8条）。

**执行引擎与工具适配层**
- 封装主流渗透工具调用接口：Nmap、Gobuster、SQLMap、Nuclei、Xray、Metasploit等；
- 负责命令生成、参数校验、执行超时控制、结果结构化解析；
- 支持工具调用失败自动重试与降级替代方案。

**本地共享缓存**
- 子Agent内部所有测试路线共享的本地数据存储，实现中间结果复用；
- 缓存内容：端口扫描结果、目录爆破结果、服务指纹、页面响应、漏洞候选等高频复用数据；
- 生命周期：与子Agent生命周期一致，高价值数据主动发布到环形总线。

**分支健康度管理器**
- 为每条测试路线计算健康度评分（维度：阶段进展、发现价值、连续失败次数、时间消耗、暴露风险）；
- 自动终止低于阈值的无效路线，释放资源给高评分路线；
- 自动合并相似度高于阈值的冗余路线，减少重复工作。

**局部反思与纠错模块**
- 单步执行失败时，自动分析失败原因，调整参数或更换工具重试；
- 每执行3步进行一次局部复盘，优化路线下一步执行策略；
- 无需等待主Agent指令，实现毫秒级局部决策响应。

#### 4.3.2 漏洞全链路核验模块（核心）
**漏洞候选采集与初筛**
- 实时聚合3条测试路线发现的所有漏洞候选，自动去重、合并同类项；
- 初筛过滤：排除明显无危害的信息（如单纯版本号泄露、默认欢迎页、通用404页面），减少后续核验压力。

**漏洞复核与复现引擎**
- 对初筛通过的漏洞候选进行 **独立复现验证**：重新构造请求、更换测试路径、排除缓存与环境干扰；
- 多维度验证：至少通过2种不同方式/工具交叉验证漏洞存在性，降低误报率；
- 复现失败标记为待排查，自动分析失败原因（环境变动、参数依赖、权限限制），最多重试3次，仍失败则判定为误报。

**误报排查引擎**
- 基于全局误报特征库，匹配常见误报场景：
  - 防护设备拦截页面、WAF响应页误判为漏洞；
  - 环境差异导致的异常响应、测试端网络问题；
  - 业务正常逻辑误判、自定义响应页面误识别；
- 配置类问题判定：识别仅为配置建议、无实际安全风险的问题，直接标记为不予收录；
- 输出误报判定结论与原因，同步至全局误报特征库持续迭代。

**PoC/EXP自动生成模块**
- **PoC生成**：验证漏洞真实存在后，基于全局PoC模板库，自动生成可独立运行的概念验证代码，标注复现步骤、影响参数、触发条件；
- **EXP生成**：对于中高危且可深度利用的漏洞，自动生成完整利用代码，实现数据获取、命令执行等实际效果；
- **有效性校验**：自动运行生成的PoC/EXP，验证其可复现性与稳定性，无法稳定复现则迭代优化；
- 代码标准化：统一编码风格、注释规范、使用说明，符合SRC提交代码可读性要求。

**SRC合规校验引擎**
内置主流SRC平台（阿里云SRC、腾讯安全应急响应中心、字节跳动安全中心等）通用收录规则，对漏洞进行合规判定：

| 判定类型 | 判定标准 |
|----------|----------|
| 予以收录 | 可获取敏感数据（用户信息、业务数据、配置文件、源码等）；可执行系统命令/代码、控制目标服务器；可越权操作（水平越权、垂直越权、未授权访问核心功能）；可造成业务影响（SQL注入致数据篡改、业务逻辑绕过致交易异常）；有完整利用链的组合漏洞 |
| 不予收录 | 纯信息泄露无利用价值（单纯路径泄露、版本号泄露、banner信息）；通用配置建议类问题（缺少安全头、非敏感路径TLS配置、弱密码建议但无验证）；自证型漏洞（无实际危害的self-XSS、仅自身可触发的CSRF）；无法复现、利用条件极其苛刻的理论性漏洞；目标业务正常设计逻辑、非安全问题；重复漏洞、已知公开通用问题无特殊利用场景 |

- 输出合规判定结果：收录/不予收录，附带判定依据与规则来源；
- 标记漏洞等级：按照CVSS 3.1标准评分，对应SRC平台的严重/高危/中危/低危分级；
- 仅 **中危及以上且具备实际可利用性** 的漏洞进入最终收录池，低危且无实际危害的漏洞仅记录不输出。

**危害等级评估**
- 从机密性影响、完整性影响、可用性影响三个维度量化评估；
- 结合利用难度、影响范围、业务价值综合判定漏洞最终等级。

#### 4.3.3 环形总线交互接口
- 订阅全局任务指令与相关主题数据；
- 主动发布高价值中间结果与关键发现；
- 上报本地执行结果与漏洞数据到汇聚引擎。

### 4.4 CTF专项子Agent集群（CTF模式专属）

CTF模式采用 **五大方向专项子Agent + 统一Flag提交模块** 的装配结构。**根据设计要求，CTF模式不启用端口扫描**，所有子Agent直接面向赛题入口（题目URL、附件、二进制文件、源码包）进行定向突破。

#### 4.4.1 Web专项子Agent
- 直接分析赛题URL：参数注入、文件包含、上传绕过、反序列化、模板注入（SSTI）、SSRF、逻辑漏洞、源码泄露；
- 结合赛题源码（若提供）进行静态审计 + 动态验证双路推进；
- 复用探测类子Agent的漏洞核验能力，但对Flag提取进行专项强化。

#### 4.4.2 Pwn专项子Agent
- 二进制漏洞分析：栈溢出、堆溢出、UAF、格式化字符串、整数溢出；
- 自动化利用链构造：基于pwntools模板生成exploit脚本，逐字节调试偏移；
- 保护机制识别：NX / PIE / Canary / RELRO / Fortify，自动选择绕过策略（ROP / ret2libc / 堆风水等）；
- 本地验证 + 远程交互验证双通道，确保利用脚本对赛题环境有效。

#### 4.4.3 Reverse逆向专项子Agent
- 反编译引擎：Ghidra脚本化自动分析、IDA Python辅助、angr符号执行；
- 算法还原：自动提取加密/编码逻辑（异或、Base64、RC4、AES等），调用z3约束求解还原flag；
- 壳与混淆处理：UPX自动脱壳、花指令清理、ollvm混淆初步还原；
- 动态调试：远程gdb调试、内存dump提取关键数据。

#### 4.4.4 Crypto密码学专项子Agent
- 古典密码识别：凯撒、维吉尼亚、栅栏等自动识别与破解；
- 现代密码攻击：RSA（低指数、共模、Wiener攻击、p/q分解）、AES（padding oracle、CBC翻转）、ECC（参数弱化）；
- 编码变换链：Base系、Hex、URL、rot系列、培根等自动解码链推理；
- 基于z3 / SageMath / 符号库的方程求解。

#### 4.4.5 Misc杂项专项子Agent
- 隐写分析：LSB隐写、图片EXIF、文件分离、压缩包伪加密、流量包分析（pcap）；
- 编码与格式识别：文件头魔数识别、多种编码自动探测；
- 社工与OSINT线索聚合（按赛题允许范围）。

#### 4.4.6 Flag统一提交模块
- **Flag格式识别**：从赛制规则库加载当前赛事的Flag格式（如 `flag{...}`、`ctf{...}`、`SCTF{...}`），支持正则模板配置；
- **自动提取**：汇总各专项子Agent提取的候选Flag，按格式校验去重；
- **自动提交**：对接赛事提交接口，自动提交候选Flag，解析返回结果（正确/错误/频率限制）；
- **反馈闭环**：提交失败自动反馈给对应子Agent调整提取策略；提交成功立即上报主Agent标记该题完成，释放资源转向其他赛题。

### 4.5 智能渗透赛专项引擎（渗透赛模式专属）

智能渗透赛（含AWD攻防赛、Jeopardy渗透题、靶场渗透赛）的核心挑战是 **赛制多变、规则异构、提交实时**。本模式内置赛制自适应引擎，按赛方规则动态调整全部行为。

#### 4.5.1 赛制规则解析器
- **规则文档解析**：支持输入赛方规则文档（文本/PDF/网页），自动抽取关键字段：
  - 赛制类型：Jeopardy / AWD（攻防对抗）/ 靶场渗透赛；
  - Flag提交格式与提交接口（API地址、认证方式、提交频率限制）；
  - 计分规则：题目分值、动态分值（血条/时间衰减）、扣分规则；
  - 攻击/防守范围：允许攻击的IP段、禁止行为、禁打主机列表；
  - 时间窗口：开赛/关赛时间、每轮攻击窗口、加固窗口；
- **规则冲突检测**：规则解析结果与内置合规基线交叉校验，冲突项上报主Agent人工确认，防止越权攻击。

#### 4.5.2 赛制自适应调度器
- **Jeopardy赛制**：按分值/难度动态排题，优先攻克高分且多子Agent可并行的赛题；Flag提交成功后自动标记完成；
- **AWD攻防赛制**：双线调度——
  - 攻击线：扫描对手靶机（启用端口扫描），发现漏洞后生成EXP批量打点，提取Flag自动提交；
  - 防守线：对己方靶机进行漏洞自查，生成加固建议并自动执行（补丁、权限收敛、流量监控）；
  - 动态换防：实时监测己方被攻破情况，自动切换防守优先级；
- **靶场渗透赛制**：与常规渗透模式一致，但提交目标切换为赛方Flag/漏洞报告接口，按赛方评分标准（截图、利用步骤、flag）自动整理提交材料。

#### 4.5.3 赛况实时监控与策略迭代
- 实时监控：已提交Flag、剩余时间、当前排名（如接口提供）、题目解锁状态；
- 策略迭代：每轮汇聚结果后，主Agent按「剩余时间 × 题目分值 × 突破成功率」重新计算任务优先级；
- 频率管控：内置提交限速与退避机制，避免触发赛方防滥用限制。

### 4.6 报告生成子Agent（独立支撑类）

专门负责标准化报告产出，从结果汇聚引擎获取有效漏洞数据，保证输出格式统一、内容规范。

#### 4.6.1 漏洞数据聚合
- 接收汇聚引擎提交的、通过全链路核验的有效漏洞；
- 自动去重、按资产分组、按危害等级排序；
- 关联对应资产信息、漏洞详情、PoC/EXP代码、复现截图、危害分析。

#### 4.6.2 标准化报告生成
- 内置多套报告模板：通用渗透测试报告、SRC提交专用报告、合规审计报告、CTF解题报告（WriteUp）；
- 自动生成完整报告内容：测试概述、资产汇总、漏洞详情、复现步骤、PoC/EXP代码、危害影响、修复建议；
- **CTF模式**：自动生成结构化WriteUp（题目、考点、解题思路、Flag、复现步骤）；
- 支持多格式输出：Markdown、Word、PDF、SRC平台专用提交格式。

#### 4.6.3 报告质量校验
- 自动检查报告完整性：漏洞是否缺少复现步骤、PoC是否可运行、修复建议是否匹配；
- 格式合规性校验：匹配对应SRC平台/赛方的提交规范与格式要求；
- 敏感信息脱敏：自动对报告中涉及的真实资产、敏感数据进行脱敏处理。

### 4.7 监控与审计模块
- 全流程操作日志记录，包含所有工具调用、命令执行、决策变更、漏洞核验全流程、Flag提交记录；
- 可视化监控面板：实时展示环形子Agent集群状态、所有测试路线进度、漏洞发现与核验统计、赛况数据；
- 支持一键导出完整渗透过程审计报告与漏洞证据链。

### 4.8 黑板架构（Blackboard Architecture）设计

黑板架构是本系统「环形数据总线 + 全局共享知识库」在架构层的增强形态：把共享数据空间升级为**结构化分层黑板**，各子Agent（知识源）通过「注册-订阅-触发」机制围绕黑板协作，实现数据驱动、完全解耦的协作。

#### 4.8.1 黑板分层结构

黑板按渗透知识域分为 8 层：

| 黑板层 | 内容 | 写入方 | 消费方 |
|---|---|---|---|
| 目标与授权层 | 目标定义、授权范围、运行模式、时间窗口 | 主Agent/用户 | 全部子Agent |
| 资产层 | 资产清单、端口、服务、指纹、版本 | 侦察/扫描子Agent | Web漏洞/主机漏洞/后渗透 |
| 侦察线索层 | 子域、OSINT、历史DNS、敏感文件、代码泄露 | 侦察子Agent | 全部探测Agent |
| 漏洞层 | 漏洞候选、核验状态机（候选→初筛→复核→误报→合规→收录）、PoC/EXP | 探测子Agent | 核验模块/报告Agent |
| 凭据层 | 凭证、hash、会话、票据、云AK/SK | 后渗透/内网Agent | 横向/提权/SSRF Agent |
| 拓扑层 | 网络拓扑、主机关系、域结构、云资源 | 内网探测Agent | 主Agent DAG规划 |
| 任务状态层 | DAG节点状态、分支健康度、任务进度 | 全部分布 | 主Agent/汇聚引擎 |
| 经验反馈层 | 成功/失败案例、绕过模式、误报特征 | 核验模块 | 经验库（回写沉淀） |

#### 4.8.2 知识源（KS）与触发机制
- 每个子Agent/专项能力注册为知识源，声明：关注的黑板层、写权限、触发条件（黑板某层数据变化事件）、优先级；
- **事件驱动调度**：数据写入黑板 → 汇聚引擎校验后发布事件 → 触发条件匹配的知识源被调度执行；
- **完全解耦**：知识源之间不直接通信，只通过黑板间接协作；环形数据总线承载事件通道（NATS Pub/Sub），点对点/广播消息与黑板共享状态互补。

#### 4.8.3 控制策略
- **焦点管理**：控制模块（主Agent调度引擎）决定当前焦点层——侦察阶段聚焦资产层/线索层，利用阶段聚焦凭据层/拓扑层；
- **优先级调度**：高危事件（新RCE证据、新Flag、新凭据）优先触发对应知识源；
- **防抖与循环检测**：同一数据重复写入不重复触发；记录知识源触发历史，防止 A 触发 B、B 触发 A 的循环；
- **写权限分级**：按子Agent类型限制黑板层写入范围，防止越权覆盖（与 6.1 一致性机制联动）。

#### 4.8.4 与现有机制的关系
- 黑板 = 全局共享知识库的逻辑分层视图（SQLite + Chroma + 可选 Neo4j）；
- 环形数据总线 = 黑板事件通道（事件发布/订阅）；
- 汇聚引擎 = 黑板写入的校验、去重、冲突解决网关；
- 主Agent = 黑板控制模块 + 元决策；
- 子Agent = 知识源（可动态注册/注销，对应环形集群扩缩容）。

### 4.9 多模型协作（Multi-LLM）设计

#### 4.9.1 协作目标
- **质量**：关键决策多模型交叉验证，降低单模型幻觉；
- **成本**：任务-模型匹配，避免全部使用旗舰模型；
- **鲁棒**：主模型故障/超时自动降级切换，任务不中断；
- **专业**：按任务类型选择最擅长该领域的模型（代码、推理、中文报告）。

**模型接入方式（默认云端算力）**：所有模型统一通过 **OpenAI / Anthropic 兼容格式的 API** 接入，在系统配置中填入 `base_url`（或 `baseurl`）与 `api_key` 即完成模型启用，由云端提供模型推理算力；系统不依赖本地模型部署（本地模型仅作为可选的私有化扩展，非默认背景）。

#### 4.9.2 模型路由（Router）
| 任务类型 | 推荐模型档位 | 说明 |
|---|---|---|
| 元规划 / DAG决策 / 全局复盘 | 旗舰推理模型 | 复杂多步推理，决策质量优先 |
| 子Agent执行 / 工具调用 / 结果解析 | 中档快速模型 | 高频低延迟，成本可控 |
| PoC / EXP 代码生成 | 代码特化模型 | 代码正确性优先，配合模板库 |
| 漏洞核验 / 报告审查 / SRC合规判定 | 严谨模型 + 规则引擎 | 规则裁决为主，模型辅助 |
| CTF逆向 / 密码破解 | 特化模型 + 专用工具 | angr/z3/SageMath 等工具驱动 |
| 简单任务 / 高吞吐场景 | 云端轻量模型（OpenAI/Anthropic 兼容 API） | 成本最低，统一走云端网关 |

#### 4.9.3 协作模式（六种）
1. **路由模式**：默认模式，按任务类型路由到最优模型；
2. **投票模式**：关键判定（漏洞是否收录、Flag是否有效、高危定级）由 ≥2 个模型独立判断，一致才通过，分歧则降级复核；
3. **辩论模式**：重大分歧（高危/严重漏洞定级、复杂利用链可行性）由两个模型背对背论证后收敛结论；
4. **级联模式**：便宜模型先答，置信度低于阈值升级到旗舰模型；
5. **主备切换**：主模型超时/失败/内容审查拒绝时自动切换备选模型，任务不中断；
6. **异构角色**：规划/执行/核验三角色使用不同模型（如规划用推理旗舰、执行用快速模型、核验用严谨模型），与 4.3/4.9.2 联动。

#### 4.9.4 模型注册表与管理
- **模型注册表**：每条记录能力画像（推理/代码/中文/安全知识）、成本（$/1M token）、速率限制、历史质量评分；
- **质量基准**：定期用 CTF 基准题集、SRC 判定基准集、报告质量评估集评测各模型，动态更新评分与路由权重；
- **成本预算**：按运行模式（SRC/CTF/渗透赛）配置预算与 token 上限，超预算自动降级到低档模型；
- **偏差记录**：记录各模型在各类任务上的失败模式（如某模型在反序列化判定上易误报），反馈给路由与规则引擎。

#### 4.9.5 与规则引擎的关系（安全护栏）
- **模型是建议者、规则是裁决者**：模型输出一律经规则引擎校验（SRC合规基线、工具白名单、授权边界、命令参数校验），不符合即拒绝执行；
- 多模型投票结果仅作为规则引擎的输入之一，防止模型集体幻觉绕过规则；
- 大模型行为差异（拒答/越界）由分模式 system prompt（3.2.4-14）统一约束。

## 五、核心工作流程

整体采用 **多轮闭环迭代** 模式，每轮完成「任务分发→并行执行→环形共享→结果汇聚→全局决策→策略更新」的完整循环。以下按三种运行模式分别说明。

### 5.1 常规渗透模式工作流程

#### 5.1.1 任务初始化阶段
1. 用户输入渗透目标、范围、时间窗口、合规约束、目标SRC平台等参数；
2. 主Agent元规划器拆解目标，生成初始DAG任务图谱与首轮任务包；
3. 初始化全局共享知识库，加载对应SRC平台收录规则、漏洞标准库与PoC模板；
4. 启动环形数据总线与结果汇聚引擎，初始化环形子Agent集群（侦察/端口扫描/Web漏洞/主机漏洞/后渗透）。

#### 5.1.2 环形并行执行阶段
1. 所有子Agent同时并行执行本地测试路线，各自完成探测、漏洞初筛与核验；
2. 子Agent内部多条路线共享本地缓存，复用中间结果；
3. 环形数据共享：子Agent发现高价值中间结果时，主动发布到环形总线，其他相关子Agent实时订阅获取复用；
4. 分支健康度管理器实时监控，自动剪枝无效路线、合并冗余路线。

#### 5.1.3 漏洞全链路核验阶段
1. 子Agent实时采集所有路线发现的漏洞候选，进行初筛去重；
2. **复核复现**：独立重新构造测试用例，交叉验证漏洞真实性；
3. **误报排查**：匹配误报特征库，排除环境干扰、业务逻辑、防护设备拦截导致的误报；
4. **PoC/EXP生成**：验证通过的漏洞，自动生成标准化PoC代码；中高危漏洞自动生成EXP并验证有效性；
5. **SRC合规校验**：匹配目标平台收录规则，判定是否收录，评估危害等级；
6. 通过核验的有效漏洞同步至全局知识库，不予收录的漏洞标记原因后仅本地记录。

#### 5.1.4 结果汇聚与全局决策阶段
1. 子Agent将执行结果、漏洞数据实时上报到结果汇聚引擎；
2. 汇聚引擎进行全局去重、数据聚合、冲突校验与标准化处理；
3. 主Agent基于全局汇聚结果进行关联分析与全局复盘，更新DAG任务图谱；
4. 生成下一轮迭代策略：调整任务优先级、增删子Agent任务、优化资源分配；
5. 重复「执行→汇聚→决策→调度」循环，直至达到结束条件（时间窗口耗尽、核心目标完成、无新发现）。

#### 5.1.5 报告生成与输出阶段
1. 主Agent触发报告生成子Agent启动；
2. 报告生成子Agent从汇聚引擎拉取所有通过核验的有效漏洞；
3. 按指定模板生成标准化渗透测试报告，经主Agent终审后输出，可直接用于SRC平台提交。

### 5.2 CTF专项模式工作流程（不启用端口扫描）

#### 5.2.1 赛题初始化与分发阶段
1. 用户输入赛事信息、赛题列表（题目URL、附件、分值）与赛方规则（Flag格式、提交接口）；
2. 主Agent加载赛制规则库，按题目方向（Web/Pwn/Reverse/Crypto/Misc）与分值生成任务包；
3. **跳过端口扫描与资产测绘环节**，直接按题目分发至对应专项子Agent；
4. 若题目未标注方向，由题目识别器根据入口特征（URL/附件类型/二进制架构）自动归类。

#### 5.2.2 定向突破阶段
1. 各专项子Agent对分配到的赛题直接开展定向分析（源码审计、逆向、密码破解等）；
2. 每个专项子Agent内部同样生成3条并行解题路线，本地缓存共享，路线间交叉验证；
3. 多专项子Agent间的线索通过环形总线共享（如Reverse还原的密钥被Crypto复用）；
4. 分支健康度管理：连续无进展路线自动剪枝，转向更高分值/更高成功率题目。

#### 5.2.3 Flag提取与提交阶段
1. 专项子Agent提取候选Flag，经格式校验与去重后上报Flag提交模块；
2. Flag提交模块按赛方接口自动提交，解析返回结果；
3. 提交失败自动反馈调整；提交成功标记该题完成，主Agent回收该子Agent资源分配新题；
4. 所有赛题完成或时间窗口结束，触发收敛。

#### 5.2.4 报告生成阶段
1. 报告生成子Agent汇总各题解题过程，自动生成结构化WriteUp；
2. 输出包含题目、考点、解题思路、关键步骤、Flag与复现方法。

### 5.3 智能渗透赛专项模式工作流程（赛制自适应）

#### 5.3.1 赛制解析与初始化阶段
1. 用户输入赛方规则文档、赛事入口、认证凭据；
2. 赛制规则解析器自动抽取赛制类型、Flag格式、提交接口、计分规则、攻击范围、时间窗口；
3. 主Agent按赛制类型动态装配子Agent集群与任务策略，冲突项上报人工确认。

#### 5.3.2 Jeopardy赛制流程
1. 按分值/难度动态排题，多专项子Agent并行攻克高分题；
2. 每道题内部沿用CTF模式定向突破流程（不启用端口扫描，除非赛题要求访问目标主机服务）；
3. 提交成功即回收资源转向下一题。

#### 5.3.3 AWD攻防赛制流程
1. **攻击线**：对允许攻击的对手IP段启用端口扫描与漏洞探测，发现漏洞生成EXP批量打点，提取Flag自动提交；
2. **防守线**：对己方靶机并行漏洞自查，生成加固建议并自动执行，监控己方被攻破情况；
3. **动态换防**：主Agent按「得分速率 × 失分速率 × 剩余时间」动态调整攻防资源配比；
4. 提交频率严格受控，避免触发限速。

#### 5.3.4 靶场渗透赛制流程
1. 按常规渗透模式开展完整渗透（含端口扫描）；
2. 提交目标切换为赛方Flag/漏洞报告接口；
3. 按赛方评分标准（截图、利用步骤、flag）自动整理提交材料并提交。

#### 5.3.5 赛后收尾
- 汇总所有已提交Flag与漏洞，生成比赛复盘报告与提交记录清单。

## 六、关键技术方案

### 6.1 环形集群一致性机制
- **全局唯一标识**：每个资产、每个漏洞候选、每个赛题分配唯一ID，确保跨子Agent识别一致；
- **版本号控制**：所有共享数据带版本号，写入时校验版本，避免脏数据覆盖；
- **冲突解决策略**：数据冲突时，以验证更充分、证据更完整的结果为准，标记冲突记录触发二次核验；
- **最终一致性模型**：环形总线采用最终一致性，保障高可用与低延迟，核心数据通过汇聚引擎强一致校验。

### 6.2 动态分支广度调节机制
- **基线值**：每个子Agent默认3条测试路线，平衡探索广度与资源消耗；
- **阶段自适应**：广度探测轮次扩展至5~8条；深度验证轮次收缩至1~2条；
- **触发条件**：连续发现高价值线索时自动拆分分支；连续2步无有效产出时自动减少分支。

### 6.3 三级数据共享体系

| 层级 | 范围 | 一致性 | 用途 |
|------|------|--------|------|
| 本地缓存 | 子Agent内部路线 | 强一致 | 同Agent内路线快速复用中间结果 |
| 环形总线 | 子Agent间 | 最终一致 | 跨Agent实时共享高价值线索，避免重复探测 |
| 全局知识库 | 全系统 | 强一致 | 持久化存储核心数据、规则模板，支撑全局决策 |

### 6.4 分级决策延迟优化
- **局部决策（子Agent）**：90%的执行细节、错误重试、路线调整、漏洞初审由子Agent本地完成，延迟<1s；
- **全局决策（主Agent）**：仅处理轮次级策略、资源调度、任务规划、漏洞终审等关键事件，延迟<10s；
- 避免主Agent处理全量执行日志与漏洞细节，大幅降低决策瓶颈。

### 6.5 分支健康度评估算法
```text
健康度得分 = 0.3×进展分 + 0.3×价值分 - 0.2×失败惩罚 - 0.2×风险分
```
- 进展分：当前任务完成进度；
- 价值分：已发现的有效信息/有效漏洞/赛题突破线索数量与权重；
- 失败惩罚：连续失败次数的指数惩罚；
- 风险分：探测频率、流量特征的暴露风险。

### 6.6 漏洞核验四重校验机制
1. **初筛过滤**：排除明显无价值的信息与通用配置问题；
2. **复现验证**：独立重放+交叉工具验证，确保漏洞真实存在；
3. **误报排查**：基于特征库排除环境与业务逻辑干扰；
4. **合规判定**：匹配SRC收录规则，仅保留有实际危害的有效漏洞。

### 6.7 赛制自适应决策算法
```text
任务优先级 = 赛题分值 × 突破成功率预估 × 时间衰减系数 ÷ 资源消耗预估
```
- 突破成功率预估：基于同类型赛题历史解法命中率与当前路线健康度；
- 时间衰减系数：随剩余时间推移，对耗时长的题目降权；
- AWD模式下叠加攻防动态项：得分速率、失分速率、防守缺口。

### 6.8 CTF专项分析技术栈
- **Reverse**：angr符号执行、z3约束求解、Ghidra脚本、脱壳自动化；
- **Pwn**：pwntools模板化利用链生成、保护机制自动识别、ROP链自动拼接；
- **Crypto**：SageMath方程求解、padding oracle自动化、常见RSA攻击参数自动检测；
- **Misc**：隐写分析工具链（zsteg、steghide、binwalk、foremost）、流量分析（tshark/NetworkMiner）。

### 6.9 黑板架构事件一致性机制
- **写入校验**：黑板写入统一经汇聚引擎（去重/冲突解决/版本号），校验通过才发布事件；
- **事件幂等**：事件携带「黑板层+数据ID+版本」，消费方按版本去重，重复事件不重复执行；
- **焦点与优先级**：控制模块维护焦点层与事件优先级队列，高危事件（RCE/Flag/凭据）优先消费；
- **循环防护**：知识源触发图（A→B→A）检测，记录触发次数与最近触发时间，超阈值熔断。

### 6.10 多模型路由与投票决策算法
```text
模型选择 = argmax( 任务适配分(model, task) × 质量评分(model) ÷ 单位成本(model) )
关键判定 = ( 模型A判定 == 模型B判定 == 规则引擎判定 ) → 通过；否则进入辩论/人工
级联升级 = 基础模型置信度 < 0.8 → 升级旗舰模型复判
```
- 路由约束：运行模式预算、授权白名单、模型可用性；
- 投票规则：仅对**不可逆/高影响判定**（收录、提交、删除、高危定级）启用多模型投票，常规执行保持单模型低延迟。

## 九、风险评估与应对措施

### 9.1 技术风险

| 风险点 | 影响 | 应对措施 |
|--------|------|----------|
| 大模型幻觉导致错误漏洞判定与无效PoC | 输出质量下降、误报率升高 | 工具调用白名单、参数校验、PoC自动运行验证、多重交叉核验、规则兜底 |
| 环形数据不一致导致重复探测与核验 | 效率降低、暴露风险上升 | 全局唯一ID、版本号校验、汇聚引擎强一致去重、冲突自动合并 |
| 分支指数爆炸耗尽资源 | 系统崩溃、任务超时 | 最大分支数硬限制、健康度自动剪枝、全局资源配额管控 |
| SRC规则匹配不准确导致漏判/误判 | 输出不符合平台要求 | 内置多平台官方规则库、人工标注案例训练、可配置规则权重、人工终审入口 |
| CTF自动化解题成功率低（尤其Pwn/Reverse） | 竞赛场景价值下降 | 模板化利用链库、多工具交叉验证、失败路线自动换思路、人工介入接口 |
| 赛方规则解析歧义导致违规操作 | 竞赛违规、账号封禁 | 规则冲突人工确认、合规基线交叉校验、危险操作白名单化 |
| 多模型判定分歧导致决策延迟/混乱 | 关键节点卡顿、结论反复 | 投票/辩论收敛机制、规则引擎终裁、分歧样本回流入库训练 |
| 模型成本失控（多模型多Agent叠加） | 预算超支、任务中断 | 任务-模型路由、级联降级、预算硬顶、token监控与限额 |
| 模型集体幻觉绕过规则 | 违规探测、误报入库 | 规则引擎终裁（模型仅建议者）、多模型交叉验证、工具白名单硬约束 |

### 9.2 性能风险

| 风险点 | 影响 | 应对措施 |
|--------|------|----------|
| 主Agent决策瓶颈 | 实时性下降、策略延迟 | 分级决策机制、局部决策下沉、事件驱动而非轮询、漏洞批量上报 |

| Flag提交频率过高被限 | 竞赛失分 | 提交限速、指数退避、批量提交策略、接口并发控制 |

### 9.3 业务风险

| 风险点 | 影响 | 应对措施 |
|--------|------|----------|
| 自动化渗透超出授权范围 | 合规风险 | 目标范围白名单、边界校验、越界操作自动拦截、赛方禁打列表强制加载 |

### 2. 各项目详细要点

#### 2.1 PentestGPT（GreyDGL/PentestGPT）
- 【已查证事实】USENIX Security 2024 论文（arXiv:2308.06782）提出；官网 https://pentestgpt.com/ ；Tsecbench 2026-09 统计约 15.2k stars。
- **架构**：三个自交互模块——Reasoning（战略规划）、Generation（命令生成）、Parsing（输出分析），共同维护 testing context，构成状态机。定位是**半自动 advisory co-pilot**：人是工具执行者，AI 负责推理与下一步建议。
- **知识/记忆**：以专家 system prompt 为核心；无向量库；长程靠模块间上下文传递。
- **工具调用**：不自主执行，由人在 Kali 中跑命令后把输出贴回 Parsing。
- **优缺点**：理论奠基、生态影响大；但非全自动，且 ARTEMIS 论文将其归为「semi-autonomous」并在真实企业网评测中不及全自主系统。
- **可借鉴**：Reasoning/Generation/Parsing 三段式职责分离，对应本系统「主 Agent 元决策 → 子 Agent 生成 → 工具结果解析」。

#### 2.2 HackSynth（aielte-research/HackSynth）
- 【已查证事实】arXiv:2412.01778；ELTE；约 316 stars。
- **架构**：Planner（生成单条 bash 命令，强制包裹在 `<CMD></CMD>`）+ Summarizer（滚动合并历史与最新观测），循环直至拿到 Flag 或达迭代上限。容器化 Kali + 防火墙隔离。
- **知识/记忆**：Summarizer 是关键——用摘要代替全量拼接，`new_observation_window_size` 截断超长输出，控制 token。Planner prompt 强调「CTF 语境」以防 LLM 伦理拒答。
- **工具调用**：解析 `<CMD>` 标签执行 bash；非交互（用 sshpass 等）。
- **优点**：轻量、token 经济、配套 PicoCTF(120)+OverTheWire(80) 共 200 题 CTF 基准；GPT-4o 最佳。**缺点**：单线程、无分支探索、无真实 Web 漏洞核验。
- **可借鉴**：① 工具结果「窗口截断+摘要」→ 子 Agent 本地缓存与结果结构化；② CTF 模式下 Flag 自动探测/判定 → 本系统 CTF 子 Agent 的 Flag 自动提交模块。

#### 2.3 PentestAgent（GH05TCREW/pentestagent）
- 【已查证事实】约 3.0k stars，MIT，Python 3.10+；Tsecbench 与多家媒体交叉确认。
- **架构**：Assist（人机协同）/ Agent（单任务自主）/ Crew（多 Agent 编排）三模式。内置工具 `spawn_mcp_agent` 可派生**隔离的子 MCP server**（独立 runtime、LLM client、对话历史、notes），父 Agent 并行委派子任务（如同时多端口扫描）。
- **知识/记忆**：`pentestagent/knowledge/sources/` 目录文件经 **RAG** 注入；会话存 JSON；预置攻击手册（playbooks）；集成 HexStrike。
- **工具调用**：LiteLLM 抽象 OpenAI/Anthropic/OpenAI 兼容后端；subprocess 或 Docker exec 跑 nmap/sqlmap；MCP server 模式暴露 `run_task/run_task_async/get_task_result`。
- **优缺点**：多后端、子 Agent 派生、RAG、MCP 化是亮点；一方评测（followagents FA 50/100）指其有明显短板。
- **可借鉴**：`spawn_mcp_agent` 派生隔离子 Agent → 本系统环形子 Agent 集群的并行派生；RAG 注入 sources → Chroma 向量库五库检索。

#### 2.4 ARTEMIS（Stanford-Trinity/ARTEMIS）
- 【已查证事实】arXiv:2512.09882；DeepWiki 镜像确认仓库 `Stanford-Trinity/ARTEMIS`；Stanford Trinity 项目；HackerOne 官方博客报道。
- **架构**：Python Supervisor + 大量 Rust/Codex 子 Agent + Triage 模块。Supervisor 工具集包括 spawn_codex、terminate_instance、send_followup、list_instances、read_instance_logs、write/read_supervisor_note、update/read_todo、web_search、submit、finished。先递归生成大 TODO 列表再实例化 Supervisor。
- **知识/记忆**：**动态 prompt 生成**（外部模块为每个子 Agent 生成任务专属 expert system prompt，注入所需命令行工具提示与行为边界）；笔记系统 + 智能摘要 + **会话切分**（总结全部上下文→可选换 Supervisor 模型→清空上下文→断点续跑），从而支撑 16 小时连续作业。
- **工具调用**：子 Agent 在沙箱执行；峰值 8 个并行、平均 2.82 并发。
- **成效**：在约 8000 主机/12 子网真实大学网络评测中，9 个有效漏洞、**82% 有效提交率**，总分第二、胜过 10 名人类中的 9 名；成本约 \$18/小时 vs 人类 \$60/小时。
- **Triage 模块（最值得借鉴）**：三阶段——①相关性（是真漏洞描述、在范围内、非重复）→ 否则反馈给 Supervisor；②复现（无法复现则反馈）；③定级 + 生成详细报告提交。极大降噪与降误报。
- **缺点**：GUI 类任务弱（TinyPilot RCE 靠 hint 才发现）；仍比人类误报多；过早提交低危漏洞而错过高危 RCE。
- **可借鉴**：Triage 三阶段 → **本系统「初筛→复核→误报排查→SRC合规→PoC/EXP」核验链路**；会话切分续跑 → 主 Agent 长任务管理；动态专家 prompt → 子 Agent 差异化测试路线生成。

#### 2.5 PentAGI（vxcontrol/pentagi）
- 【已查证事实】约 22.2k stars；官网 pentagi.com；Go 后端 + React 前端 + Docker 执行层。
- **架构**：5 角色——Generator（从用户输入生成子任务计划）、Refiner（优化子任务覆盖度）、Pentester（执行扫描/利用/横向移动）、Coder（编写并执行自定义攻击代码）、Searcher（Google/DuckDuckGo/Tavily 等情报）。
- **知识/记忆**：**知识图谱 Neo4j + Graphiti** 持久化记忆；实时 UI 观测。
- **工具调用**：Docker 沙箱内 20+（一方称 200+）Kali 工具（nmap/metasploit/sqlmap/nikto/gobuster）；终端/浏览器/编辑器/外部搜索四类工具。
- **优缺点**：全自主、可观测、知识图谱记忆工业级；缺点是资源重、部署复杂。
- **可借鉴**：知识图谱持久记忆 → **资产库**与全局共享状态；5 角色分工 → 主/子 Agent 职能拆分；Docker 沙箱 → 子 Agent 执行隔离。

#### 2.6 MazeRunner（arXiv:2608.14216）
- 【已查证事实】2026-08-14 提交；作者 Zhenyuan Li 等（含 Shouling Ji）；10 个新 HTB 靶机、每目标 20M token 预算、Claude Sonnet 4.5。
- **架构（与本系统 DAG 最契合）**：三 Agent——Global Orchestrator（全局编排）、Context-intensive Executor（重上下文执行）、Failure-oriented Reviewer（失败导向复盘）。**持久维护任务状态与环境证据**，支持：动作修订、前置恢复（prerequisite recovery）、**分支切换（branch switching）**、长程线索关联（long-range clue correlation）。
- **成效**：完成 47.7% 标注子任务（vs PentestGPT-V2 36.2%、Claude Code 34.2%）；6 个目标达 user 级、其中 2 个 root；执行轨迹分析显示其**探索更多攻击分支、更高效拿到 shell**。
- **针对的痛点**：现有 Agent 易陷入深度优先探索、误诊失败、遗忘先前证据——这正是本系统「分支健康度剪枝」要解决的问题。
- **可借鉴**：**失败复盘 Agent + 分支切换 + 长程线索关联** → 本系统「环形子 Agent 集群并行探索 + 分支健康度剪枝 + DAG 回退」的直接对标；建议把「失败 Reviewer」独立成一类元决策子 Agent。

#### 2.7 PenForge（arXiv:2601.06910）
- 【已查证事实】2026；CVE-Bench 0day 设定 30.0%（12/40），较 SOTA 提升约 3 倍；Claude-3.7-Sonnet。
- **架构**：Meta-Planner 两阶段——Phase-I 目标侦察（EndpointScanner 用 feroxbuster 扫端点、WebPageReader 读页面、KnowledgeRetriever 用 Perplexity API 补外部知识）；Phase-II **Expert Agent Constructor 动态按需构造**专家 Agent（生成 AutoGPT 执行脚本，注入目标端点+角色+最佳实践+约束），按攻击类型排序逐个尝试，失败则换候选攻击类型。
- **关键洞察**：主要失败原因是 **「工具误用（tool misuse）」**——选错工具或参数不当；作者明确提出要用「**渗透专用知识检索器**」替代通用 Perplexity，按攻击类型推荐工具与环境用法。
- **可借鉴**：① 按需构造专家 Agent + 攻击类型排序 → 主 Agent 动态生成子 Agent 差异化路线；② 「渗透专用知识检索器」→ **本系统漏洞标准库 + PoC/EXP 模板库**应承担「按漏洞类推荐工具+用法」职责（对应 Chroma 检索）。

#### 2.8 Red-MIRROR（arXiv:2603.27127）
- 【已查证事实】2026-03-28；26 页。
- **架构**：多 Agent；核心是**记忆-反思骨干（memory-reflection backbone）**显式治理 Agent 间推理。
- **知识/记忆三机制**：① **RAG** 外部知识增强；② **SRMM（Shared Recurrent Memory Mechanism）**持久状态管理；③ **Dual-Phase Reflection** 自适应校验 payload 与响应。
- **成效**：XBOW 总成功率 **86.0%**（vs PentestAgent 50.0%、AutoPT 46.0%、VulnBot 6.0%），子任务完成率 93.99%。
- **可借鉴**：**SRMM 共享记忆 + 反思校验** → 本系统「环形数据总线共享 + 子 Agent 分支健康度自评」；RAG → Chroma 五库。其「反思作为系统级控制机制、与持久共享记忆紧耦合」与本系统「分支健康度剪枝」理念一致。

#### 2.9 AWE（stuxlabs/AWE）
- 【已查证事实】arXiv:2603.00960；GitHub `stuxlabs/AWE`；Claude Sonnet 4。
- **架构（三层）**：
  - **Orchestration Layer**：Intelligent Orchestrator 维护全局利用上下文（已发现输入/服务端变换/认证态/已试 payload/已成功步骤），LLM 把侦察结果转成优先执行计划；并做**资源治理**（监控 token/运行时/工具成本，高危发现后提前退出、低产 Agent 收缩）。
  - **Specialized Agents Layer**：按漏洞类专项流水线——XSS 五阶段（并行 canary 注入→DOM 上下文识别→过滤策略探测→结构化喂给 LLM 生成 payload→确定性证据）、SQLi、SSTI、CMDi、XXE、SSRF、IDOR（认证差分测试）、LFI。
  - **Foundation Layer**：**双层持久记忆**（短期=本 engagement 已试 payload/过滤器/进度标记；长期=跨目标有效绕过模式/过滤签名/历史成功率）；**浏览器验证引擎**（在受控浏览器执行 payload，观测 script 执行/DOM 变化/dialog，消除纯 HTTP 无法确认的误报）；端点发现/参数提取/指纹。
- **成效**：XBOW XSS 87%、盲注 66.7%；token 比 MAPTA 少 98%、成本降 63%、4.4×提速。
- **设计三原则**：专业化优于通用推理；有状态/记忆驱动；**验证优于推测（verification rather than speculation）**。
- **缺点**：只攻注入类，不擅业务逻辑/多步链式（默认凭证→IDOR→提权）。
- **可借鉴**：① 按漏洞类专项流水线 → **子 Agent 差异化测试路线**（每类漏洞一条流水线）；② 浏览器确定性 PoC 验证 → **误报特征库 + PoC/EXP 模板库**；③ 双层记忆 → 资产库（短期）+ 长期经验库；④ 资源治理 → 分支剪枝的成本控制依据。

### 3. 调研结论：对 灵探（SpiritScout） 的可借鉴设计点清单

> 本系统五库：**资产库 / 漏洞标准库（CVSS+SRC 收录规则）/ 误报特征库 / PoC-EXP 模板库 / 赛制规则库**；技术栈含 **Chroma 向量库**；架构为「主 Agent DAG 元决策 + 环形子 Agent 集群并行（每子 Agent 3 条差异化路线+本地缓存+分支健康度剪枝）+ 环形数据总线 + 汇聚引擎 + 全链路核验 + 报告子 Agent」。
> 以下每条均指明借鉴到本系统的**哪个模块**。

1. **【主 Agent / DAG 规划】攻击图必须动态、不可刚性**——Incalmo 因刚性任务图在早期侦察即停滞（0 发现）。借鉴：主 Agent 的 DAG 要支持运行时重规划、边探索边推断攻击图（对应 MazeRunner「攻击图初始未知、从环境反馈增量推断」），而非一次性静态排定。
2. **【子 Agent 集群 / 分支剪枝】独立「失败复盘 Agent」+ 分支切换 + 长程线索关联**——直接对标 MazeRunner 三 Agent 设计。借鉴：把环形子 Agent 中一类专门做「失败导向复盘」，基于持久任务态/环境证据做动作修订、前置恢复、分支切换；这正是「分支健康度剪枝」的算法内核。
3. **【子 Agent 集群】每子 Agent 3 条差异化路线 = 按漏洞类的专项流水线**——对标 AWE 按 XSS/SQLi/SSTI/SSRF/IDOR 等每类一条结构化流水线。借鉴：3 条路线不要靠 LLM 自由发散，而应绑定「漏洞类专用 prompt + 工具集 + 判定特征」，既提成功率又降 token。
4. **【全局共享知识库 → 误报特征库 / PoC-EXP 模板库】「验证优于推测」的确定性 PoC 验证**——对标 AWE 浏览器验证引擎 + ARTEMIS triage「复现」阶段 + MAPTA Validation Agent 证据门控。借鉴：任何漏洞候选在提交前必须由独立核验环节**真实复现**（浏览器执行/HTTP 差分/PoC 跑通），复现证据结构化存入 PoC-EXP 模板库；纯推测性发现一律不进 SRC 提交队列。
5. **【漏洞核验链路】Triage 三阶段作为核验链路骨架**——对标 ARTEMIS「相关性(在范围/非重复)→复现→定级+报告」。借鉴：本系统「初筛→复核→误报排查→SRC合规→PoC/EXP」可直接映射：初筛=相关性（在范围/非重复），复核=复现，误报排查=确定性证据比对，SRC 合规=对照 SRC 收录规则定级，PoC/EXP=证据归档。
6. **【Chroma 向量库 → 漏洞标准库 / PoC-EXP 模板库】渗透专用知识检索器，而非通用 RAG**——PenForge 明确指出主因失败是「工具误用」，需按攻击类型推荐工具+用法；Red-MIRROR/PentestAgent 用 RAG 外部知识。借鉴：Chroma 中除漏洞条目外，必须索引「漏洞类 → 推荐工具 → 参数用法 → 对应 PoC 模板」的映射，让子 Agent 取到的不只是漏洞描述，而是「下一步怎么打」。
7. **【全局共享知识库 → 资产库】双层持久记忆：短期 engagement 态 + 长期跨目标学习**——对标 AWE（短期已试 payload/过滤器/进度；长期绕过模式/过滤签名/成功率）+ PentAGI 知识图谱。借鉴：资产库存短期（本目标已扫端口/已认证态/已试 payload/进度标记），另设长期经验层存「有效绕过模式/过滤签名/历史成功率」，二者都进环形数据总线供子 Agent 共享。
8. **【环形数据总线 / 子 Agent 协调】SRMM 共享循环记忆 + 信息素黑板式去中心化协调**——对标 Red-MIRROR SRMM 与 Pentest-Swarm-AI 信息素黑板。借鉴：环形数据总线不要做成「主 Agent 事事中转」，而应让子 Agent 可直接读写共享记忆（信息素=分支健康度/已发现线索），主 Agent 只做元决策与剪枝，降低协调开销。
9. **【主 Agent 长任务】会话切分 + 智能摘要 + 断点续跑**——对标 ARTEMIS（总结上下文→可选换模型→清空→续跑，支撑 16 小时）。借鉴：长 engagement 中主 Agent 定期把上下文压缩成结构化笔记写回资产库，避免上下文爆炸；子 Agent 本地缓存（对应 HackSynth 输出窗口截断 + Summarizer 滚动摘要）防止超长工具输出污染上下文。
10. **【子 Agent 工具调用层】工具统一 MCP/CLI/Docker 三态封装 + 结果结构化解析**——对标 HexStrike AI（MCP 150+ 工具）、PentestAgent（subprocess/Docker exec）、HackSynth（`<CMD>` 标签解析 + 窗口截断）。借鉴：子 Agent 不直接裸调 Nmap/SQLMap/Burp/ZAP，而是经统一工具抽象层（MCP 优先），返回结构化 JSON + 经窗口截断的摘要，再喂给规划器。
11. **【执行隔离】每个子 Agent / 每次任务 Docker 沙箱隔离**——对标 PentAGI、MAPTA（每任务 Sandbox）、HackSynth（容器 Kali+防火墙）。借鉴：环形子 Agent 各自在隔离容器中执行，既防相互污染，又便于在 CTF/赛制模式下限制网络（CTF 模式不做端口扫描——对应 HackSynth 防火墙限制网络访问的做法）。
12. **【CTF / 智能渗透赛模式】仿真评测底座 + Flag 自动判定提交**——对标 CyberBattleSim（Gym 仿真训练）、HackSynth（CTF 基准 Flag 判定）、Tsecbench/CTFBench 评测体系。借鉴：赛制规则库应内置各赛制（Jeopardy/AWD/靶场）规则与 Flag 提交接口；子 Agent 命中 Flag 后自动提交并回写赛制规则库得分；可用 CyberBattleSim 类环境做子 Agent 自训练。
13. **【SRC 报告子 Agent】中文合规报告 + 业务逻辑漏洞表达**——对标 vibe-pentest（中文整改建议）、ARTEMIS（定级+详细报告提交）、Caldera（ATT&CK 映射）。借鉴：报告子 Agent 输出应对照漏洞标准库的 CVSS + SRC 收录规则定级，按 ATT&CK 战术组织，并生成中文可落地整改建议；业务逻辑漏洞单列章节。
14. **【合规与安全护栏】CTF 语境 prompt 防拒答 + 授权范围硬约束**——对标 HackSynth（强调 CTF 语境防 LLM 伦理拒答）、ARTEMIS（动态 prompt 注入 in-scope 边界）、PentestMCP（内置 SoW 授权范围采集 + prompt 注入缓解）。借鉴：三模式下用不同 system prompt 显式声明授权范围（SRC=授权目标、CTF=靶机、赛制=靶场），既防 LLM 拒答又防止越界；SRC 模式强制校验目标在授权清单内。
15. **【成本与剪枝依据】资源治理：token/运行时/工具成本预算**——对标 AWE（监控 token/运行时/工具成本，高危发现后提前退出、低产 Agent 收缩）。借鉴：环形数据总线上为每条分支记录「已耗 token/工具调用次数/最近产出」，作为分支健康度剪枝的量化依据；高产分支加预算、低产分支及早终止（对应 AWE「scale back low-yield agents」）。

### 一、方法论层次分析：各框架的定位与层次关系

红队经验不是单一框架，而是一套**分层叠加**的体系。落地为经验库时，必须先分清每层管什么，否则会出现"用 Kill Chain 排 DAG"或"用 ATT&CK 写报告"的错位。

#### 1.1 四大主流框架定位

| 框架 | 提出方/年份 | 层次定位 | 粒度 | 线性/非线性 | 核心用途 |
|---|---|---|---|---|---|
| **Cyber Kill Chain** | Lockheed Martin, 2011 | **阶段模型**（最高层） | 7 阶段 | 严格线性 | 向管理层解释攻击进程、做阶段阻断沟通 |
| **MITRE ATT&CK** | MITRE, 2013 起持续更新 | **行为知识库**（中层，机器可读） | 15 战术 × 200+ 技术/子技术 | 非线性、可回流 | 任务拆解、技术选型、检测/对抗映射、红队计划 |
| **PTES** | 社区标准, 2012 | **作业流程**（工程层） | 7 大阶段 | 流程化但含迭代 | 渗透测试全生命周期管理（范围→报告） |
| **OWASP WSTG / MASTG** | OWASP 社区 | **专项 checklist**（条目层） | Web/移动逐条用例 | 按检查项 | Web 应用/移动 App 的具体测试用例 |

【已查证事实】Cyber Kill Chain 七阶段：Reconnaissance → Weaponization → Delivery → Exploitation → Installation → Command and Control → Actions on Objectives（IBM/Palo Alto/Quant Lab 多源交叉确认）。

【已查证事实】PTES 七大阶段：Pre-engagement Interactions → Intelligence Gathering → Threat Modeling → Vulnerability Analysis → Exploitation → Post-Exploitation → Reporting（来源：pentest-standard.readthedocs.io 官方文档目录）。

【已查证事实】ATT&CK Enterprise 当前为 **15 个战术**（注意：相比旧版 14 战术，已新增 TA0005 **Stealth** 与 TA0112 **Defense Impairment**，原 Defense Evasion 已拆分重组）。来源：attack.mitre.org/tactics/enterprise/ 实际访问 2026-10-09。

#### 1.2 层次关系（建议经验库直接采用此分层）

```
L0 框架层（Why/What）   : Cyber Kill Chain 七阶段 —— 给人看的阶段叙事
L1 战术层（Tactic）     : ATT&CK 15 战术 —— 给主 Agent 做 DAG 拆解的节点类型
L2 技术层（Technique）  : ATT&CK Txxxx / Txxxx.xxx —— 子 Agent 可执行的动作类
L3 攻击路径层（Path）   : 多技术串联的完整 kill-chain 片段（见第四节）
L4 条目层（Checklist）  : 具体命令/Payload/验证步骤（HackTricks/PA/LOLBAS 级）
```

关键判断：
- **主 Agent 的元决策应落在 L1（战术）**，不要直接用 Kill Chain 排任务——Kill Chain 是线性的，真实攻击是 DAG（横向移动可反复回流到 Discovery/Credential Access）。
- **子 Agent 的执行应落在 L2/L4**，即"我现在要做 T1190，对应的 checklist 条目是哪几条"。
- **L3 攻击路径是连接 L1 与 L4 的桥梁**：主 Agent 按战术拆 DAG 后，可调用已沉淀的攻击路径模板来填充"这个战术节点后面通常接哪些技术"。

#### 1.3 红队标准作业流程各阶段要点（与子 Agent 类型对应）

| 作业阶段 | 对应 ATT&CK 战术 | 对应本系统子 Agent 类型 | 要点 |
|---|---|---|---|
| 侦察 Recon | TA0043 Recon / TA0042 Resource Dev | 侦察 Agent（OSINT/端口扫描/指纹） | 被动 OSINT（域名、邮箱、GitHub 泄露、子域名）→ 主动端口扫描 → 服务指纹 → 技术栈识别 |

| 执行 | TA0002 Execution | Web 漏洞 Agent / 主机 Agent | 反弹 Shell、命令执行（T1059）、WebShell 落地 |

### 四、常见攻击路径模板（≥6 类，完整步骤序列）

每条路径给出：场景 / 入口条件 / 步骤序列（含触发条件、工具、验证方法）/ 分支决策点 / 失败处理 / 关联 ATT&CK 战术。

#### 路径 1：Web 打点 → 内网横向（最经典 SRC 路径）

**场景**：公网 Web 应用存在可利用漏洞，目标是拿到内网一台机器立足点并横向。
**入口条件**：发现公网 URL，且存在 RCE/文件上传/SQLi/SSRF 等可直达执行的漏洞。

| 步 | 动作 | 触发/前置 | 工具 | 验证方法（漏洞核验闭环） |
|---|---|---|---|---|
| 1.1 | 信息收集：子域名、端口、指纹、技术栈 | 入口可达 | amass, nmap, whatweb, nuclei | 输出资产清单，确认开放端口与框架版本 |
| 1.2 | Web 漏洞探测与确认 | 指纹已知 | Burp, nuclei, sqlmap | **核验**：对每个疑似漏洞做最小化 PoC，确认返回异常/可执行 |
| 1.3 | 利用漏洞获取初始 Shell | 漏洞可利用 | exp 脚本, msf | **核验**：执行 `whoami/id` 回显，确认当前权限与主机名 |
| 1.4 | 反弹/交互式 Shell 稳定化 | 已命令执行 | bash -i, nc, msfvenom | **核验**：能执行交互命令、能上传文件 |
| 1.5 | 本机枚举：系统版本、用户、网络配置 | 立足成功 | ipconfig/ifconfig, systeminfo | 确认内网网段、是否域成员 |
| 1.6 | 内网探测：存活、端口、域控位置 | 拿到内网网卡 | nmap, fscan, crackmapexec | 输出内网拓扑与存活主机清单 |
| 1.7 | 本机/横向提权 | 有普通权限 | 根据 OS 选提权路径（见路径 3/2） | **核验**：拿到 admin/root/SYSTEM 或域管 |
| 1.8 | 横向移动到目标主机 | 有可用凭据/服务 | PsExec/WinRM/WMI/RDP | **核验**：在目标机执行命令回显 |
| 1.9 | 达成目标并留痕/清理 | 横向成功 | - | 证明可达敏感数据；按授权清理 |

**分支决策点**：1.3 无 RCE 但有 SQLi → 转数据库取凭据；有 SSRF → 转路径 4（云）；无 Web 漏洞但有弱口令 → 转 T1110.003 喷洒。
**关联战术**：TA0043 → TA0001(T1190) → TA0002(T1059) → TA0007(T1016/T1087) → TA0004 → TA0006 → TA0008(T1021) → TA0009。

#### 路径 2：Windows 域攻击链（从立足点到 Domain Admin）

**场景**：已在域内普通用户权限下立足，目标是域管/域控。
**入口条件**：机器加入域，已拿到任一域普通用户凭据或交互式 Shell。

| 步 | 动作 | 前置 | 工具（Linux 侧 Impacket / Windows 侧） | 验证 |
|---|---|---|---|---|
| 2.1 | 域信息枚举：域名、DC、域版本、用户、SPN | 域用户权限 | BloodHound(SharpHound), PowerView, impacket-GetADUsers | 拿到域 SID、DC IP、用户清单 |
| 2.2 | （可选）LLMNR/NBT-NS 投毒 + NTLM 中继 | 内网可监听流量 | Responder, ntlmrelayx | 捕获到 Net-NTLM hash；**核验**：中继到目标机器拿到 shell 或解出账号 |
| 2.3 | Kerberoasting | 任一域用户 + 目标有 SPN 账户 | GetUserSPNs.py / Rubeus kerberoast | 拿到 TGS hash（hashcat -m 13100）；**核验**：离线破解出明文密码 |
| 2.4 | （并行）AS-REP Roasting | 目标账户禁用了预认证 | GetNPUsers.py / Rubeus asreproast | 拿到 AS-REP hash（hashcat -m 18200）；破解 |
| 2.5 | Pass-the-Hash / Over-Pass-the-Hash | 拿到某用户 NTLM hash | impacket-wmiexec / psexec, mimikatz | **核验**：用 hash 免密登录到该用户可访问机器 |
| 2.6 | 提权至高权限后转储 LSASS/SAM | 本机 admin 或 SYSTEM | mimikatz sekurlsa::logonpasswords | **核验**：拿到内存中明文/hash |
| 2.7 | DCSync | 有 DS-Replication 权限（域管/特定 ACE） | mimikatz lsadump::dcsync /user:krbtgt | **核验**：拿到 krbtgt hash 与全域用户 hash |
| 2.8 | 黄金票据（Golden Ticket） | 拿到 krbtgt hash + 域 SID | mimikatz kerberos::golden / Rubeus / ticketer.py | **核验**：伪造任意账户 TGT，能访问任意域资源 |
| 2.9 | （备选）白银票据（Silver Ticket） | 拿到某服务账户 hash | 同上 | 针对单服务伪造 TGS，更隐蔽 |
| 2.10 | 持久化与横向到目标 | 域管权限 | DCSync 后任意横向 | **核验**：在 DC 或目标机落命令 |

**分支决策点**：2.2 若 SMB 签名强制开启 → 中继失败，退回 Kerberoasting；2.3 破解不出 → 转 BloodHound 找 ACE/约束委派/AD CS 路径（HackTricks AD 方法论列了 Shadow Credentials、AD CS Domain Escalation、Constrained Delegation、Resource-based Constrained Delegation 等）。
**关联战术**：TA0007(Discovery) → TA0006(T1557.001/T1110/T1003/T1558) → TA0008(T1550/T1021) → TA0003(持久化)。

#### 路径 3：Linux 提权与后渗透

**场景**：Linux 普通用户 Shell，目标是 root。
**入口条件**：拿到任一非 root 用户的交互式 Shell。

| 步 | 动作 | 检测命令 | 工具/利用 | 验证 |
|---|---|---|---|---|
| 3.1 | 基础枚举：内核版本、发行版、用户、组 | `uname -a; cat /etc/*release; id; who; last` | linpeas / linux-exploit-suggester | 输出提权面清单 |
| 3.2 | sudo 配置滥用 | `sudo -l` | 对照 GTFOBins 查每个 NOPASSWD 二进制 | **核验**：如 `sudo find . -exec /bin/sh \;` 拿到 root shell |
| 3.3 | SUID/SGID 二进制 | `find / -perm -4000 -type f 2>/dev/null` | GTFOBins 逐个查 | **核验**：如 vim/nmap/python 以 root 跑 shell |
| 3.4 | cron 任务滥用 | `cat /etc/crontab; ls -la /etc/cron.*; ps aux \| grep cron` | 若 root 跑的脚本/通配符/脚本可写，植入命令 | **核验**：等待 cron 触发拿到 root |
| 3.5 | SSH 私钥滥用 | `cat ~/.ssh/id_*; grep -r "PRIVATE KEY" /` | 用私钥登录其他主机或 root | **核验**：`ssh -i id_rsa root@target` |
| 3.6 | 内核漏洞 | 3.1 确认内核版本过旧 | 匹配 CVE（如 DirtyCow/CVE-2016-5195 类） | **核验**：跑 exp 拿到 root；**警告**：内核 exp 易崩系统，授权内先快照 |
| 3.7 | 服务/配置文件可写 | 找可写的服务配置/数据库配置 | 改配置触发 root 执行 | 拿到 root |
| 3.8 | 后渗透：留存、凭据收集、内网 | root 后 | cat /etc/shadow,  history, 找 hash | 离线破解 hashcat |

**分支决策点**：3.2 无 sudo 可滥用 → 3.3 无 SUID → 3.4 无 cron → 3.6 内核不旧 → 转横向（本机无可提权面时，靠窃取的 SSH key/云凭据横向到其他主机）。
**关联战术**：TA0007(Discovery) → TA0004(T1548.003 sudo / T1548) → TA0006(T1552.004 Private Keys / T1003.008 /etc/passwd&shadow) → TA0003(T1053.003 cron)。

#### 路径 4：云环境攻击链（SSRF → 元数据 → IAM 提权 → 横向/容器逃逸）

**场景**：云上 Web 服务器存在 SSRF，目标是拿到云账号高权限。
**入口条件**：公网 Web 应用存在 SSRF（可让服务器发起任意请求），且运行在云主机上。

| 步 | 动作 | 前置 | 工具/请求 | 验证 |
|---|---|---|---|---|
| 4.1 | 确认 SSRF | Web 有可控 URL/参数 | Burp Collaborator / interactsh | **核验**：服务器发起了对攻击者控制地址的请求 |
| 4.2 | 访问云元数据服务 | SSRF 可请求内网地址 | `http://169.254.169.254/latest/meta-data/iam/security-credentials/`（AWS） | **核验**：返回角色名 |
| 4.3 | 窃取临时凭据 | 元数据无防护（IMDSv1） | 访问上一步返回的角色路径 | **核验**：拿到 AccessKeyId/SecretAccessKey/Token |
| 4.4 | 用凭据枚举 IAM 权限 | 拿到 AK/SK | `aws sts get-caller-identity; aws iam list-*` | 确认该角色实际权限 |
| 4.5 | IAM 权限提升 | 角色有可滥用权限（如 iam:PassRole / iam:CreateAccessKey / lambda:CreateFunction） | 按权限链提权（Attacking IAM 的标准路径） | **核验**：拿到更高权限或持久化 access key |
| 4.6 | （并行）S3 桶权限配置错误 | 枚举到桶名 | `aws s3 ls s3://bucket` 看是否可读/可写 | **核验**：列出/写入对象 |
| 4.7 | 容器/集群逃逸 |  workload 在容器/K8s 中 | 检查 privileged 容器、挂载宿主目录、Docker API 暴露 | **核验**：在宿主执行命令 |
| 4.8 | （备选）供应链投毒 | 有代码仓库/CI 写权限 | typosquat / 投毒依赖 | 在下一次构建植入 |

**分支决策点**：4.2 若目标已强制 IMDSv2（需 PUT token）→ SSRF 无法带 token，元数据路径失败，转找应用配置里的硬编码 AK/SK（T1552.001）；4.5 若无 IAM 提权链 → 看该角色能直接读的 S3/数据库是否即目标。
**关联战术**：TA0001(T1190 含 SSRF) → TA0006(T1552.005 Cloud Instance Metadata API) → TA0004(IAM 提权) → TA0008(跨服务横向) → TA0003(持久化 access key)。
**来源**：Capital One  breach 即为 IMDSv1 SSRF 经典案例（linuxcent.com / breachline.io 多源）；AWS 官方 CloudTrail IR 文档亦列"SSRF to IMDSv1 credential harvesting"为标准场景。

#### 路径 5：办公网钓鱼与凭据收割（按授权范围考虑）

**场景**：已获授权对目标员工进行钓鱼测试，目标是拿到用户凭据或落脚点。
**入口条件**：有目标员工邮箱清单（OSINT 所得），授权范围内可发钓鱼邮件。

| 步 | 动作 | 前置 | 工具 | 验证 |
|---|---|---|---|---|
| 5.1 | 钓鱼素材准备：仿冒页面/附件 | 授权 | gophish, 克隆登录页（HackTricks Phishing Methodology） | 本地测试页面可收集凭据 |
| 5.2 | 鱼叉式钓鱼投递 | 员工邮箱清单 | 按 T1566.001 附件 / .002 链接 / .003 第三方 | 邮件送达（不触发网关） |
| 5.3 | 凭据收割 | 用户上当输入 | 仿冒页/宏/恶意 LNK | **核验**：后台收到明文凭据或回调 |
| 5.4 | （可选）落地执行 | 用户执行附件 | 宏 → 反弹 shell | **核验**：C2 收到会话 |
| 5.5 | 凭据验证与喷洒 | 拿到凭据 | 验证 OWA/VPN 是否可登录 | **核验**：登录成功，转入路径 2 域攻击链 |

**分支决策点**：5.3 无输入但有 5.4 执行 → 直接立足；若 MFA 强制 → 转 MFA 拦截/复用会话 cookie（T1550.003 / T1539）。
**关联战术**：TA0042(Resource Development 仿冒域/页) → TA0001(T1566) → TA0006(T1078/T1539) → TA0002(T1204.002)。

#### 路径 6：数据外泄路径（收集→汇聚→加密→外传）

**场景**：已拿到目标数据访问权，需在授权范围内证明数据可被外传。
**入口条件**：已能访问敏感数据（数据库/文件共享）。

| 步 | 动作 | 前置 | 工具/技术 | 验证 |
|---|---|---|---|---|
| 6.1 | 收集定位敏感数据 | 已立足 | find/grep、数据库导出 | 列出目标文件/表 |
| 6.2 | 汇聚打包 | 数据分散 | tar/zip/csv 导出到临时目录 | 生成待外传包 |
| 6.3 | 加密/混淆 | 防内容检测 | 对称加密（T1048.001）或 Base64 编码 | 生成密文/编码包 |
| 6.4 | 选择外传通道（按出站策略决策） | 知道哪些端口出网 | 见下方分支 | 见验证 |
| 6.5a | 经 C2 通道外传 | 已有 C2 会话 | T1041，数据塞进现有 C2 流量 | **核验**：C2 端收到文件分片 |
| 6.5b | 经替代协议外传 | C2 通道被限制 | T1048：DNS 隧道（dnscat2，数据编码进子域名/TXT 记录）、ICMP、SMTP | **核验**：攻击者 DNS 服务器/邮件收到数据 |
| 6.5c | 经合法云存储外传 | 可访问外部网盘 | 上传到攻击者控制的桶/Git | **核验**：外部可见文件 |

**分支决策点**：先测出网策略（curl 出 443/53/25 是否通）→ 通则用对应通道；全堵 → 降级证明"数据已被打包待传"并记录日志证据。
**关联战术**：TA0009(Collection T1005) → TA0010(Exfiltration T1041/T1048)。
**来源**：T1041（Exfiltration Over C2 Channel）、T1048.001/.002/.003（Exfiltration Over Alternative Protocol）均为 attack.mitre.org 官方技术页确认；DNS 隧道映射 T1048.003 / C2 侧 T1071.004（pwnsy blog / securityscientist 交叉）。

### 六、对本系统（灵探（SpiritScout））经验库落地建议

#### 6.1 哪些进经验库（按价值排序）

1. **L2 技术层**：ATT&CK 15 战术下与三模式（SRC/CTF/渗透赛）相关的技术全集，每个技术 ID 一条结构化条目。优先覆盖 Initial Access / Execution / Privilege Escalation / Credential Access / Discovery / Lateral Movement / Exfiltration（即日常 80% 工作量）。
2. **L4 条目层**：从 HackTricks（AD 方法论 37 子页、Linux Post-Exploitation、Windows Local Privesc Checklist）、PayloadsAllTheThings（Web Payload）、LOLBAS/GTFOBins（白名单二进制）中抽取"可执行命令 + 验证方法"条目，**不要照抄全文**——只抽结构化字段。
3. **L3 攻击路径层**：本文第四节 6 类路径 + 按目标环境（域/云/Linux/Win）扩展，作为主 Agent 拆 DAG 时的"模板库"。

#### 6.2 如何被子 Agent 检索调用

- **检索维度**：子 Agent 收到任务后，按 `tactic_id + os_platform + preconditions 是否满足` 三条件检索经验库，命中候选条目列表。
- **preconditions 是关键**：每条经验必须带"前置条件"，子 Agent 据此决定是否执行，避免"盲目跑不适用的 exp"。例如 Kerberoasting 前置是"有域用户凭据"，没有则不选这条。
- **verify_method 直接喂给"漏洞全链路核验"模块**：子 Agent 执行后，用条目的 verify_method 做核验闭环（如"hashcat 出明文"才算成功），核验通过才标记 DAG 节点完成。

#### 6.3 如何与 ATT&CK 任务拆解联动

- **主 Agent 元决策**：把渗透目标映射为 ATT&CK 战术 DAG（不是 Kill Chain 线性图）。每个战术节点 = 一个子任务类型。
- **战术节点展开**：主 Agent 先在经验库里查"该战术下有哪些技术/攻击路径可用"，结合当前已掌握情报（已拿到什么凭据/什么权限），调用匹配的攻击路径模板填充后续节点。
- **DAG 回流**：横向移动、凭据访问可反复出现（发现新主机→再枚举→再拿凭据），经验库的 preconditions 让主 Agent 知道"在什么新条件下可以启用哪条已执行过的路径的变体"。
- **子 Agent 类型 ↔ 战术对应**（直接落地映射）：
  - 侦察 Agent → TA0043/TA0042
  - 端口扫描/指纹 → TA0043
  - Web 漏洞 Agent → TA0001(T1190) / TA0002(T1059)
  - 主机漏洞/后渗透 Agent → TA0004 / TA0006 / TA0005
  - 内网横向 Agent → TA0007 / TA0008
  - 数据/外泄 → TA0009 / TA0010

#### 6.4 来源与更新机制建议

- **权威基线**：ATT&CK 官方（attack.mitre.org）定期更新，建议季度同步技术 ID/名称（注意本次调研发现新版已拆出 Stealth/Defense Impairment，ID 会变，经验库必须以官方 ID 为准并做版本管理）。
- **增量来源**：HackTricks、PayloadsAllTheThings、LOLBAS、GTFOBins、Atomic Red Team 持续更新，建议做 RSS/GitHub watch，新条目经人工审核后按字段模板入库。
- **版本管理**：每条经验带 `source` 与 `last_verified` 字段，过期（CVE 失效/技术被修补）的条目标 `deprecated` 而非删除，保留审计痕迹。

#### 1.2 各平台规则要点补充（已查证事实）

**ASRC 处理/合并/降级策略（§六、§七，直接可入库）：**
- 同一应用下同类型漏洞：正常等级确认前 3 个；同一问题点导致（修一个全修）只确认第 1 个。
- 同一功能越权增删改查只确认 1 个；同库 SQL 注入确认前 3 个，第 1 个正常、后 2 个降一级。
- 0Day 按实际影响业务确认，最多前 3 个；无实际影响案例不关注。
- 同一组件导致多业务问题确认前 3 个；同一漏洞源导致只确认第 1 个。
- 内部已知 Web 漏洞在处理时效内对外按重复驳回；严重超期未修对外正常确认。
- **降级场景**：需用户交互（除 CSRF/反射 XSS/JSONP 外）降级；利用有依赖/限制（如爆破 6 位验证码）降级；影响用户量/数据量极小降级；部分环节与其他漏洞重复降级、全重复驳回；仅理论可行无成功案例＝无效；仅给利用结果未给 PoC＝无效；仅非 Chrome 触发的 XSS/JSONP 最高低危。

**漏洞盒子通用评定原则（§faq?id=79，直接可入库）：**
- 弱口令：同系统多用户弱口令只确认第 1 个；同用户弱口令登不同系统算同一漏洞合并。
- **同一漏洞源产生的多个漏洞计 1 个**：同一接口多漏洞、同一发布系统多页面、框架整站漏洞、泛解析多站、未做身份校验导致多接口越权、未做 token 校验导致多 CSRF、同上传组件多功能任意上传、短信验证码失效导致全站多问题、报错信息未处理导致多页敏感报错。
- 前后关联漏洞合并（先弱口令进后台，后提该后台 SQL/越权合并；厂商许可后方可深入单独提交）。
- 边缘/废弃业务系统酌情降级。
- 严重敏感身份信息＝至少 3 个敏感字段（姓名/身份证、银行卡、手机/邮箱、密码、地址），不足降级。
- 厂商保护机制：同系统短时大量同类型高危（一般 3 个）＝合并/降级，后续忽略。

**ByteSRC 测试红线（§基本原则与测试规范 V4.0/V6.0）：**
- 禁止引起业务异常；禁止扫描器/自动化工具，只允许手工；禁止任何 DoS/DDoS 及自动扫描产生大流量。
- 禁止内网渗透延伸行为（获内网权限后横向移动）。
- 注入严禁读表；UPDATE/DELETE/INSERT 类注入禁自动化，可能改表数据须提前报备。
- 敏感测试（反弹 shell、容器逃逸、文件上传）须提前在线报备，未报备不计奖励。
- 禁止近源攻击/物理入侵/社工/邮件钓鱼；禁止用社工库。
- AI 辅助报告须人工复现，含危害说明+详细步骤+完整 PoC+关键截图，否则无效。

### 二、漏洞类型优先级分级表（按 SRC 实战价值）

> 分级逻辑：**SRC 收录倾向 = 技术危害 × 业务影响 × 可利用性 × 赏金单价**。综合 ASRC 五级标准、TSRC 技术+业务维度、漏洞盒子评定原则得出。系统基线为「仅中危及以上」，故 P0/P1 为核心目标，P2 为边界，P3/P4 默认不提交。

### 三、常见挖洞思路模板（≥8 类场景，按步骤）

> 通用前置：① 先读目标 SRC 规则页确认授权范围与红线（尤其字节要求手工/敏感测试报备、补天禁高并发）；② 全程双账号/抓包，操作留痕截图带时间戳；③ 不拖库、不下源码、不发起真实支付。

#### 场景 1：目标资产收集与攻击面梳理
1. 读 SRC 公告拿授权根域名/资产清单（含子域、APP、小程序、云资产）。
2. 子域名枚举：OneForAll/Subfinder/Assetfinder + `site:target.com -www` 语法，配合 DNS 历史记录（viewdns）找未上 CDN 的真实 IP。
3. IP/端口/指纹：微步/Shodan/Zoomeye 查归属，Nmap 扫端口（445/6379/8080/9200 等），Wappalyzer/WhatWeb 识别技术栈。
4. API 与文档：Dirsearch/Gobuster 扫 `/api/ /v1/ /swagger-ui.html /v2/api-docs /actuator`，找未授权接口文档。
5. 敏感文件：`/robots.txt /backup/ /config.php /.git/ /db_backup.sql /README.md`。
6. 移动端/小程序/供应链：反编译 APP 找硬编码 AK/SK/内部接口；抓小程序包找后端 API；梳理引入的二方 SDK/框架。
7. 产出：一张攻击面清单（域名→服务→技术栈→可疑入口），按 P0~P4 排优先级。

#### 场景 2：登录与认证绕过 / 任意密码重置
1. 走完整注册→登录→改密→找回密流程，抓全部接口。
2. 测验证码：可复用（同码多次注册）、后端不校验（提交空值/固定值）、爆破（6 位短信码无次数限制）、返回包泄露验证码。
3. 测重置 token：token 可预测/与用户无关、改 `user=victim` 参数、重置链接不绑定会话。
4. 测 session：登录前后 session 是否刷新（会话固定）、退出后 Cookie 是否失效、超时是否过长。
5. 测 JWT：弱密钥爆破、`alg:none`、篡改 role。
6. 判定：能接管任意主账号＝P0；需高条件（爆破 6 位码）降级。

#### 场景 3：支付/优惠券/订单业务逻辑
1. 定位商品下单→结算→支付→退款全链路接口，全部抓包。
2. 金额篡改：改 price/amount 为 0.01、负数、极小小数；改数量为负。
3. 优惠券：叠加互斥券（coupon=A&B 同时传）、一次性券重复用、改券面额/适用范围。
4. 并发竞态：Burp 重放签到/领奖/提现接口（Intruder 并发），看是否重复到账。
5. 退款/积分：退款后货物未回收、积分重复计算、负数金额溢出。
6. **合规红线：禁止真实下单/真实支付，仅抓包观测请求与响应；证明资损即可停。**

#### 场景 4：水平/垂直越权
1. 注册 A、B 两个测试账号，A 登录抓包。
2. 水平：把 `user_id/order_id/phone` 从 A 的值改成 B 的值，看能否读/改 B 的数据。
3. 垂直：用普通用户 A 的 Cookie 直接调管理员接口（`/admin/xxx`），或改 `Role:user→admin`。
4. 遍历：ID 从自增 1 开始遍历，统计可获取的数据量与字段敏感度。
5. 判定：核心数据（身份证/资金/手机号）任意遍历＝P0/P1；非核心少量越权＝P2/P3。
6. 注意：同一功能增删改查越权只报 1 个（避免合并降权）。

#### 场景 5：SSRF 打内网 / 云元数据
1. 找所有服务端取 URL 的功能：图片转存、网址预览、webhook、PDF 生成、导入远程文件。
2. 基础验证：把 URL 改成 `http://127.0.0.1` / 内网 IP，看是否有回显（区分真 SSRF 与仅展示固定域名的伪 SSRF）。
3. 打云元数据：`http://100.100.100.200/`（阿里云）/`http://169.254.169.254/latest/meta-data/`（AWS），读临时 AK/SK。
4. 进阶：gopher 协议打内网 Redis/Memcached；dict 探测端口；DNS rebinding 绕过白名单。
5. 回显受限：用 OOB（DNSLog/带外平台）确认盲 SSRF；写图片/文件后再读。
6. 判定：可进核心网络代理或可回显＝高危；仅能读自身无进一步利用＝降级。

#### 场景 6：文件上传绕过 getshell
1. 找上传点（头像/附件/富文本/导入），抓包。
2. 绕扩展名：`.phtml/.php5/.pHp` 大小写、`.jpg.php`、`.htaccess`、`.user.ini`。
3. 绕 Content-Type：`filename=shell.php` 但 `Content-Type: image/jpeg`。
4. 绕内容校验：图片马（文件头加 GIF89a）、二次渲染绕过、截断 `%00`。
5. 上传后访问路径确认解析，执行 `whoami` 证明。
6. **红线：字节等要求文件上传须提前报备；拿到 webshell 后漏洞盒子禁止下载源码审计。**

#### 场景 7：注入（SQL）绕 WAF
1. 探测点：URL 参数、表单、JSON body、HTTP 头（User-Agent/Referer）。
2. 输入 `'`、`and 1=1`/`and 1=2` 看报错与页面变化。
3. 无回显：时间盲注 `if(1=1,sleep(5),1)`、布尔盲注逐字符猜解。
4. 绕 WAF：内联注释 `/*!*/`、大小写混写、编码（URL/双重/Hex）、分块、HTTP 头携带、等价函数。
5. **只注出 1 条数据证明危害即停，严禁 `information_schema` 全拖库**（漏洞盒子明确严禁拖库）。
6. 判定：核心库/可获大量敏感多元组＝高危；非核心/少量＝中危；报错无数据＝拒收。

#### 场景 8：JSONP / CORS 配置类
1. JSONP：找 `?callback=xxx` 接口，看是否返回敏感数据且 callback 未校验来源。
2. CORS：发 `Origin: https://evil.com`，看响应头是否 `Access-Control-Allow-Origin` 反射且 `Allow-Credentials: true`。
3. 构造 PoC 页面跨域读取敏感接口数据。
4. 判定：能劫持敏感信息（手机号/订单）＝中危；仅非 Chrome 触发/无敏感数据＝低危/拒收。

#### 场景 9：SSO / 联合登录
1. 梳理 OAuth/CAS/SSO 授权流程：authorize→callback→token。
2. 测 callback 地址是否校验（改 redirect_uri 到 evil 域名偷 code/token）。
3. 测 state 参数是否缺失（CSRF 绑定他人账号）。
4. 测登出后 token 是否失效、跨子域 cookie 作用域过宽。
5. 判定：可劫持他人登录态/账号绑定＝高危。

#### 场景 10（加分高价值点）：测试环境 / 内部系统 / 供应链 N-day
1. 测试/预发环境：通过子域名/历史 DNS 找 `test./uat./pre./dev.` 子域，常缺 WAF/弱口令/调试接口开放。
2. 内部系统：`oa./admin./crm./jenkins./gitlab./wiki.` 未授权或弱口令。
3. 供应链 N-day：识别组件版本（Struts2/Log4j/Fastjson/Shiro/Confluence），对照最新 CVE 打 PoC；**N-day 红利期短，爆发后第一时间扫资产（如 Log4j 爆发期）**。
4. 0day vs N-day 取舍：入门/量产优先 N-day（已知 PoC、命中率高、周期短）；高价值目标/长期深耕做 0day（单价高、竞争少）。ASRC 0Day 须有实际影响案例，无案例不关注。

### 四、提交流程与报告撰写规范

#### 4.1 标准提交流程（以补天/ASRC 为通用参照）
1. 实名认证（全平台强制，身份证=手机号本人）。
2. 在授权范围内手工测试→确认可复现→量化危害。
3. 平台提交：选等级、填 URL/标题、漏洞详情（描述+证明+修复方案）、传截图/PDF 附件。
4. 平台初审（补天约 1 工作日）→厂商复审（约 1 周，超期自动通过）→奖金确认→打款（补天每周三）。
5. 跟进复测：响应厂商补充要求，配合修复验证。

#### 4.2 报告结构（六段式，直接可作模板）
1. **标题**：`[平台/业务] + 漏洞类型 + 影响对象`，如「抖音某用户中心接口存在水平越权可遍历任意用户手机号」。一眼说清是什么洞、影响谁。
2. **漏洞描述**：非技术语言讲清「在哪发现→怎么利用→影响范围」，点明业务危害（可泄露哪些敏感数据/可造成多少资损）。
3. **危害等级判定**：对照平台标准自评为 严重/高/中/低，给出定级理由（别夸大也别压低）。
4. **复现步骤**：编号分步，每步配 HTTP 请求包文本 + 截图（含 URL、Payload、响应结果），让审核员照做即可复现。
5. **影响范围证明**：数据打码后展示泄露字段（证明≥3 敏感字段）、命令执行回显（whoami）、订单金额篡改前后对比。
6. **修复建议**：可落地（如「接口增加 user_id 与登录态绑定校验」「金额服务端重算不接受前端传值」「SSRF 加目标地址白名单」）。

#### 4.3 标题与等级判定技巧
- 标题带「任意用户/批量/未授权/RCE/越权」等关键词，审核员一眼判高价值；避免模糊标题。
- 等级判定：能实际刷钱/接管主账号/核心库拖数据→严重；越权改核心数据/RCE 到生产机→高危；少量敏感数据/需交互→中危；照抄平台资产档×漏洞类型表对应奖励档自评。
- TSRC 对「利用链复杂、多账号多动作」的漏洞，逐步写清请求包+思路+PoC 脚本可拿最高 5000 高质量报告奖。

#### 4.4 常见被驳回原因与规避
| 驳回原因 | 规避方法 |
|---|---|
| 重复提交 | 提交前查平台已有漏洞列表/已公开细节；同漏洞源只报 1 个；被标重复要原报告号，若参数/端点/链路不同则具体申诉 |
| 无实际危害 / 自证型 | 必须给成功案例+危害量化（截图证明拿到敏感数据/造成资损），不只写「理论可行」 |
| 不可复现 | 自己先完整跑一遍；步骤+请求包+截图齐全；含时间戳；不直接交 AI 草稿（字节明确 AI 报告须人工复现） |
| 配置类 / 纯信息泄露 | 只提交能进一步利用的泄露（含敏感数据≥3 字段），纯 phpinfo/目录遍历不提交 |
| 超出授权范围 | 严格在 SRC 公告资产内测；敏感测试先报备（字节）；不碰未授权资产 |
| 拖库/下载源码/高并发 | 只注 1 条数据；拿 webshell 先问平台；禁高并发与 DoS |
| 与已有漏洞源合并 | 同接口/同上传组件/同验证码失效导致的多洞合并报 1 个，避免被降权 |

### 五、经验库落地设计要素（关键产出）

#### 5.1 SRC 规则库字段设计
| 字段 | 类型 | 说明/示例 |
|---|---|---|
| platform | 枚举 | asrc / tsrc / bytesrc / butian / vulbox / cnvd / cnnvd / huawei / baidu / jd / meituan |
| asset_tier | 枚举 | 超级/关键/核心/一般（ASRC）；核心/重点/边缘（TSRC）；高/中/低系数（ByteSRC） |
| rule_type | 枚举 | 收录条件 / 排除条件 / 等级映射 / 奖励档位 / 测试红线 / 合并去重 / 报备要求 |
| include_condition | 文本 | 收录判定逻辑，如「未授权可组合达 RCE」「核心库 SQL 注入须注出≥1 条数据」 |
| exclude_condition | 文本 | 拒收逻辑，如「Self-XSS / 无敏感操作 CSRF / 测试数据 / 厂商已停维」 |
| level_mapping | JSON | {严重: 奖励/贡献值, 高:..., 中:..., 低:...}，按 asset_tier 分档 |
| reward_range | 文本 | 如「超级资产严重 100000 元」 |
| auto_test_allowed | bool | 是否允许自动化（字节=false 手工；补天禁高并发） |
| report_required | JSON | 报备要求，如 {敏感测试: [反弹shell,容器逃逸,文件上传], 需提前报备: true} |
| source_url | URL | 官方规则页链接（必真实可溯） |
| verified_at | 日期 | 最近人工核验日期 |
| effective_date | 日期 | 规则生效日 |
| note | 文本 | 经验性补充（一方观点标注） |

#### 5.2 漏洞优先级分级表进库（含权重字段）
| 字段 | 说明 |
|---|---|
| vuln_type | RCE/SQLi/越权/SSRF/文件上传/逻辑支付/信息泄露/XSS/CSRF/JSONP/CORS/SSO/弱口令 |
| priority | P0/P1/P2/P3/P4（对应严重/高/中/低/不收） |
| harm_keywords | 危害关键词，供自动判定：敏感数据/系统命令/越权操作/业务影响/组合利用链 |
| weight | 权重分（P0=10,P1=7,P2=4,P3=1,P4=0），供合规引擎自动给出「建议提交/降权/驳回」 |
| src_tendency | 各平台收录倾向映射（哪些平台收为严重/高危） |
| detect_points | 检测要点清单 |
| reject_if | 判拒收条件（如 SQLi 无数据回显→降 P4） |
| representative_scene | 代表场景 |

> 自动判定参考：weight≥7 且命中「harm_keywords」→建议收录提交；weight=0 或命中 reject_if →直接判无效不提交；边界（P2）按目标平台 asset_tier 与 exclude_condition 二次过滤。

#### 5.3 挖洞思路模板字段设计
| 字段 | 说明 |
|---|---|
| scene | 场景名（资产收集/认证绕过/支付逻辑/越权/SSRF/文件上传/SQLi/JSONP-CORS/SSO/测试环境Nday） |
| precondition | 前置条件（已授权资产/双账号/抓包环境） |
| step_sequence | 有序步骤数组（每步：动作→工具→预期现象） |
| tools | 工具集（Burp/OneForAll/SQLMap/DNSLog/Hydra…） |
| common_pitfall | 常见坑（如：真 SSRF vs 伪 SSRF；拖库被处罚；验证码复用误判） |
| related_vuln_type | 关联漏洞类型（供链路组合） |
| compliance_redline | 该场景合规红线（禁真实支付/禁高并发/需报备） |
| expected_priority | 预期优先级 |

#### 5.4 报告模板库与撰写规范库
- **报告模板库**：按场景存六段式模板（标题/描述/定级/复现步骤/危害证明/修复建议），每类漏洞一个模板实例。
- **撰写规范库**：标题命名规则、定级对照规则、截图要求（带时间戳、敏感打码）、PoC 要求（可一键复现脚本/请求包）、AI 报告须人工复现标记。
- **驳回原因库**：第七章 4.4 表逐条入库，带规避动作，供提交前自检。

#### 5.5 来源与更新机制
- 规则类：以官方帮助中心/规则 PDF/安全公告为准，每季度或平台发新版时复核 `verified_at`。
- 经验类：白帽博客/众测报告标注「一方观点」，定期补充新案例。
- 触发更新：平台发新版规则（如 ByteSRC V6.0、ASRC V2.0）、重大漏洞事件（Log4j 类）后 1 周内更新对应 N-day 模板。

### 六、与系统既有基线的差异对照（供升级多平台可配置规则库）

系统基线：**收**＝敏感数据/系统命令/越权操作/业务影响/完整组合链；**不收**＝纯信息泄露/通用配置建议/自证型/无法复现/业务正常逻辑/重复。

| 维度 | 系统基线 | 平台调研差异 / 可补充规则项 |
|---|---|---|
| 收录下限 | 仅中危及以上 | **各平台普遍收低危但奖励极低**（ASRC 低危 100~500 元、漏洞盒子低危 ¥50~200）。建议：经验库保留低危规则但默认不推荐提交，仅在冲量/公益 SRC 场景启用。 |
| 弱口令 | 基线未单列 | **漏洞盒子/补天明确收弱口令**（重要系统管理员弱口令=高危）。建议补充：弱口令按系统重要度分级入规则库。 |
| 信息泄露 | 基线「纯信息泄露不收」 | **平台细化为：含敏感数据≥3 字段才够「严重敏感信息」**（漏洞盒子）；仅 phpinfo/目录遍历/内网 IP 泄露＝不收（ASRC）。建议补充字段数阈值判定。 |
| SQL 注入 | 基线「可执行/敏感数据」 | **漏洞盒子要求须注出≥1 条数据证明、严禁拖库；ASRC 同库只确认前 3 个、第 1 个正常后 2 个降级**。建议补充「最小证明原则」与同库去重规则。 |
| 合并去重 | 基线「重复漏洞不收」 | **平台有「同一漏洞源合并计 1 个」细化规则**（同接口/同上传组件/同验证码失效导致多洞）。建议补充漏洞源归并字段，避免多报被降权。 |
| 自动化测试 | 基线未明确 | **字节明确禁止扫描器/自动化、只允许手工；补天禁高并发**。建议补充 auto_test_allowed 配置项与红线拦截。 |
| 报备制 | 基线未涉及 | **字节敏感测试（反弹 shell/容器逃逸/文件上传）须提前报备，未报备不计奖励**。建议补充报备前置检查项。 |
| AI 报告 | 基线未涉及 | **字节 2026 立规：AI 生成报告须人工复现，含完整 PoC+截图，否则无效**。建议补充 AI 辅助报告的人工验证门。 |
| 测试环境/测试数据 | 基线未明确 | **ASRC：未运行实际业务的测试机 RCE、影响测试数据＝无效**。建议补充环境有效性判定。 |
| 厂商维度 | 基线无 | **补天：厂商权重<1/已停维不通过；TSRC 按核心/重点/边缘产品给不同贡献系数**。建议补充厂商资产 tier 与权重系数字段。 |
| 组合利用链 | 基线「完整利用链收」 | **平台对「利用链复杂、多账号多动作」给高质量报告额外奖（TSRC 最高 5000）**。建议在报告模板库对复杂链路加权鼓励。 |
