# 09 · 演进路线与贡献指南

本文把项目放进时间轴：过去怎么走到今天、现在在做什么、未来可能往哪走；然后给出一份可执行的贡献者上手指南。

> 未来部分明确标注「推断」：它是基于当前代码、缺口与 CHANGELOG 方向的分析，不是项目承诺。

这条路径的规律是：**先让多 Agent 跑起来，再让它跑得安全/省/可解释，最后把判断权交回用户与模型**。

## 9.2 现在：正在收敛的方向

从最近提交与 CHANGELOG 看，当前重点不是“加更多 Agent”，而是“让已有链路更可靠”：

1. **会话体验**：历史分页、SSE 断线续读、登录面板、项目文件夹分组。
2. **真实浏览器**：Chrome MCP 复用登录态，人工接管验证码/滑块。
3. **竞赛调度**：连续补位、完成回收、后台经验提炼。
4. **模式语义**：用户显式选择模式，开放赛制，不再按标签裁剪角色。
5. **审计与排查**：原文落盘、执行台账、恢复视图。

这也意味着：**短期不适合大改架构**。当前更需要的是补齐文档、测试、评测与安全边界，而不是再引入一层新抽象。

## 9.3 未来：短/中/长期（推断）

### 短期（下一个版本周期）

| 事项 | 为什么 | 涉及文件 |
| --- | --- | --- |
| 同步根文档 | README/CONTRIBUTING 有过时表述 | `README.md`、`CONTRIBUTING.md` |
| 修复用量缓存脆弱性 | WSL/网络盘读到旧数据 | `gateway/usage.py`、`tests/test_usage_storage.py` |
| MCP 目标参数校验 | 当前只是元数据 | `runtime.py`、`tools/registry.py` |
| 清理/接线竞赛死代码 | AWD/排序/榜单未接线 | `competition/engine.py` |
| 行为评测基准 | 无法量化改动 | `tests/`、新增 `benchmarks/`（建议） |
| 前端拆分 | `views.js` 约 1,574 行 | `web/static/js/` |
| Windows 启动器 | 当前仅 WSL/Docker | 新增 `launch.ps1`（建议） |

### 中期（产品化前置）

1. **RBAC / SSO / 多用户**：当前只有单一管理员；企业使用需要角色与审计归属。
2. **审计加密与留存**：原文审计是优点，也是共享主机的风险。
3. **多租户/分布式执行**：单进程 + SQLite 不适合团队并发；需要执行器与调度器分离。
4. **成本治理**：预算告警、任务级软预算、缓存优化；不是恢复“熔断”，而是让成本可见可控。
5. **平台适配标准化**：更多平台模板、档案校验器、错误诊断。
6. **OpenAPI/插件规范**：方便集成与被集成。

### 长期（商业化/生态）

1. 赛事/靶场 SaaS（强隔离、排行榜、反作弊）。
2. 企业自托管版（支持、SLA、合规包）。
3. 插件/经验生态（需解决质量与合规）。
4. 本地模型支持（降低对闭源供应商依赖）。

### 明确不做的（除非产品决策改变）

- 不恢复固定回合顶或预算熔断。
- 不把意图分类/模式判断写回后端规则。
- 不恢复后端正则提取 Flag。
- 不把危险动作审批改成自动放行。
- 不把测试边界改成硬编码禁打列表（可作为**可选**企业模式，但不作为默认）。

这些是 [AGENTS.md](../AGENTS.md) 的约束，也是项目辨识度的一部分。

## 9.4 贡献者上手

### 9.4.1 环境

当前仓库的 `.venv` 是在 WSL 内创建的 Linux venv。Windows 原生不能直接跑（`launch.sh` 是 bash，沙箱依赖 bwrap）。

```bash
# WSL / Linux
cd /mnt/d/Work/produce/work/SpiritScout
python3 -m venv .venv
.venv/bin/pip install -e '.[toolkit]'      # 运行所需
.venv/bin/pip install -e '.[dev]'          # 开发检查（ruff）
sudo apt install bubblewrap                # 沙箱
./launch.sh                                # 默认 127.0.0.1:8000
```

Docker：

```bash
cp .env.example .env
docker compose up -d --build
```

### 9.4.2 配置

1. 打开控制台 → 「模型」页添加供应商（base_url + API Key）→ 拉取/手填模型。
2. 「编队」页把模型指派给灵枢与各角色。
3. 首页选择模式，描述目标与授权范围；可附 HAR/附件。
4. MCP 服务器在 `configs/system.yaml` 配置；不可达只留痕，不阻断。

### 9.4.3 验证命令

```bash
LITELLM_LOCAL_MODEL_COST_MAP=True .venv/bin/python -m unittest discover tests/
.venv/bin/python -m ruff check src/ tests/
for f in src/spiritscout/web/static/js/*.js; do node --check "$f"; done
for f in tests/test_*.js; do node "$f"; done
```

注意：

- 本机 venv 若未装 `.[dev]`，`ruff` 会报 `No module named ruff`。
- 沙箱/Redis/Docker/Chrome/Node 相关测试会按环境跳过（11 个左右），不是失败。
- 行为质量以真实任务浏览器实测为准；单测通过不等于体验正确。

## 9.5 VibeCoding 约束清单

在让 AI 帮你改代码之前，把这些贴进上下文：

1. **不要写死解题模板**：知识库存参考事实，不存步骤序列。
2. **不要后端写死行为规则**：意图分类、派生时机、模式由模型/用户决定。
3. **不要恢复回合顶**：没有固定回合数限制或预算熔断。
4. **授权边界由模型上下文维护**：后端不做硬性禁打匹配；扩围由模型提问用户确认。
5. **危险操作必须用户审批**：删除、反弹 shell、上传 WebShell、容器逃逸、爆破；不要绕过 ApprovalBroker。
6. **Flag 提交由模型判定**：不要恢复后端正则裁决。
7. **前端无构建**：直接改 `static/`，改完 `node --check`。
8. **中文注释、ruff 全绿、类型标注**。
9. **提交信息一行人话摘要**。
10. **改动行为时同步文档**：至少更新 `docs/` 对应章节。
11. **任务收尾必须闭环**：每次任务结束前评估并同步 `docs/`、`README.md`、`CHANGELOG.md` 与过时注释；新增功能/模块先写测试并通过最小可用性测试，结束前跑全量测试（unittest、ruff、`node --check`、`tests/test_*.js`），全部通过才结束。

## 9.7 定义完成（DoD）

一个改动算完成，至少满足：

1. **功能**：行为符合需求，失败路径有明确语义（不静默降级）。
2. **测试**：新增/修改单测；涉及前端跑 `node --check`；涉及行为做真实任务验证。
3. **静态检查**：`ruff check src/ tests/` 通过。
4. **安全**：不绕过审批、不扩大授权、不把密钥写进日志/配置。
5. **可观测**：关键路径有审计事件；错误有原因，不是“失败了”。
6. **文档**：更新 `docs/` 对应章节；如果改了约束，更新 `AGENTS.md`。
7. **兼容**：旧会话/旧配置能读；不能读时给出迁移说明。

## 9.9 给 VibeCoding 的实践建议

- **小步提交**：一次只改一个机制，避免“顺手重构”把行为变化混在一起。
- **先写失败用例**：尤其是安全/状态机/恢复路径。
- **不要盲改提示词**：提示词是行为代码；改完要做真实任务对比。
- **保留回执**：任何“跳过/拒绝/降级”都要留原因，否则模型会空等。
- **不要在安全路径上加“聪明”**：审批、沙箱、密钥的代码越简单越好。
- **用审计验证**：改完打开会话页，看事件流是否符合预期；不要只看单测。

## 9.10 结语

灵枢的长期价值不在于“又一个会调工具的 Agent”，而在于它把四件事做成了系统：**动态规划、证据核验、共享环境、可审计的人在环**。这三件事（规划/核验/审计）越成熟，它越像一个可靠的安全测试搭档；越不成熟，它越像一个会写报告的扫描器。

未来的路线可以很多，但优先级应该始终是：**先把边界与证据做扎实，再谈规模与商业**。
