### 8.1.1 原失败用例的根因与处理

`test_cache_retains_only_latest_snapshot_for_each_file` 原来反复写入同尺寸 JSON（`{"used_tokens":0}` → `{"used_tokens":1}`），期待 `read_usage` 每次失效缓存。`file_version` 使用 `(dev, ino, size, mtime_ns, ctime_ns)`；在 Windows D 盘 DrvFs 上，同一时间粒度内重写，`mtime_ns` 与 `ctime_ns` **完全不变**（已单独验证）。因此读取到旧缓存 `0`，断言 `0 != 1` 失败。

- 这是**环境相关的测试脆弱性**，不是核心业务逻辑错误。
- 处理：测试改用长度变化的载荷（`pad` 随 tokens 增长），继续验证“缓存只保留最新快照”，不再依赖文件系统时间戳粒度；全量测试当前 0 失败。
- 但产品风险仍在：按文件时间戳做缓存失效，在网络盘、粗粒度文件系统、某些容器卷上不可靠。产品侧建议增加内容摘要或显式能力检测；不要用“重试”掩盖。

## 8.3 能力边界

### 8.3.1 授权边界

- 后端不做硬性禁打匹配；范围仅用于标注与 HAR 过滤。
- 范围外目标不拦截；Agent 应提问，但是否提问取决于模型。
- SRC 危险动作逐次审批；CTF、智能体模式自动批准并留审计。智能体模式禁止公开网页搜索。
- 结论：**没有确定性阻断保证**。详见 04.9。

### 8.3.2 规模边界

- 单进程、单端口单实例；`ExecutionRunLock` 防止同工作区并发。
- 并发会话默认 4（[config/settings.py](../src/spiritscout/config/settings.py#L144-L150)、[web/app.py](../src/spiritscout/web/app.py#L345-L346)）。
- 单任务路线上限 8（[config/settings.py](../src/spiritscout/config/settings.py#L251-L253)）。
- SQLite WAL；Redis/NATS 只解决事件总线，不解决调度/执行器分布式化。

### 8.3.3 模式边界

- CTF 禁端口扫描；Docker CTF 可 `--network none`。
- SRC/竞赛允许端口扫描（竞赛按赛方规则动态禁用）。
- 竞赛不按赛制标签裁剪角色；规则原文交模型理解。

### 8.3.4 环境边界

- bwrap 只支持 Linux；Windows 需 WSL。
- Docker 部署给容器 `SYS_ADMIN` + unconfined（为了 bwrap），不是强隔离边界。
- `executor.backend=docker` 需要 Docker 守护进程/套接字；默认 compose 未挂载 socket，通常不可用。

### 8.3.5 模型边界

- 需要至少一个可用模型；没有模型时不开工。
- 不同模型的工具调用、JSON 输出、思考档位差异大；项目做了协议回退与空正文重试，但不能消除差异。
- 预算只计量不熔断；成本可能失控。

### 8.4.1 P0：安全/合规相关

## 8.6 成熟度结论

- **技术原型**：已经越过“能跑”阶段，进入“可自用、可演示、可复盘”的阶段。
- **产品**：还不是。缺少多租户、RBAC、评测、SLA、商业支持。
- **安全工具**：适合授权测试者在本机/受控环境使用；不适合直接暴露在不可信网络或共享主机。
- **研究平台**：有较高价值，尤其是鉴真、DAG、上下文工程、经验库这些可被单独研究的机制。

## 8.7 优先级建议

**P0（先做）**

1. 同步根 README/CONTRIBUTING 的过时表述，避免新人被误导。
2. 产品侧修复用量缓存的时间戳脆弱性（测试已改为不依赖时间戳，但缓存策略仍需内容摘要或能力检测）。
3. 明确 MCP `target_params` 的实际语义（文档 + 可选校验）。
4. 在部署文档中显著标注 Docker `SYS_ADMIN` 的风险与替代方案。

**P1（近期）**

5. 清理/接线竞赛死代码与 `collab.py`。
6. 建立行为评测基准（真实任务集 + 评分）。
7. 拆分 `views.js`，补前端回归。
8. 增加 Windows PowerShell 启动器或明确“仅 WSL”。

**P2（中期）**

9. RBAC/SSO/多租户。
10. 审计加密与留存策略。
11. OpenAPI/集成文档。
12. 成本预算与告警（不熔断，只提醒）。

## 8.8 一句话

灵枢已经是一个**有辨识度的技术原型**，但它的安全边界、工程化与商业化能力都还在早期。把它当“能自己思考的安全测试搭档”是合理的；把它当“开箱即用的企业安全产品”则高估了它。
