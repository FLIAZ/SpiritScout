# 本地外部工具调用验证

日期：2026-11-07。结论：现有轻量 Agent 已能通过 shell / Python 通道实际调用若干成熟
工具；统一能力目录、正确用法查询和持久调试方案尚未完成，不能宣称所有工具均稳定可用。

## 验证条件

- Linux 原生轻量控制台，真实 Qwen3.5 9B / llama.cpp，配置上下文 98,304。
- 从浏览器创建两个 CTF 轻量会话，上传自制的离线 ELF、Java class、单包 PCAP 和整数
  约束夹具。没有网络目标，不下载依赖，没有修改 Agent 代码、系统提示或工具适配器。
- 第一轮明确点名工具；第二轮最初只给分析目标，没有点名工具，之后单独追加 pwndbg
  验收消息。不能把追加后的指定调用算作模型自主选择 pwndbg。
- 核对真实工具调用、退出状态、完整日志、生成文件和夹具真值；没有只凭模型声称完成
  或进程返回 0 判定成功。预先的沙箱可用性探测与 Agent 调用分别记录。

## 实际结果

| 工具 | Agent 如何选择 | 核对结果 | 边界 |
| --- | --- | --- | --- |
| TShark | 未点名，自主选择 | 读取离线 PCAP，端口与载荷均匹配真值 | 小型离线抓包，不是在线抓包或复杂协议验收 |
| GDB | 未点名，自主选择 | 实际命中断点，参数为 37，取得调用栈，继续后程序输出 262 | 单次批处理，不是跨工具回合的持久调试 |
| jadx | 未点名，自主选择 | 成功反编译 class 并读取生成源码；方法计算结果为 62，与真值一致 | 本次不是 APK 资源、混淆或大工程测试 |
| Z3 | 明确点名 | 首次取值类型转换错误，自行修正后求得正确整数解，并代回约束核对 | 简单约束，只运行一次任务 |
| pwndbg | 后续消息明确点名 | 前几次参数错误；改为脚本文件后，实际加载扩展、命中断点并执行 `regs`，RDI 为 `0x25`，继续后输出 262 | 证明批处理可调用，未证明主动选择或持久会话能力 |
| pwntools | 明确点名 | 实际 `cyclic` 生成序列成功；`cyclic_find` 偏移检查失败，反复传入不存在的 `length` 参数 | 完整任务未通过，不能算稳定调用 |
| apktool | 仅做沙箱预检 | 版本命令成功，版本 3.0.3 | 未由 Agent 执行 APK 分析 |
| radare2 | 仅做沙箱预检 | 版本命令成功，现有结构化静态读取通道仍在 | 本轮没有做 Agent 分析验证 |
| IDA | 本轮未测 | 无新的实际分析结果 | 不从其他工具成功推断 IDA 可用 |

本机实际沙箱能找到项目虚拟环境中的 jadx、apktool、pwndbg 等入口；只检查宿主终端
PATH 会遗漏它们。预检得到 jadx 1.5.6、pwntools 4.15.0、Z3 5.1.0.0、Scapy 2.8.0，
并确认 pwndbg 扩展可加载。这个结果只描述本机执行环境，不是默认 Docker 镜像的安装清单。

## 失败与未覆盖项

明确点名的一轮记录 16 次模型调用、14 次工具调用，最大实际输入 20,091 tokens。
`cyclic_find` 错误共发生 7 次，最长连续完全相同参数调用为 5 次，测试在明确重复后停止。
核对持久化的模型工具消息后确认，完整的“不接受 length 关键字”报错已返回模型；
不能把该循环归因于库未安装或模型完全看不到错误。

模型还曾把 Python 库函数名当作灵枢工具名查询，随后检索到无关技能资料。这说明需要
补充与实际安装版本匹配的 CLI 帮助、Python 函数签名和局部用法入口，减少错误猜参。

第二轮含追加的 pwndbg 检查，共 28 次模型调用、16 次工具调用，最大实际输入
23,835 tokens。已生成并追加分析报告，数值与原始观察匹配；报告仍未完整列出 jadx
生成源码的路径引用。取得所需调用证据后人工结束验证，未将其计为自动收尾通过。

pwndbg 的早期错误调用虽然返回进程退出码 0，实际没有执行所需调试命令；只有后来的
断点、扩展寄存器输出和程序结果齐全，才计为本项通过。退出码不是任务完成的充分条件。

本轮未验证 Windows Docker Desktop、IDA 许可证、完整工具清单、跨回合调试进程保持、
长会话中的工具选择稳定性或所有依赖缺失路径。单次成功不代表通用成功率。
原始审计、会话、截图、模型配置及测试产物只保留本机，不随测试仓库发布。

后续接入与验收范围见 [本地模型外部工具方案](本地模型外部工具方案.md)。
