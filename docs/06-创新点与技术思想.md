# 06 · 创新点与技术思想

本文不把“用了 LangGraph”“用了多 Agent”当成创新。创新应当是：**在这个问题上，采用了与常见做法不同的取舍，并且这个取舍解决了具体痛点**。下面按“思想 → 代码落点 → 相比常见做法 → 成熟度”组织。

## 6.1 从“固定流程”到“交付目标驱动的动态 DAG”

### 思想

常见自动化渗透工具是“阶段流水线”：信息收集 → 端口扫描 → 目录爆破 → 漏洞扫描 → 报告。每个阶段有固定动作和固定顺序。灵枢的做法是：

- DAG 节点不是“动作”，而是**可核验的交付目标**（例如“证明某接口存在越权”），标题要写清完成判据（[agents/master/agent.py](../src/spiritscout/agents/master/agent.py#L1276-L1298)）。
- 节点可运行时增删；失败可重建；同战术×赛题去重；依赖可两遍解析（[dag.py](../src/spiritscout/agents/master/dag.py#L62-L157)）。
- 每轮复盘决定继续、补节点或收敛；没有固定回合顶（[agent.py](../src/spiritscout/agents/master/agent.py#L145-L203)）。

### 相比常见做法

| 常见做法 | 灵枢 | 差异 |
| --- | --- | --- |
| 固定阶段流水线 | 目标节点 + 动态重规划 | 早期侦察停滞时可以换角度，而不是空转 |
| 单 Agent ReAct 循环 | 主 Agent 规划 + 子 Agent 执行 | 规划与执行分离，子 Agent 不被全局提示词淹没 |
| 一次性计划 | 每轮 upsert + 回执 | 计划可修正，模型知道哪些被跳过/拒绝 |

### 成熟度

**已落地且是核心路径**。但“交付目标”的质量取决于模型；如果模型把节点写成动作（“扫描端口”），DAG 就退化成流水线。提示词里明确禁止这样写，但没有确定性校验。

## 6.2 授权边界交给模型上下文，而不是后端规则表

### 思想

传统安全工具用 allowlist/denylist 做硬边界。灵枢反过来：

- 用户原话、项目规则、后续答复**原文**进入 `world_state`；
- 后端不编译禁打列表，不做关键词分类；
- 范围外目标不拦截，只加 `scope_note`，由 Agent 向用户确认扩围；
- 扩围写入会话批准集，原文落盘，跨恢复保留。

代码：[policy/scope.py](../src/spiritscout/policy/scope.py#L1-L6)、[gateway/world_state.py](../src/spiritscout/gateway/world_state.py#L21-L146)、[tools/builtin.py](../src/spiritscout/tools/builtin.py#L258-L263)。

### 为什么这样做

安全测试的边界经常是“用户口头说的、文档里写的、后续补充的”混合体，规则表很难穷举。把原文交给模型，能让边界随对话更新，而不是被一条正则误判。

### 代价

这是**全项目最大的风险取舍**：没有确定性阻断保证。它适合“用户本人就是授权测试者”的场景，不适合不可信用户/多租户。详见 04 的 4.9.2。

### 成熟度

**已落地，但仍有争议**。2026-10-21 从“禁打硬边界”改为“模型上下文维护”，是一次明确的方向选择；未来的企业版可能需要可选的强制模式。

## 6.3 独立鉴真：把“自我批评”变成“独立复测 + 原文核对”

### 思想

多数 Agent 系统的“验证”是让同一个模型再想一遍（self-critique），容易被自己的结论带偏。灵枢把验证拆成独立角色：

- 鉴真不复用发现者的上下文与结论；
- 读取用户规则原文；
- 自己发请求、自己做对照；
- 必须提交 `execution_id + quote`，引用本次工具返回的连续原文；
- 引用不匹配会被退回补证；
- `confirmed` 才进收录池。

代码：[agents/verifier.py](../src/spiritscout/agents/verifier.py#L27-L159)、[agents/master/agent.py](../src/spiritscout/agents/master/agent.py#L1221-L1243)。

### 相比常见做法

| 做法 | 问题 |
| --- | --- |
| 同模型 self-critique | 共享同一上下文偏见，容易“自己说服自己” |
| 规则引擎复测 | 只能覆盖已知漏洞类型，无法理解业务语义 |
| 人工复核 | 成本高、不可扩展 |
| 灵枢鉴真 | 独立上下文 + 用户规则 + 实际执行证据 + 逐字核对 |

### 成熟度

**已落地且效果明显**，是项目最有辨识度的机制之一。局限是“对照实验设计”仍依赖模型；证据严格不等于判断正确。

## 6.4 黑板 + 环形台账 + 共享缓存：用“环境”协调多 Agent

### 思想

多 Agent 协调常见两种做法：中心调度器发消息，或 Agent 之间直接对话。灵枢用第三种：**共享环境**。

- 黑板 8 层：事实的单一事实源；
- 环形台账：已尝试登记 + 督导建议；
- 共享缓存：同题并行路线共享现场；
- 事件总线：变更通知。

子 Agent 不需要互相认识，只需要读写同一个环境。这是典型的 stigmergy（间接协作）思想。

### 代码

- 黑板写入带层权限、版本锁、dedup_key 升级、outbox（[blackboard/store.py](../src/spiritscout/blackboard/store.py#L126-L196)）；
- 环形避让 `ZERO_OUTCOME=0.1`（[ring.py](../src/spiritscout/agents/ring.py#L22-L68)）；
- 共享缓存命名空间/TTL（[agents/sub/cache.py](../src/spiritscout/agents/sub/cache.py#L22-L63)）。

### 相比常见做法

| 做法 | 问题 |
| --- | --- |
| 中心消息总线 | 消息风暴、顺序依赖、Agent 需要知道彼此 |
| Agent 直接对话 | 上下文爆炸、责任不清 |
| 共享环境 | 松耦合、可回放、可审计；但需要好的事实模型与去重 |

### 成熟度

**已落地**。黑板是核心路径；环形台账是进程内启发式，跨会话不共享；共享缓存只在单进程内有效。

## 6.5 上下文工程：稳定前缀 + 世界状态增量 + 决策补丁 + 记录回放

### 思想

长任务最大的成本不是工具调用，而是**上下文重复**。灵枢做了四层治理：

1. **稳定系统前缀**：系统提示不插值授权范围，便于端点前缀缓存。
2. **世界状态片段**：运行时事实放 `<world_state>`，变化时整字段重发（[world_state.py](../src/spiritscout/gateway/world_state.py#L143-L167)）。
3. **决策记忆**：同阶段第一次发完整 snapshot，后续只发 JSON Patch（[context.py](../src/spiritscout/gateway/context.py#L225-L299)）。
4. **记录回放**：CTF 已读地址再次请求直接回放，模型用 `refresh` 决定是否重取（[ctf/agents.py](../src/spiritscout/ctf/agents.py#L1780-L1917)）。

另外 `compact_json` 保护授权/用户答复等字段不被压缩（[context.py](../src/spiritscout/gateway/context.py#L10-L65)）。

### 相比常见做法

很多系统要么“每轮全量重发”，要么“粗暴截断历史”。灵枢的选择是：**事实分块、稳定在前、变化在后、受保护字段永不裁**。

### 成熟度

**已落地，工程细节多**。`PrefixTracker` 只做诊断，不冒充服务端缓存命中；这是一个很诚实的计量设计。局限是补丁机制要求模型理解 JSON Patch，提示词里明确说明了语义，但仍可能出现“看漏补丁”的情况。

## 6.6 经验自进化：存“洞察”，不存“步骤”

### 思想

很多 Agent 的“记忆”会退化成“把上次的解题步骤抄一遍”，换一道题就失效，甚至误导。灵枢的提炼提示词明确要求：

- 洞察必须脱离本题仍然成立；
- 单题坐标（路径、参数、口令、端口、flag 原文）一律不写；
- 不写操作序列与处方；
- 只写“什么条件下、能看到什么信号、为什么值得注意”。

代码：[runtime.py](../src/spiritscout/runtime.py#L882-L936)、[knowledge/experience.py](../src/spiritscout/knowledge/experience.py#L207-L244)。

### 相比常见做法

| 做法 | 问题 |
| --- | --- |
| 保存完整对话 | 噪声大、不可复用、成本高 |
| 保存步骤模板 | 换题失效，违反“不写死模板”原则 |
| 保存抽象洞察 | 可迁移，但需要好的提炼提示与人工审核 |

### 成熟度

**已落地**。完成态与报告并行提炼；取消/失败转后台；进程重启可恢复快照。局限是提炼质量无自动评估，跑偏条目需要用户手动删除。

## 6.7 模式装配：模式只决定“谁上场”，不决定“怎么打”

### 思想

常见做法是按模式套一套固定流程。灵枢的模式装配器只做三件事：

- 决定装配哪些 Agent；
- 决定战术→Agent 映射；
- 决定模式专属规划器（CTF 方向轮换、竞赛开放规则）。

至于“先打什么、怎么打”，交给模型和现场。CTF 五方向、SRC 六角色、渗透赛混合编队都是这样。

代码：[modes/assembler.py](../src/spiritscout/modes/assembler.py#L205-L334)。

### 成熟度

**已落地**。竞赛模式不再按赛制标签裁剪角色；这是 2026-10-22 的明确变化。局限是模式装配器仍有一些规则化逻辑（CTF 方向分类、并行方向选择），不完全由模型决定。

## 6.8 声明式平台适配：换平台不改代码

### 思想

不同 CTF/靶场平台的 API 千差万别。灵枢用一份 YAML/JSON 档案描述：

- 列题、开容器、关容器、提交、提示、预检；
- 字段映射、点路径、占位符、并发上限；
- 重定向与凭据策略。

代码：[ctf/platform.py](../src/spiritscout/ctf/platform.py#L150-L606)。

### 成熟度

**已落地**。适合 REST/JSON 平台；复杂签名、分页、GraphQL、WebSocket 平台需要扩展。档案抽取依赖模型读文档，可能抽错。

## 6.9 审计与可观测是一等公民

### 思想

多数 Agent 系统的日志是“调试附属品”。灵枢把审计当成产品能力：

- 原文落盘、原文转播；
- 每个决策、工具调用、Flag、审批、用户消息都有事件；
- 会话页可以实时看 agent 数据流；
- SSE 字节游标支持断线续读；
- 执行台账记录调用状态与副作用状态，未知不自动重放。

代码：[core/audit.py](../src/spiritscout/core/audit.py)、[web/events.py](../src/spiritscout/web/events.py)、[tools/journal.py](../src/spiritscout/tools/journal.py)。

### 成熟度

**已落地**。代价是共享主机上的明文数据风险；这是部署问题，不是机制问题。

## 6.10 人在环上，但不打断自治

### 思想

常见做法要么“全自动、出事再说”，要么“每步确认、效率极低”。灵枢把人的介入放在几个关键点：

- 范围外目标：`ask_user`，不拦截但要求确认；
- 危险动作：触发时刻审批，不设超时；
- 用户消息：1 秒内直达灵枢，不等待回合边界；
- 暂停：协作式，在节点/步骤边界挂起；
- 停止：审批全部拒绝、提问全部无答复、资源回收。

代码：[policy/questions.py](../src/spiritscout/policy/questions.py)、[policy/approvals.py](../src/spiritscout/policy/approvals.py)、[agents/master/agent.py](../src/spiritscout/agents/master/agent.py#L784-L841)、[core/pause.py](../src/spiritscout/core/pause.py)。

### 成熟度

**已落地**。局限是审批疲劳、用户可能不看细节就点允许；UI 仍需改进。

## 6.11 竞赛调度：得分效率优先、滚动补位

### 思想

比赛场景的目标函数不是“把每道题做到底”，而是“在有限时间里拿更多分”。项目据此调整：

- Flag 平台确认后立即关闭容器、释放名额；
- 已规划的下一题直接补位，不等同批任务结束；
- 卡题由模型判断后暂缓，后端只执行资源操作；
- 赛后只出轻量摘要，经验提炼转后台。

代码：[runtime.py](../src/spiritscout/runtime.py#L1391-L1557)、[agents/master/agent.py](../src/spiritscout/agents/master/agent.py#L445-L527)、[ctf/platform.py](../src/spiritscout/ctf/platform.py#L507-L606)。

### 成熟度

**已落地**。但是 `CompetitionEngine` 里的优先级公式、AWD 换防、榜单拉取没有接线（见 08），AWD 防守侧基本未实现。

## 6.12 哪些是“借鉴”，不是“创新”

诚实地说，以下部分是常见思想的具体工程化，不应包装成原创：

- **ReAct / 工具调用循环**：来自通用 Agent 范式。
- **黑板架构**：经典 AI 协作模式。
- **DAG 规划**：工作流/任务编排常见。
- **Codex 式 world_state**：代码注释明确引用 Codex 的 `environment_context`。
- **Claude Code 式 ask_user**：代码注释明确对齐。
- **多模型投票/辩论/级联**：`gateway/collab.py` 有实现，但**当前没有调用方**，不能作为卖点。
- **CTF 方向分类**：规则化启发式，不是模型决策。

真正有辨识度的是这些**组合与取舍**：

1. 把“交付目标”而不是“动作”作为 DAG 节点；
2. 把授权边界交给模型上下文，并接受不确定性；
3. 独立鉴真 + 执行原文引用；
4. 稳定前缀 + 世界状态 + 决策补丁的上下文工程；
5. “不写步骤”的经验库；
6. 审计原文 + 可回放执行台账；
7. 竞赛“得分效率”而非“逐题到底”的调度。

## 6.13 技术思想总结

可以用四句话概括：

1. **规划是假设，不是命令**：DAG 可以重规划，节点可以失败重建。
2. **结论是证据，不是叙述**：鉴真只认实际执行原文。
3. **协调是环境，不是消息**：黑板、环形台账、共享缓存让 Agent 间接协作。
4. **人是授权者，不是操作员**：人负责边界与危险动作，执行交给模型。

这四句话也解释了项目的很多“看起来奇怪”的设计：为什么不设回合顶、为什么不硬拦范围外目标、为什么审计原文落盘、为什么审批不可代答。
