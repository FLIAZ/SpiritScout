# 05 · 核心算法与技术实现

本文按“算法/机制”组织，而不是按目录组织。每节回答：**解决什么问题、用什么方法、代码在哪、效果与代价**。

## 5.1 动态 DAG：可重规划的任务图

### 5.1.1 问题

固定流水线在早期侦察停滞时会空转；纯自由对话又无法保证依赖顺序、去重与可恢复。项目用“动态 DAG”折中。

### 5.1.2 数据结构

`DAGNode`（[core/models.py](../src/spiritscout/core/models.py#L239-L250)）：

```python
node_id, tactic, technique, title, status,
depends_on[], task_ids[], round_created, meta{}
```

`meta` 里可以放 `target`（多域拆分）、`challenge`（CTF 赛题载荷）、`deferred/defer_reason`（竞赛暂缓）。

### 5.1.3 upsert 算法

`TaskDAG.upsert_from_plan`（[agents/master/dag.py](../src/spiritscout/agents/master/dag.py#L62-L157)）分两步：

```text
1. 在副本上构建（staged = from_dict(self.to_dict())）
2. 第一遍：建节点
   - 去重键 = tactic × challenge.id
   - 同键已有节点且最新状态不是 FAILED/CANCELLED/PRUNED → 跳过，并带原因回执
   - 否则新建节点（依赖先置空）
3. 第二遍：解析依赖
   - 自依赖 → 报错
   - 未知战术 → 报错（不静默丢边）
   - 同战术候选取“最新创建且非失败”；多题时优先同赛题候选
   - 把失败节点的下游依赖重绑到重建节点
4. 环校验（DFS 三色标记）
5. 全部成功才应用；任一失败 → 整批回滚新建节点
```

为什么要两遍？因为计划内的节点可以互相引用，节点在计划中的先后顺序不应决定依赖能否解析。

为什么要“最新且非失败”？因为一个战术失败后重建，下游应该绑到新节点，而不是被旧失败节点卡死。

为什么去重键含赛题？多题并行时，同一战术（如 `CTF-WEB`）在 A 题和 B 题是两个独立节点，不能互相吞并。

### 5.1.4 效果与代价

- 效果：计划可以边探索边补节点；失败可重建；坏计划不会落半个图。
- 代价：`upsert` 的逻辑复杂，回执（created/skipped/rejected）必须完整回给模型，否则模型会误以为节点“在途”而空等（代码注释明确记录了这个历史问题，[dag.py](../src/spiritscout/agents/master/dag.py#L17-L25)）。

## 5.2 分支健康度与暴露风险

### 5.2.1 公式

`BranchHealthManager.evaluate`（[agents/sub/health.py](../src/spiritscout/agents/sub/health.py#L81-L93)）：

```text
健康度 = 0.3 × progress
       + 0.3 × value
       − 0.2 × failure_penalty
       − 0.2 × risk

failure_penalty = 1 − 0.5^consecutive_failures
risk = max(declared_risk, 0.5 × rate + 0.5 × signals)
```

其中：

- `progress`、`value` 都在 `[0,1]`；
- `rate` = 60 秒窗口内步骤数 / 30（每分钟 30 步记满）；
- `signals` = `detection_signals × 0.25`，上限 1（WAF/403/429 计数）；
- `declared_risk` 是步骤申报风险累计（`risk_delta`）。

`risk` 取 `max` 而不是求和：申报风险是粘性下限，频率/信号补充“跑得太快/已被拦截”的动态暴露，避免双重计数误剪（[health.py](../src/spiritscout/agents/sub/health.py#L42-L61)）。

### 5.2.2 剪枝与合并

- 剪枝阈值默认 `0.2`，宽限期 `min_steps_before_prune=2`：起步路线进展/价值为 0 属正常，不能一上来就剪（[health.py](../src/spiritscout/agents/sub/health.py#L97-L103)）。
- 冗余合并：路线名做 Jaccard 相似度，>0.6 合并，保留健康度更高者（[health.py](../src/spiritscout/agents/sub/health.py#L114-L145)）。

### 5.2.3 效果与局限

- 效果：资源向高价值路线倾斜，避免“一个死胡同拖住整个任务”。
- 局限：`progress`/`value` 是子 Agent 每步自报的，模型可以虚报；合并只看路线名，语义相似但名字不同的路线不会合并。它是“资源治理启发式”，不是精确调度。

## 5.3 环形协同：避免重复做功

### 5.3.1 尝试键

`attempt_key(method, url, params)`（[agents/ring.py](../src/spiritscout/agents/ring.py#L26-L31)）：

```text
METHOD URL [key=value|key=value...]
```

参数值截断 32 字符、按 key 排序，避免参数顺序影响去重。

### 5.3.2 避让规则

`should_avoid(key, agent_id)`（[ring.py](../src/spiritscout/agents/ring.py#L47-L56)）：

- 记录存在；
- 记录不是自己；
- `outcome < ZERO_OUTCOME`（0.1）。

也就是“同伴做过、且没有产出”的入口才避让。有产出的尝试不避让——有价值痕迹值得各自复核。

`record_attempt` 后写不覆盖高价值先写：保留更有信息量的记录（[ring.py](../src/spiritscout/agents/ring.py#L58-L68)）。

### 5.3.3 督导通道

灵枢通过 `ring.steer(agent, hint, task_id=...)` 定向投递；子 Agent 在下一次 LLM 决策边界消费，不取消正在执行的模型请求。CTF 调查对话中，未完成指令持续可见，`steering_feedback` 区分 delivered / accepted / completed / blocked；投递不代表执行完成，别题指令不会混入当前任务。

自 0.12.5 起，普通 **CTF** 模式不启动按路线笔记变化自动干预的督导循环：在途路线由专项 Agent 自主探索，同伴事实与派生能力保留，完成后仍由主 Agent 复盘。用户主动补充的指令走独立对话通道，暂停、停止与授权交互保持原语义。SRC 与智能体（competition）模式保留原实时督导和调度；模式来自用户选择，不据目标或题面改判。

此修复来自 `sess-18589383` 的本地审计：约四分钟中出现 13 条自动督导，其中截断摘要被误作完整证据，Flag 登记后仍要求重复取证。普通 CTF 不再把这些摘要转换成实时换向指令；没有固定回合、时长或费用阈值。系统提示、工具 schema、旧对话及缓存布局不改写，不以降低思考强度换速度。关闭普通 CTF 自动督导意味着主 Agent 不再在任务执行中主动纠偏，路线判断由持有完整现场上下文的子 Agent 承担；用户指导与任务结束后的复盘仍可纠偏。

无提交接口时，`submit_flag` 明确反馈“已登记，等待人工提交”，不把没有平台回执当成拒绝或要求继续等候；重复登记也给出相同收尾语义。证据是否充分、是否还有其他目标仍由模型判断，不因字符串格式或登记次数强制终止。普通 CTF 保留一次主 Agent 复盘和完整 WriteUp；经验提炼与智能体模式共用持久后台队列，前台结束后再占后台槽位，可在重启后恢复，不阻塞报告交付。

### 5.3.4 执行过程展示

自 0.12.6 起，会话页保留任务身份，并按 `(route_id, turn)` 拆分可独立展开的推进步骤；它们不是虚构的并行子 Agent。工具结果按原调用关联，迟到结果不回退当前步骤，历史向上补载以稳定步骤键恢复展开状态。结构化出处不足的旧记录只在唯一匹配时归属，歧义记录不挂到碰巧仍在执行的其他任务。

`web/process_graph.py` 从只读审计窗口投影过程节点：执行步骤、工具观察（含失败）、Agent 发现记录、明确记录路径的输出产物。步骤到产出使用 `produces` 实线；已产生的返回／产物索引连接到下一步上下文使用 `context` 虚线；没有新返回时用 `sequence` 虚线表示执行先后。上下文连线不表示工具返回必真、文件全文已读或已证明因果。无结构化产物路径的历史记录不补造文件节点，真实原文仍在审计与记录页。新 CTF 审计补齐工具返回／笔记的任务、路线、回合及沙箱输出路径，模型输入和工具 schema 不变。

过程读取最多最近 320 个完整活动，文件不变复用投影缓存；同文件只保留一版，缓存最多 16 个会话。窗口外不绘制悬空依赖，明确提示更早过程到会话历史查看。长图初始聚焦末端并保留总览按钮，缩放／拖动可看完整保留窗口；手机布局改变时保持视野中心。此展示不会追加模型调用、模型 token 预算或改写缓存前缀。

### 5.3.5 局限

- 环形台账是进程内状态，随会话消亡；跨会话不共享。展示用的过程投影可从持久审计重建。
- `attempt_key` 只归一化 GET 类入口；POST/带 body 的尝试依靠 CTF 共享缓存的另一套键。
- 只避让“无产出”，不避让“低价值但非零”，可能仍有重复。

## 5.4 共享缓存

`LocalSharedCache`（[agents/sub/cache.py](../src/spiritscout/agents/sub/cache.py#L22-L63)）：

- 按 `namespace/key` 存 `value/expires_at/hits`；
- 默认 TTL 3600 秒（由 `runtime._Infra` 注入）；
- 同会话所有 Agent 共持一份，按命名空间隔离（如 `routes`、`ctf_shared`）。

它不是分布式缓存；只在单进程内有效。跨进程/重启靠黑板与审计恢复。

## 5.5 上下文工程

这是项目最“工程化”的部分。目标：**在长任务中保住事实、降低成本、支持前缀缓存，同时不丢授权与用户答复**。

### 5.5.1 稳定前缀 + 世界状态

- 系统提示是稳定前缀，不随授权扩围、任务或环境变化（[profiles.py](../src/spiritscout/agents/profiles.py#L182-L221)）。
- 运行时事实放在 user 角色的 `<world_state>` 片段：授权范围、批准目标、测试规则、沙箱环境、用户原话、项目规则（[gateway/world_state.py](../src/spiritscout/gateway/world_state.py#L21-L146)）。
- 变化时只发**变化字段的完整值**（不发明细 JSON Patch），因为旧片段可能被压缩折叠，后续片段必须能独立读懂（[world_state.py](../src/spiritscout/gateway/world_state.py#L143-L167)）。

### 5.5.2 `compact_json`

`compact_json`（[gateway/context.py](../src/spiritscout/gateway/context.py#L10-L65)）：

- `_PROTECTED` 字段永不裁剪：`constraints/task_intent/scope/rules/mission/target/world_state/project_rules/user_context/...`；
- 超预算时，从最大字段开始，把字符串/列表/字典逐层减半，直到装下；
- **不删除字典键**；追加 `_context_projection` 说明哪些字段是节选；
- 输出始终是合法 JSON。

意义：避免“为了省 token把授权/用户答复裁掉”，这是很多 Agent 系统的真实事故来源。

### 5.5.3 `decision_messages`

`decision_messages(system, payload, max_chars)`（[gateway/context.py](../src/spiritscout/gateway/context.py#L196-L222)）：

- 先放 system + constraints；
- 再把稳定字段（world_state、available_tactics、task_intent、mission、rules、target、execution_recovery、reference_skills、business_context、shared_context）单独放一个 user 块；
- 最后放动态观察（situation、views 等）。

目的：稳定块在前，变化观察在后，便于端点前缀缓存；同时不为了“虚增命中率”而重复填充无意义前缀（代码注释明确反对这种做法）。

### 5.5.4 `DecisionMemory`

`DecisionMemory`（[gateway/context.py](../src/spiritscout/gateway/context.py#L225-L299)）：

- 同阶段第一次发送完整 `snapshot`；
- 后续只发送 JSON Patch（add/replace/remove，JSON Pointer 路径）；
- 契约变化或超过软窗口（48,000 字符）时，用最新现场重建；
- `commit` 只在模型返回可解析 JSON 后提交；失败不提交，避免把坏回答带入下一轮。

意义：长任务不必每轮重发全量现场，降低 token 成本；同时保留“最新现场”的可还原性。

### 5.5.5 前缀诊断

`PrefixTracker`（[gateway/cache.py](../src/spiritscout/gateway/cache.py#L33-L58)）：

- 把请求体 JSON 按 256 字节分块做 SHA-256；
- 与上一次同 key 请求比较公共前缀块数；
- 输出 `request_bytes/reused_prefix_bytes/new_suffix_bytes`。

它只记录哈希与长度，不保存提示词正文；`cache_summary` 只采用端点返回的真实缓存用量，不把“字符前缀相同”冒充服务端缓存命中（[gateway/cache.py](../src/spiritscout/gateway/cache.py#L11-L30)）。这是很诚实的计量设计。

### 5.5.6 CTF 长对话压缩

`_compact_messages` + 常量（[ctf/agents.py](../src/spiritscout/ctf/agents.py#L77-L87)）：

- 对话预算 `_MSG_CHAR_BUDGET = 48000`；
- 单条工具结果回灌 `_TOOL_RESULT_CAP = 6000`；
- 已读地址回放 `_FETCH_RECORD_CAP = 3600`；
- 沙箱输出回灌 `_SAND_MODEL_CAP = 3600`；
- 单次 LLM 调用超时 `_SOLVER_TIMEOUT = 420` 秒。

压缩时只折叠旧观察，保留工具调用配对；用户声明完整保留（[gateway/context.py](../src/spiritscout/gateway/context.py#L175-L193)）。

## 5.6 多模型网关与输出可靠性

### 5.6.1 协议适配

`LiteLLMBackend`（[gateway/backends.py](../src/spiritscout/gateway/backends.py#L178-L350)）支持：

- `chat_completions`：大多数 OpenAI 兼容端点；
- `responses`：OpenAI Responses（o 系/gpt-5 原生）；
- `anthropic_messages`：Anthropic Messages，litellm 负责翻译；
- `mock`：离线开发/测试。

模型名会按 base_url 加可路由前缀，避免 litellm 解析不出供应商（[backends.py](../src/spiritscout/gateway/backends.py#L284-L287)）。JSON 模式被端点拒绝、`stream_options` 不支持、工具参数被截断时都有显式降级/重试路径（[backends.py](../src/spiritscout/gateway/backends.py#L303-L339)）。

### 5.6.2 `chat_decision`：空正文重试

`output_lost(resp)` 判定“正文为空或被端点掐断”（`finish_reason in length/max_tokens`）。`chat_decision` 会加大输出余量重试一次，而不是把残缺当决策缺席（[gateway/gateway.py](../src/spiritscout/gateway/gateway.py#L53-L92)）。

这是一个很实用的工程经验：思考型模型可能把输出额度全耗在思考上，正文是半截 JSON；一次重试远比误判便宜。

### 5.6.3 用量计量

`BudgetTracker` 只计量不拦截（[gateway/gateway.py](../src/spiritscout/gateway/gateway.py#L95-L114)）：

- 总量、按模型、按模式；
- 逐笔调用（`call_series`）；
- 缓存命中只用端点返回的真实用量；
- 主备切换、失败调用也计入。

设计理由是“调查正酣时被后端预算掐断对用户是灾难”。代价是成本不可预测（见 08）。

## 5.7 汇聚与冲突：不替模型裁决

`ConvergenceEngine`（[blackboard/convergence.py](../src/spiritscout/blackboard/convergence.py)）做三件事：

1. **资产去重**：按 `dedup_key` 合并 fingerprint/attrs 并集，新实测覆盖同字段旧值。
2. **漏洞去重 + 冲突检测**：
   - 同键但状态/严重度差 ≥2 → 记录冲突；
   - 冲突的 `resolution` 是 `requeue_reverify`（有新实证）或 `keep_existing`；
   - **后端不按状态字母序挑赢家**，只保留“事实载体”（有鉴真背书的一侧）并合并证据。
3. **新实证重开**：如果已有 `verification` 但来了新证据，状态回到 `CANDIDATE`，`poc_verified/exploitable=False`，交回鉴真重判（[convergence.py](../src/spiritscout/blackboard/convergence.py#L100-L135)）。

这条设计来自一次真实缺陷：此前按状态名字母序挑赢家，`candidate` 可能顶掉 `accepted`（CHANGELOG 2026-10-19）。修复原则是“后端不替模型定生死”。

## 5.8 鉴真：证据逐字核对

### 5.8.1 工作循环

`VerifierAgent.review`（[agents/verifier.py](../src/spiritscout/agents/verifier.py#L90-L159)）：

```text
messages = system + world_state + candidate + user_rules
loop:
    world_state 变化 → 追加片段
    compact_history
    response = gateway.chat(tools=[http_probe, ask_user, finish_verification, MCP...])
    if no tool calls: validate(JSON)
    for call:
        finish_verification → validate 参数
            - 证据引用不匹配 → 退回补证（带可用执行列表）
            - 匹配 → 结束
        ask_user → 挂起等用户
        http_probe/MCP → 执行，记录 execution_id
```

### 5.8.2 校验规则

`validate` 的关键约束（[verifier.py](../src/spiritscout/agents/verifier.py#L35-L40)）：

- `confirmed` 必须有独立实际复现、不同执行的对照、明确危害、对应用户规则；
- `false_positive` 必须有实际验证的反证；
- 超时/被拦截/审批拒绝/规则不足/无法排除假设 → `inconclusive`；
- `quote` 只能是本次工具返回 `result` 字段的连续原文子串；
- 不能引用发现者的证据当作自己的独立证明。

### 5.8.3 意义与局限

- 意义：把“模型说发现了”变成“模型能拿出这次实际执行的原文”，大幅降低幻觉与自我引用。
- 局限：`http_probe` 仍是模型选择的请求；对照实验的设计质量取决于模型；如果模型不理解业务，可能把“200 反射”误判为危害（尽管提示词明确禁止）。

## 5.9 Flag 生命周期

### 5.9.1 两条路径

- `extract(text)`：正则扫描，格式校验，去重（[ctf/flags.py](../src/spiritscout/ctf/flags.py#L84-L101)）；
- `register(value)`：模型带着证据提交，**不做内容判断**，`format_ok` 只作登记信息（[ctf/flags.py](../src/spiritscout/ctf/flags.py#L103-L123)）。

设计上“Flag 提交由模型判定”，正则只用于候选提取，不恢复后端正则裁决（AGENTS.md 约束）。

### 5.9.2 提交

`submit`（[ctf/flags.py](../src/spiritscout/ctf/flags.py#L127-L158)）：

- 已终判幂等跳过；
- 未配置提交接口 → 只提取待人工判定；
- 锁内二次检查，避免并发重复提交；
- 频率限制：`min_interval = 60 / rate_limit_per_minute`；
- 平台未明确判定（`accepted=None`）→ 指数退避重试，最多 3 次；
- 明确对/错即终态；
- 发布 `flag.submit` / `flag.feedback` 事件。

### 5.9.3 多 Flag 语义

平台声明了 `is_completed` 时，以平台完成态为准；多 Flag 题拿到一个 Flag 不等于完赛，只有平台通报完成才停止派发（[modes/assembler.py](../src/spiritscout/modes/assembler.py#L254-L281)、[ctf/platform.py](../src/spiritscout/ctf/platform.py#L585-L606)）。

## 5.10 平台档案：声明式适配

### 5.10.1 档案结构

`PlatformProfile`（[ctf/platform.py](../src/spiritscout/ctf/platform.py#L150-L212)）包含：

- `base_url`、`headers`（凭据）；
- `ops`：`list/start/close/submit/hint/precheck`，每个操作有 method/path/url/query/body/items_field/addr_field/accepted_field/duplicate_code；
- `challenge_fields`：平台字段 → 内部字段（id/title/description/points/container_addr/is_completed…）；
- `limits`：`max_active`。

### 5.10.2 映射算法

- 点路径 `_dig`：`a.b.0.c`，数组索引；
- 占位符渲染 `_render`：`{challenge}`、`{flag}` 递归替换；
- 列题 `_extract_items`：优先 `items_field`，否则猜第一个对象数组；
- 开容器 `ensure_instance`：按题幂等、名额检查、失败退避、2xx 无地址按未就绪处理；
- 完成回收 `release_completed`：有完成态按平台，否则按已判对 Flag；
- 重定向：同主机、不降级、跨站阻断。

### 5.10.3 意义与局限

意义：换主办方 = 换一份档案，代码不动；平台凭据只在适配器内。

局限：档案抽取依赖模型读平台 API 文档，字段映射错了会导致列题/开容器失败；没有统一的平台协议标准，适配器只能做通用映射，复杂签名/分页/GraphQL 可能需要扩展。

## 5.13 工具执行与沙箱

### 5.13.1 进程执行

`ToolExecutor.run_argv`（[tools/executor.py](../src/spiritscout/tools/executor.py#L86-L173)）：

- `create_subprocess_exec` 走 argv，不经 shell，天然防注入；
- `start_new_session=True` 独立进程组；
- 超时/取消 → 杀整个组；
- 流式读取只留头尾，内存不随输出增长；
- 非零退出是“结果”不是“工具故障”；超时才 `ok=False`；
- 失败时回滚已跟踪的进程/文件。

### 5.13.2 参数注入防护

- LocalExecutor：`command_template` 的槽位用 `str.format`，但 argv 数组不经过 shell；
- DockerExecutor：内层命令用 `shlex.quote` 转义后拼 `sh -c`，外层 docker argv 不再二次格式化（[executor.py](../src/spiritscout/tools/executor.py#L268-L304)）。

### 5.13.3 沙箱

见 04 的 4.5。算法上它是一组确定性的挂载/遮蔽/环境清理参数，不是“智能隔离”。

## 5.14 HAR 脱敏导入

`import_har_directory`（[traffic/har.py](../src/spiritscout/traffic/har.py#L143-L193)）：

- 只读 `*.har`，最多 20 个文件；
- 单文件 ≤10 MiB，条目 ≤5000，参数 ≤64；
- 只保留 URL/方法/参数名/参数位置/状态码/模板；
- 超出授权范围的端点丢弃并统计；
- 写入黑板 ASSET 层，`source_agent=traffic_import`。

意义：用户可以把浏览器里的真实流量变成可测试端点，而不用把 Cookie/正文喂给模型。局限：HAR 只是入口清单，不包含业务语义，仍需知行/破壁走访。

## 5.15 用量账本与缓存失效

`UsageLedger`（[gateway/usage.py](../src/spiritscout/gateway/usage.py#L60-L110)）：

- SQLite WAL，`synchronous=FULL`；
- 一笔调用一个事务；
- `call_id` 唯一，重复投递不重复计量；
- 首次打开导入旧 `usage.json`，保留原文件；
- `read_usage` 先看 `usage.db`，再看旧 `usage.json`；
- 读取缓存按 `(dev, ino, size, mtime_ns, ctime_ns)` + WAL 文件版本失效。

**已知问题**：在 Windows D 盘 DrvFs 上，同尺寸内容重写时 `mtime_ns/ctime_ns` 可能不变，导致缓存不失效。本机验证过这两个字段完全不变；相关测试已改用长度变化的载荷，不再依赖时间戳粒度（详见 08）。这不是业务逻辑错误，但说明“按文件版本缓存”在粗粒度时间戳/网络盘上不够稳健，产品侧仍建议增加内容摘要或显式能力检测。

## 5.16 算法层面的设计亮点与局限

### 亮点

1. **“可回执的规划”**：DAG upsert 把 created/skipped/rejected 回给模型，避免静默吞掉导致空等。
2. **“证据门控”**：鉴真的 `execution_id + quote` 是很少见的严格做法。
3. **“上下文保护字段”**：授权/用户答复永不被压缩，击中真实痛点。
4. **“世界状态增量”**：稳定前缀 + 变化字段重发，兼顾缓存与事实完整。
5. **“不替模型裁决”**：汇聚冲突只合并证据，不按状态名排序。

### 局限

1. **健康度/价值分依赖模型自报**，不是客观测量。
2. **环形台账只在进程内**，跨会话/跨进程不共享。
3. **平台档案表达能力有限**，复杂平台需要扩展。
4. **经验提炼质量无自动评估**，可能污染后续会话。
5. **用量缓存对文件系统时间戳敏感**，在 WSL/网络盘上有真实缺陷。
6. **鉴真的对照实验设计仍依赖模型**，证据严格但判断仍可能错。
7. **预算只计量不熔断**，成本不可预测；这是哲学选择，不是遗漏。

## Token 兼容优化与基线（0.12.1）

本轮不改模型选择、思考档位、上下文/输出上限或任务推进策略，不截断用户原话和证据。
已有 `world_state` 整字段更新、工具回放与历史压缩策略保持原样。

### 无损增量编码（默认关闭）

`DecisionMemory.compact_patch()` 在原 JSON Patch 契约内选择等价的更短表达。
不足 8 项的变更继续使用原编码；密集变化可将多条字段修改合并成子树 `replace`。
只有序列化字节至少减少 20%、离线 token 估值不增加时采用，不重写历史消息，
不删除事实，不改变 JSON 类型，不把离线估值当成供应商用量。

`gateway.compact_decision_patches: false` 是默认值。首次启用、停用或恢复检查点
均沿用原先已提交的消息前缀，只改变后续增量。该开关通过同一网关配置传给阶段记忆，
不会改写系统提示。真实回放通过后仍需按实际任务验证，再考虑生产启用。

### 已验证的参数回退记忆

`gateway.remember_endpoint_capabilities: true` 默认启用。只有端点明确以 400/422
表示 `response_format` 或 `stream_options` 不支持，且省略该参数后成功，才记录该事实。
省略后的消息、工具、流式行为、温度和输出预算不变；超时、限流、仅提示 invalid
及降级失败不记忆。范围按供应商、端点、模型、协议和凭据指纹隔离，内存不存密钥原文，
10 分钟后重测，最多 128 项；开关关闭后不学习、不复用。该缓存属于每个网关，
不同会话的网关不共享能力结论。

### 用量比较

新调用持久化 `runtime_version`、`patch_optimization_enabled`、`sdk_attempts`、
`unreported_attempts` 及已报告的尝试输入/输出。SDK 尝试汇总不替代最终响应账本，
也不与其相加，避免重复记账；SDK 内部不可见的 HTTP 重试没有被宣称覆盖。
失败调用继续保留在审计中，报告的主统计仅覆盖已持久化的成功逻辑响应。

```bash
# 默认仅统计当前代码版本，无 API 调用或写操作
.venv/bin/python scripts/token_report.py
# 旧记录明确标记 legacy；不据此宣称当前版本的效果
.venv/bin/python scripts/token_report.py --all-versions
```

报告按版本、模型、阶段和短补丁开关分组，给出供应商报告的缓存命中输入、未命中输入、
输出、SDK 尝试与本地前缀字节诊断。缓存字段缺失的调用不进入命中率分母；本地字节复用
不冒充服务端缓存命中。报告不调用模型或读取密钥库；0.12.2 另从审计提取尝试用量，不输出请求或工具正文。

### 真实 DeepSeek 对照（2026-10-26）

## 稳定前缀与测试修复（0.12.2）

### 新段与新对话的布局

`gateway.stable_snapshot_prefix: true` 只在新建决策段时将 `world_state`、任务原文、
参考事实等稳定字段排在动态任务/轮次前。字段原值和 JSON 类型不变，历史前缀不排序，
原先字母序与新版字段序的编码字节数相同；不增加事实或填充无意义前缀。

`gateway.shared_ctf_prefix` 是默认 **false** 的实验开关。开启时让新建解题对话采用通用契约在前、角色职责在后的
系统提示，并按基础工具、专项工具的既有声明顺序发送 schema；原有工具集合、参数和
职责原文保留。其他通道继续按工具名排序。对话状态内的 `shared_prefix` 固定该布局，
重启恢复和模型显式选择的对话分叉沿用保存值；无标记的旧检查点保持旧布局。
切换配置不会重新排布已经初始化的对话或清空历史。

新布局上线有首次冷缓存成本；通用内容只有供应商完成缓存后才能共享，首批并行调用
可能来不及互相命中。不能承诺每次调用均提高命中率，更不能为比例好看而增加输入。
应同时比较首次调用、后续追加、未命中输入、总输入和完整解题结果，不能把不同进度、
重试、续跑或报告长度造成的比例差异当作缓存优化的因果收益。

### 证据文件与产物路径

题级工作目录在 `sandbox/<challenge>/`，因此 `../artifacts/` 不一定是会话产物目录。
新建对话（包括保持旧工具布局的新对话）使用世界状态内真实的 `environment.artifacts`。旧对话的提示仍原样回放，完整
世界状态已携带正确位置。不会为了迁移改写旧系统消息。

每次 `sandbox_exec` 用排他创建的唯一日志路径保存输出；返回的 `output_file` 始终
对应这一调用。同题分支共用工作区的协作能力不变，但模型自行选择的同名脚本/文件仍
可能相互覆盖，不能把日志修复宣称为所有工作区文件都已经隔离。每份调用日志仍按
10 MiB 轮转并保留两代；调用之间不再覆盖日志，证据保留量会随调用数增长。

有限域密钥恢复、AEAD 和最终证据。黄金答案只存在于工作区之外的测试器。

这些限制只在独立测试进程生效，生产没有增加回合顶、输出顶或预算熔断。

`token_report.py` 仍是只读报告。新增 `audit_attempts` 仅提取尝试用量字段，失败、取消和
未知字段单列，不输出审计中的请求/工具正文；该尝试汇总与成功逻辑账本不能相加。
没有收到供应商 usage 的已消费 tokens 仍需要官方控制台对账，不能由本地前缀字节推测。

### 0.12.2 真实验证与默认启用边界

完整综合题的两组都通过本地真实提交回调和七项证据检查。两组生成的恢复脚本分别在
全新沙箱中复跑原附件和换过密钥/明文的新附件，四次恢复均成功。没有用模拟模型回复
代替解题，也没有把固定答案或解题序列写入生产逻辑。

共享契约/基础工具重排实验的成功响应总体命中率为 87.50%，对照为 92.60%。实验组
经历首次冷缓存、未完成后的续跑，以及一次上游流式读超时，两组工作量并不等价；
无法把差异全部归因于布局，但也没有证据证明该布局满足命中率不下降要求。因此
`shared_ctf_prefix` 保持默认关闭，没有为漂亮指标额外填充上下文。

稳定快照字段排序另外做了单因素验证：系统契约、证据、模型、温度和输出上限一致，
先预热优化布局，再对同一个新任务 ID 做基线/优化配对。稳定事实前缀在不同任务 ID
之间复用，预热请求不计入收益。六项答案字段全部正确，供应商报告如下：

| 指标 | 字母序快照 | 稳定事实在前 |
| --- | ---: | ---: |
| 输入 tokens | 1791 | 1793 |
| 缓存命中输入 | 128 | 1536 |
| 未命中输入 | 1663 | 257 |
| 输出 tokens | 1079 | 1540 |

这是新建段场景的局部证据，不是整个系统命中率的承诺。JSON 字段顺序的分词边界让
实际输入增加 2 tokens，但既有预算参数未增加；未命中输入减少约 84.55%。输出有随机
波动，该配对不能证明总 tokens 或总费用必定下降。`stable_snapshot_prefix` 默认启用，
历史消息不重排；共享 CTF 布局和短补丁仍关闭。

测试中曾有一个 2048 输出上限的基线探针被截断，未作为质量通过或缓存收益证据，
费用仍计入测试账本；后续聚焦核验按两臂相同的 4096 上限完成，不改变生产配置。
测试脚本和失败/未知调用均保留，未把无响应的已计费请求当成零。
