# 01 · 项目定位与背景

## 1.1 一句话定位

**灵枢（SpiritScout）是一个 LLM 优先的多智能体安全测试系统**：主 Agent「灵枢」负责目标拆解、动态 DAG 规划、任务分发与复盘收敛；专项智能体集群并行执行；黑板承载事实，独立角色「鉴真」负责危害复测；用户在授权、扩围、危险动作与关键分叉上始终在线。

它同时面向三种场景（[README.md](../README.md)）：

- **SRC 漏洞挖掘**：从业务体验到侦察、测绘、Web 探测、横向、核验、报告。
- **CTF 解题**：Web / Pwn / 逆向 / 密码 / 杂项五方向。
- **智能渗透赛**：多题计分、平台托管、滚动补位、动态调度。

## 1.2 背景：它想解决什么问题

仓库内没有独立的产品背景文档或设计书原件，但代码注释大量引用「设计书 4.x / 6.x」章节，推测项目最初有一套外部设计文档。结合 [README.md](../README.md)、[CHANGELOG.md](../CHANGELOG.md) 与源码，可以把动机归纳为四类现实问题。

### 1.2.1 固定流程的安全工具无法应对“未知目标”

传统扫描器（nmap、nuclei、sqlmap）擅长已知模式的批量匹配，但面对需要理解业务、构造对照实验、跨请求关联的 SRC 场景时，往往只能给出一堆候选告警。项目用「模型规划 + DAG + 多路线并行」替代固定工作流：

- 主 Agent 只定义**交付目标**（要产出什么可核验结论），不规定步骤。
- 子 Agent 的路线（route）也是目标导向，步骤只是探测单元。
- 规划节点可以在运行中增删、失败可重建，避免刚性流水线在早期侦察停滞。

对应代码：[agents/master/dag.py](../src/spiritscout/agents/master/dag.py#L62-L157)、[agents/sub/base.py](../src/spiritscout/agents/sub/base.py#L223-L297)。

### 1.2.2 单 Agent 上下文与注意力不够

一个模型同时做“理解业务、规划、执行、核验”容易上下文膨胀、注意力漂移。项目把职责拆成角色：

- **灵枢**：元决策、派单、复盘、终审。
- **专项执行者**：知行（业务体验）、斥候（侦察）、听风（端口）、破壁（Web）、贯甲（主机）、深耕（横向）、CTF 五方向。
- **鉴真**：独立复测，不复用发现者结论。
- **秘书**：只读参谋，建议必须引用事实版本。
- **书记**：只读报告编纂。

角色、职责、工具边界集中定义在 [agents/profiles.py](../src/spiritscout/agents/profiles.py#L49-L171)，避免“页面说有、实际没装配”。

### 1.2.3 多 Agent 并行后，事实会碎、会重复、会冲突

多分支并行最大的成本不是模型调用，而是重复劳动与事实不一致。项目用三层机制解决：

- **黑板 8 层**：目标与授权、资产、侦察线索、漏洞、凭据、拓扑、任务状态、经验反馈，统一版本化存储（[blackboard/store.py](../src/spiritscout/blackboard/store.py#L29-L52)）。
- **环形台账**：同伴已尝试且无产出的入口，其他分支避让（[agents/ring.py](../src/spiritscout/agents/ring.py#L22-L68)）。
- **共享缓存**：同题并行路线共享已探入口、笔记、Flag（[agents/sub/cache.py](../src/spiritscout/agents/sub/cache.py#L21-L62)）。

### 1.2.4 “模型说发现了漏洞”不可信

项目把“发现”与“确认”彻底分开：发现者只能写候选；候选进入「鉴真」独立复测队列；鉴真必须用本次独立执行的实际返回原文（`execution_id + quote`）作为证据，并引用用户规则原文；只有 `confirmed` 才进入收录池。见 [agents/verifier.py](../src/spiritscout/agents/verifier.py#L27-L159)、[runtime.py](../src/spiritscout/runtime.py#L673-L690)。

## 1.3 目标与非目标

### 目标

| 层次 | 目标 | 当前落点 |
| --- | --- | --- |
| 产品目标 | 用一套系统覆盖 SRC、CTF、渗透赛 | 三模式装配器 [modes/assembler.py](../src/spiritscout/modes/assembler.py#L205-L334) |
| 技术目标 | 模型负责判断，后端只做感知、护栏与结果流向 | 系统提示、world_state、策略门 |
| 质量目标 | 只有可复现、符合用户规则的结论才收录 | 鉴真 + 主 Agent 终审 [planning.py](../src/spiritscout/agents/master/planning.py#L365) |
| 协作目标 | 多 Agent 并行而不重复做功 | DAG、环形台账、共享缓存、督导 |
| 可运营目标 | 全程审计、可暂停、可续传、可导出 | 审计 JSONL、暂停门、会话恢复 |
| 进化目标 | 跨会话积累经验而不是重复踩坑 | 经验库 [knowledge/experience.py](../src/spiritscout/knowledge/experience.py#L186-L251) |

### 非目标（有意不做）

- **不是确定性授权防火墙**。测试边界由模型结合用户原话、项目规则与后续答复维护；后端不做硬性禁打匹配（[policy/scope.py](../src/spiritscout/policy/scope.py#L1-L6)）。项目明确接受“没有确定性阻断保证”的代价。
- **不是固定回合的自动化流水线**。没有固定回合顶、没有预算熔断；继续/收手由复盘模型判断，用户可随时停止。
- **不把知识库存成解题步骤**。知识库存参考事实（平台特性、载荷、坑），不存步骤序列；经验库存“这类场景学到了什么”，不存单题坐标。
- **不替代人工授权**。危险动作逐次审批，审批不可代答、不设超时。
- **不做多租户 SaaS**（当前阶段）。单进程、单端口单实例、并发会话默认 4。

## 1.4 设计哲学

### 1.4.1 LLM 优先，而不是“规则引擎 + LLM 装饰”

后端只保留四类确定性职责：

1. **感知**：黑板、审计、用量、事件、状态机。
2. **安全护栏**：模式禁用、破坏性拒绝、危险动作审批、沙箱、密钥。
3. **结果流向**：事实去哪、事件发给谁、报告收什么。
4. **边界校验**：DAG 依赖/环、参数白名单、工具权限。

判断类工作交给模型：意图分类、模式理解、路线取舍、分支派生、Flag 判定、收敛时机、复测裁决。对应约束写在 [AGENTS.md](../AGENTS.md)：

> 不要写死解题模板；不要后端写死行为规则；回合顶已拆除；测试边界由模型上下文维护；危险操作必须用户审批；Flag 提交由模型判定。

### 1.4.2 证据优先于叙述

- 子 Agent 提示词要求输出分为「已观测事实、待验证假设、信息缺口」，没有请求/响应、文件或工具结果支撑的内容不得写成事实（[profiles.py](../src/spiritscout/agents/profiles.py#L182-L221)）。
- 候选人必须带 `evidence`；鉴真要求 `execution_id + quote` 逐字匹配（[verifier.py](../src/spiritscout/agents/verifier.py#L35-L40)）。
- 报告只收 `ACCEPTED`，低危与淘汰候选只进附录计数（[agents/report/agent.py](../src/spiritscout/agents/report/agent.py#L56-L83)）。

### 1.4.3 人在环上，但不打断自治

- 范围外目标：Agent 用 `ask_user` 提问，用户勾选后写入会话批准集（[policy/questions.py](../src/spiritscout/policy/questions.py#L162-L231)）。
- 危险动作：触发时刻审批，不设超时（[policy/approvals.py](../src/spiritscout/policy/approvals.py#L43-L58)）。
- 用户消息：1 秒内直达灵枢，与子 Agent 执行隔离（[interaction.py](../src/spiritscout/agents/master/interaction.py#L33)）。
- 暂停：协作式，在节点/步骤边界挂起，不杀在途调用（[core/pause.py](../src/spiritscout/core/pause.py#L28-L108)）。

### 1.4.4 可审计优先于“黑盒智能”

审计 JSONL 原文落盘、原文转播；每个决策、工具调用、Flag 提交、用户消息都有事件（[core/audit.py](../src/spiritscout/core/audit.py#L71-L131)）。信任边界是本机文件系统，而不是“脱敏后给外部看”。

| 2026-10-21 | 测试边界改由模型上下文维护、中途提问多选、世界状态片段 | 明确放弃后端硬边界，转向模型上下文边界 |

这条时间线显示了一个清晰的方向：**先把“多 Agent 跑起来”，再把“跑得安全、跑得省、跑得可解释”，最后把“模式与赛制交给用户和模型”**。

## 1.8 本项目的“诚实边界”

在进入架构之前，先明确三件事，避免读者高估：

1. **它不是“全自动黑客”**。模型仍会卡住、会误判、会重复；项目的价值在于把这些问题变得可观察、可干预、可收敛，而不是消灭它们。
2. **它不是“安全合规产品”**。授权边界是模型上下文维护，不是确定性执法；危险动作审批与沙箱是护栏，不是法律授权。
3. **它仍是 0.1.x**。核心链路已跑通，但文档一致性、评测体系、多租户、Windows 原生支持等工程化能力仍不完整（详见 08）。
