# 编码与排障经验

本文为维护本仓库的编码代理提供具体排障方法，配合 [AGENTS.md](../AGENTS.md) 按需使用。
案例依据当前工作区已有实现、测试和部署说明提炼；这里引用的测试说明其断言范围，
不代表本次文档整理执行了这些测试，也不代表已验证真实供应商或浏览器。
通用排查建议与仓库已有行为分别说明；不要将案例当成每个任务都要执行的流程。

定位问题时先写清“什么输入或操作触发、预期是什么、实际是什么、哪条证据能区分原因”。
检查优先跨越尚未确认的边界；已确认的部分无需反复证明。下面的顺序按问题类型组织。

## 1. 连通性正常，实际请求却立即失败

- **仓库依据：** [部署说明](部署与配置.md) 记录了 `CacheableResult` 导入错误：
  非流式连通性测试不能覆盖任务使用的流式初始化路径。依赖约束以
  [pyproject.toml](../pyproject.toml) 为准，不在经验文档复制版本号。
- **先区分原因：** 展开异常链，判断错误发生在本地导入、请求构造、连接过程还是远端返回。
  表层 `APIConnectionError` 不足以判断网络故障；若底层是 `ImportError`，先核对实际运行
  进程的解释器、安装版本、模块路径和镜像，而非只看当前终端的环境。
- **修复方向：** 在不兼容的依赖边界修正约束和安装状态。镜像内依赖变化需要重建对应镜像，
  重启已有容器不会重新安装依赖；开发机修改也不自动等于运行环境更新。
- **避免：** 反复轮换密钥、扩大超时、重试同一连通性测试，或为解决单个导入错误整体升级依赖。
- **有效验证：** [本机 HTTP 回归](../tests/test_gateway_local_http.py) 中
  `test_streaming_with_tools_over_real_http` 使用真实 SDK 和本机 SSE 响应，覆盖实际流式路径。
  它验证本地协议集成，不能据此宣布某个远端模型兼容。

## 2. 参数在配置中存在，却没有进入实际请求

- **仓库依据：** [适配器](../src/spiritscout/gateway/backends.py) 的 `_apply_effort`
  区分协议及 SDK 参数转换路径；[传输测试](../tests/test_provider_effort_transport.py)
  直接检查本机 HTTP 服务收到的 JSON 中是否保留 `reasoning_effort`。
- **先区分原因：** 沿“配置读取 → 网关入参 → 适配器 → SDK 序列化 → 收到的请求体”逐层核对，
  找到值首次丢失或改变的位置。诊断记录应脱敏，不能输出真实认证头或密钥。
- **修复方向：** 修改发生转换的边界，并保留协议和端点的差异；不同协议参数名相似，
  不代表语义相同。明确报错与静默忽略也必须分开处理。
- **避免：** 只给内部 kwargs 增加字段就宣布修好；Mock 拦截 SDK 入口会绕过真正的序列化。
  不要通过丢弃用户参数让请求表面成功，也不要把一个端点的特殊处理应用到所有端点。
- **有效验证：** 捕获本机接收端的实际请求，比较字段、类型和位置；远端是否接受、是否改变
  模型行为属于另一层证据。没有远端验证时只报告“本地传输已覆盖”。

## 3. 切换页面或会话后，迟到的响应覆盖当前内容

- **仓库依据：** [会话经验页](../src/spiritscout/web/static/js/session-experience.js)
  在 `loadOnce` 中核对会话 ID、请求代次与当前标签页；`load` 清理请求记录前还检查记录身份。
  [刷新回归](../tests/test_refresh_scroll.js) 构造旧会话晚返回的情况。
- **先区分原因：** 记录请求发出时的对象身份和代次，再比较响应到达时的当前对象。
  若 A 请求较慢，切换到 B 后 A 才返回，问题通常在响应归属判断，而非数据本身错误。
- **修复方向：** 成功、失败以及 `finally` 清理都应确认仍属于该次请求；旧错误不能覆盖新页，
  旧请求结束也不能清除新请求的忙碌标记。取消旧请求有助于节省资源，但不替代身份校验。
- **避免：** 加固定延时、请求前清空整个页面、让所有会话共用不带身份的 `loading` 标记，
  或把全部请求串行化。它们可能遮住时序问题，也可能让正常交互变慢。
- **有效验证：** 用可手动完成的 Promise 控制 A、B 返回顺序，断言 B 的内容和状态不被 A 改写。
  需要覆盖旧请求失败时，再增加对应顺序；不靠随机延时等偶发现象。

## 4. 刷新导致滚动跳动、展开丢失，优化后按钮又无法恢复

- **仓库依据：** [会话经验页](../src/spiritscout/web/static/js/session-experience.js)
  对相同内容保留 DOM，更新时按 `insight_id` 恢复展开状态。
  [刷新回归](../tests/test_refresh_scroll.js) 同时检查滚动、重排、跨会话隔离及按钮恢复。
- **先区分原因：** 数据是否真的变化？渲染是否重建了节点？当前状态属于服务器数据，还是
  用户本地交互？列表位置和对象身份并不等价，插入或排序会改变下标。
- **修复方向：** 保留未变化的节点；必须更新时按稳定 ID 保存同一对象的交互状态，
  切换会话则重新初始化。渲染签名应涵盖可见数据的依赖，不能遗漏会影响显示的字段。
- **容易漏掉的反例：** 点击按钮后临时设置 `disabled=true`，接口随后返回相同数据，
  渲染缓存会直接跳过更新。因此临时按钮状态要在请求收尾时独立恢复，不能等下一次重渲染。
- **避免：** 为消除闪烁停止必要的刷新、每次写入整块 `innerHTML`、按数组下标恢复状态，
  或用“大范围缓存”掩盖更新路径不清晰的问题。
- **有效验证：** 分别覆盖不变数据、新条目插入、列表重排、对象切换和操作失败。
  模拟 DOM 可验证节点身份和状态逻辑，不能证明真实布局、焦点或滚动体验正确。

## 5. 下载接口正常，但浏览器保存体验异常

- **仓库依据：** [文件模块](../src/spiritscout/web/static/js/files.js) 的 `saveFile`
  先调用保存选择器，再发起下载；[下载测试](../tests/test_file_download.js)
  断言调用顺序、取消不下载、流式写入、能力回退和写入失败。
- **先区分原因：** 检查点击事件到选择器之间是否插入了网络等待；需要用户激活的浏览器
  能力不能假设在长时间等待后仍可用。同时区分用户取消、API 不可用和文件写入失败。
- **修复方向：** 在用户操作触发时取得保存句柄，再获取并写入内容；用户取消就结束，
  API 不可用时按现有设计普通下载，写入失败则报告失败并清理资源。
- **避免：** 先下载完整大文件再弹选择器、用户取消后仍下载，或写入失败后静默再触发一次
  普通下载。后者会让用户无法判断文件到底保存到了哪里。
- **有效验证：** Node 测试能证明调用顺序和分支行为；浏览器的权限、用户激活和保存对话框
  仍需在已有或已授权的浏览器环境验证，不能因 Mock 成功就宣称浏览器兼容。

## 6. 存储变小了，旧记录或导出却坏了

- **仓库依据：** [存储编码](../src/spiritscout/core/storage_codec.py) 区分旧 TEXT、JSON
  字节和带格式头的压缩数据，检查长度与结尾；[存储回归](../tests/test_storage_compression.py)
  包含无损往返、损坏报错、重新打开数据库、历史读取和事务回滚。
- **先区分原因：** 明确需求是改变物理编码还是改变逻辑内容；列出写入、读取、迁移、导出
  入口。检查是否只有新写入路径更新，而旧数据或某个旁路读取仍按原格式解析。
- **修复方向：** 在共享编解码边界处理格式差异，保留必要的版本识别；使用临时数据库夹具
  验证新旧格式混读。迁移失败保留原记录并回滚，不把损坏数据解释成空结果。
- **避免：** 删除真实数据库重建、只测内存中的 `encode/decode`、把截断或摘要当作无损压缩，
  或在各调用方复制一份不同的解压逻辑。
- **有效验证：** 比较内容及必要的字节级往返结果，再关闭、重开数据库，验证读取与导出。
  体积减小和数据库完整性检查通过都不能单独证明业务数据没有丢失。

## 7. 等待已取消，后台工作仍在运行

- **仓库依据：** [存储维护](../src/spiritscout/web/storage.py) 用 `asyncio.to_thread`
  执行同步工作；`close` 停止维护调度后等待已启动工作结束，再完成关闭。
  [存储回归](../tests/test_storage_compression.py) 的
  `test_shutdown_waits_for_started_maintenance_worker` 检查关闭后的工作与忙碌状态。
- **先区分原因：** 区分等待协程、实际工作线程和资源持有者。取消等待不能等同于停止
  线程中的同步操作；若工作仍在写入，提前释放锁或忙碌标记就会暴露错误状态。
- **修复方向：** 明确退出语义是完成已开始的关键操作，还是支持协作式停止。
  由资源拥有者在实际工作结束后回收资源，收尾路径需要覆盖失败；不要对所有任务一律
  套用 `shield`，不同任务的取消语义应由实际职责决定。
- **避免：** 用吞掉 `CancelledError`、固定等待几秒或立刻置 `completed` 来表示工作已结束。
  前端停止轮询也不意味着后端任务停止。
- **有效验证：** 针对线程时序问题，用事件或屏障控制“开始工作”和“允许结束”，
  断言关闭行为、资源回收及最终状态。已有关闭测试不代表任意阻塞线程都能安全中断。

## 8. 页面启动慢：分清必要依赖和附带请求

- **仓库依据：** [控制台启动](../src/spiritscout/web/static/js/console.js) 与
  [页面性能测试](../tests/test_page_performance.js) 区分独立目录请求和进入会话所需数据，
  检查慢目录不阻塞会话、用户已导航后不被旧启动流程带回。
- **先区分原因：** 看请求等待顺序、可交互时间和 DOM 写入次数，判断瓶颈是网络、串行依赖
  还是重复渲染。先确认用户等待的必要路径，不凭感受增加缓存。
- **修复方向：** 先绑定可用交互，独立请求按依赖关系并行发起；关键页面只等待所需数据，
  非关键请求单独呈现失败或重试入口。请求完成后仍须核对用户是否已经导航。
- **避免：** 一个 `Promise.all` 把所有目录都变成首屏前置条件、随意加定时器，
  或缓存整个页面却不定义可见字段变化后的更新行为。
- **有效验证：** 用受控 Promise 让非关键请求保持未完成，观察关键流程能否继续；
  对渲染优化检查数据变化后仍会更新。调用顺序与写入次数测试不等同于真实浏览器性能测量。

## 9. CI 全绿，是否说明产品效果好

评价一项检查，先说明它能拦住什么具体回归、观察了哪层行为，以及运行和维护成本。
检查数量、覆盖率或绿色状态都不能替代这些问题；不同证据不能越级解释。

| 检查 | 能说明什么 | 不能单独说明什么 |
| --- | --- | --- |
| lint、语法检查 | 选定的静态规则和语法满足要求 | 功能正确、交互好用 |
| 有行为断言的单元测试 | 指定输入和分支下的局部契约成立 | Mock 外部的真实协议或界面正确 |
| 本机 HTTP、临时 SQLite 集成 | SDK 序列化、读写和恢复等边界协同 | 远端模型接受参数、真实用户体验 |
| 浏览器中的代表性用户操作 | 所测环境下实际交互路径可用 | 未测浏览器和所有边界均兼容 |
| 构建与打包 | 指定环境能生成产物 | 产物已验证安装、启动和业务效果 |
| 代表性离线任务与人工验收 | 所选需求的完成质量、结果依据、耗时和返工情况 | 所有任务和模型都有相同效果 |

当前 [主 CI](../.github/workflows/ci.yml) 在 Python 版本矩阵中重复运行相同的前端检查，
并对未区分文件范围的 push / PR 执行测试与镜像构建。
[Linux 打包](../.github/workflows/linux-packages.yml) 则是手动触发，不能算作每次提交的开销。
这些是配置层面的观察；未查看实际运行记录时，不估算节省分钟数或宣称某任务从未发现缺陷。

精简时优先考虑：

- 让不依赖 Python 版本的前端检查独立执行一次；评估 lint 是否也需要重复。
  `compileall` 与测试导入存在重叠，但删掉前应确认它是否还检查了测试未导入的模块。
- 纯文档、界面、依赖、部署等变更选择适合的检查范围；路径过滤要包含共享依赖和工作流
  本身的变化，不能只匹配直接业务文件。不要为路径优化再造复杂的测试编排框架。
- 兼容矩阵和镜像构建根据平台承诺、改动范围与发布阶段安排；保留能暴露跨模块问题的
  代表性集成验证，而非只留下最快的静态检查。
- 用已授权的代表性用户流程或离线样例评价实际结果，记录完成质量、错误行为、耗时及
  人工返工；没有执行这些验证时，交付中明确“CI 覆盖”和“实际效果验证”的区别。

是否调整 CI 由当前任务范围决定。讨论检查价值不等于授权删除测试、修改门禁或调用付费端点。

## 10. 测试越积越多，哪些值得长期保留

一次缺陷产生的回归测试可以长期有价值；需要区分一次性诊断与持续保护的行为契约。
判断单位应细到场景和断言，同一个文件也可能混合有用行为与脆弱的测试装载方式。

- **有用行为与脆弱装载要分开：** [资源目录筛选测试](../tests/test_resource_catalog.js) 验证
  `enabled=false`、分页和组合筛选参数，这些是实际行为；但它用函数名字符串切出源码，
  函数移动或改名就可能破坏测试。优先保留契约断言，改用可调用入口或必要的小夹具，
  而非把这类测试整个删除，也不为此引入新框架或重构无关业务代码。
- **文案断言要有理由：** [升级指引测试](../tests/test_update_guides.js) 保留安装方式选择、
  危险命令排除和展开状态保护，移除了固定提示措辞的断言。若具体措辞不是产品契约，
  验证对应状态与动作即可；不能因几条文案检查脆弱就丢掉其他保护。
- **重复场景优先合并：** 同一契约、相同失败路径仅输入不同，优先并入已有测试的数据表或
  `subTest`；同一函数的不同错误路径不自动视为重复。Mock 单测与真实 HTTP 集成也可能
  分别保护逻辑和传输，不能只因调用相同模块就删掉其中一层。
- **临时观察不要永久入库：** 打印依赖版本、定位一次目录、检查补丁是否包含某行代码，
  通常作为临时诊断即可。只有它对应长期约束，且现有测试没有覆盖时才考虑沉淀。
- **夹具复用与目录整理要留意发现机制：** [MCP 目录测试](../tests/test_mcp_catalog.py)
  从另一个测试模块导入 `cfg_at`。直接按目录搬文件可能破坏这种导入或让测试不再被发现。
  整理时处理必要的共享夹具与发现入口，核对原有用例仍被收集；“搬完后全绿”可能只是没跑到。

保留能识别数据损坏、身份混淆、接口不兼容及关键用户行为回归的测试；合并重复输入，
改写过度依赖实现细节的断言。只有需求已移除、独有覆盖已被替代，或确认只是一次性诊断时，
才删除相应用例。维护成本需要结合实际耗时、波动和失败原因判断，不按行数或 Mock 数量裁决。

## 11. 常见无效操作与更有用的替代

| 低收益或误导的做法 | 更有用的下一步 |
| --- | --- |
| 全仓库搜索、输出截断后原样再搜 | 先 `rg --files` 定位模块，再 `rg -n` 找符号，按行读取关键片段 |
| 对同一错误原样重试，没有新观察 | 选择能区分两个主要原因的检查，或明确缺失的环境条件 |
| 小补丁每改一行就跑全套回归 | 稳定一批相关修改后运行最小有效检查，出现跨模块风险再扩大 |
| 测试只断言源码里出现某个字符串 | 如需测试，断言稳定接口和可观察行为；结构约束测试须说明其必要性 |
| 测试失败就删缓存、重装环境、升级所有依赖 | 先保留原错误并定向复现，区分依赖、夹具和实现问题 |
| 为测试通过删断言、放宽异常或静默跳过 | 确认需求契约；只有契约确实变化才相应更新测试，并说明原因 |
| 简单错误引入新框架、大规模重构或大量开关 | 在拥有该职责的现有模块修复，另行记录真正独立的结构问题 |

## 记录下一条经验时

只有遇到可复用、非显而易见的经验才补充。记录触发条件、支持原因判断的证据、
有效修复、走不通的办法及其原因、对应回归和未覆盖边界；链接到当前实现，避免易过期的
行号、依赖版本和运行次数。没有亲自执行的检查不得写成实测成功；通用建议应明确标识。
