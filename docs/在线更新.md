# 版本提醒与在线更新

版本号旁仅在发现正式新版时显示静态 SVG 图标，不闪烁、不自动弹出。
点击图标或版本号打开详情，查看当前安装方式、目标版本和目标提交的 `CHANGELOG.md`；
日志缺失时使用 Release 发布说明。原始 HTML 不执行。
详情内附各安装方式的手动更新教程，默认展开检测到的方式；没有可用网络时也可阅读。
包含 Git、pip/uv/wheel、Docker 助手与镜像拉取、ELF/EXE、发行包和托管服务的更新步骤及失败处理，
尚未发布的 AppImage/deb/rpm/Arch 产物明确标记为未提供，不假设存在下载地址或软件源。

后端启动后异步检查官方 `FLIAZ/SpiritScout` 的最新正式 Release，默认缓存六小时，
使用 ETag；手动检查最短间隔一分钟，网络失败后十五分钟再试。
离线不阻塞控制台，不把检查失败显示成“已经最新”，旧提醒仍保留。
不把 main 分支每次提交视为发布；版本从运行中的 `spiritscout.__version__` 读取。

## 安装识别与执行条件

| 安装方式 | 更新方式 |
| --- | --- |
| Linux / Windows Git 源码，pip 或 uv 管理 Python 环境 | 校验官方 origin、工作区和快进条件，准备独立环境，再同步源码并重启 |
| pip / uv 安装的普通 Python 包（包括 wheel） | 从正式发布的确定提交准备独立环境并安装包，保留原环境，重启转入新环境 |
| PyInstaller 单文件 ELF / EXE | 匹配平台、架构与 SHA-256，下载验证后，由复制出来的独立更新进程替换主程序 |
| Docker Compose 镜像部署 | 宿主更新助手连接后，可从网页触发同步源码、构建和重建；不向容器挂载 Docker socket |
| 没有 Git 的解压源码、分叉仓库、开发容器源码挂载 | 展示原因，使用原部署方式更新 |
| deb / rpm / Arch 包、AppImage | 已提供 Linux 构建入口；系统包交由原包管理器更新，AppImage 手动替换 |
| 外部 ASGI 或 systemd / Supervisor 托管 | 展示更新信息，由原部署管理器更新和重启，避免重复启动服务 |

独立程序附件必须命名为 `spiritscout-linux-x86_64`、`spiritscout-linux-arm64`、
`spiritscout-windows-x86_64.exe` 或 `spiritscout-windows-arm64.exe`，Release API 需提供
`sha256:...` 的 `digest` 和实际大小。没有匹配附件时禁用更新，不猜测无架构标识的程序。
该路径用于单文件 PyInstaller 程序，不用于需要一起替换 DLL/资源目录的 onedir 安装。

只有通过灵枢 CLI 启动的服务可以由内置更新进程自动重启。更新要求安装/状态目录可写，
所有会话已终止且在途写操作已结束；不会中止运行中的任务。更新阶段拒绝新的写操作，
暂停自动计划触发；新版本通过健康检查前不恢复后台模型作业。

## 源码与 Python 包更新

源码 origin 需指向官方仓库。未提交修改、未跟踪文件、分支分叉、分离 HEAD、
被忽略文件碰撞、配置/工作区路径会被目标版本改写时停止更新。
不自动 stash、不强制 reset、不合并分支、不删除本地数据。
下载和安装依赖发生在切换前，网络/依赖准备失败时原服务继续运行。

新环境保存在更新状态目录的 `envs/<运行标识>`，不会移动虚拟环境。
有 uv 时使用 uv；存在 `uv.lock` 时按锁文件同步，不更新锁文件；否则使用 pip。
保留能够确认已完整安装的可选依赖组，不复制整个旧环境内任意第三方包。
自定义、非项目声明的 Python 插件依赖需要自行确认，无法自动推断其用途。

同步源码仅快进到已解析的发布提交，随后重绑定新环境的 editable 安装。
普通包安装使用非 editable 模式。原配置、密钥、工作区路径保持不变。
`active.json` 保存新解释器路径，原 CLI 下次启动时也会转入新环境。
这不会修改系统 Python，也不会把源码更新当成任意包的升级入口。

## Docker 宿主更新助手

需要宿主已有 Python 3.11+、Git、Docker Compose 和部署仓库；容器持久化工作区必须挂载卷。
在宿主原部署目录运行（前台保持运行）：

```bash
python3 scripts/update-container.py --url http://127.0.0.1:10010 --project-dir /path/to/SpiritScout
```

服务名默认 `spiritscout`，可用 `--service` 指定；`--compose-file` 可重复传入原部署文件。
启用了管理员认证时，通过 `SPIRITSCOUT_UPDATE_USERNAME` 和 `SPIRITSCOUT_UPDATE_PASSWORD`
提供管理员凭据，不写入命令行、更新计划或日志。远程控制台必须使用 HTTPS。

助手先检查仓库、容器和挂载，再向控制台报告可用状态；只有用户在网页点击更新后才执行。
助手不从网页接收 shell 命令、仓库地址、Compose 路径或服务名；这些由宿主启动参数确定。

镜像先构建，构建成功后停止原容器，用原镜像和原数据卷建立备份，再重建指定服务并验证。
不重建无关服务。构建失败时原容器不受影响；开始重建后验证失败需要人工恢复。
助手失联不重放更新操作，需要查看宿主和容器更新状态。助手退出后网页更新能力会过期。
宿主日志在仓库 `.spiritscout-updates/host-<运行标识>.log`；备份在容器持久化工作区的
`.spiritscout-updates/jobs/<运行标识>/backup/`。

## 失败与恢复

更新状态、日志和备份保存在 `.spiritscout-updates/`，不进入 Git；其中可能包含私有配置和证据，
目录/计划使用私有权限，不通过网页下载。普通源码安装该目录位于仓库根，Python 包安装位于
当前用户的数据目录（按原解释器环境区分），独立程序位于程序旁，容器位于持久化工作区。
保留历史环境与备份便于人工恢复，不自动清理。大工作区备份可能较慢，需预留磁盘空间。

- 准备失败：原服务保持运行，详情见 `jobs/<id>/worker.log`。
- 原服务已停止、新版尚未启动时失败：仅在确认源码仍为本轮目标且没有其他修改时回退，恢复原解释器再启动。
- 新版启动后健康检查失败：标记为需要恢复，保留 `backup/` 和 `service.log`，不自动拿旧代码打开新版数据。
- 更新进程中断：不自动重放命令。检查日志、进程、端口和更新锁后人工处理。

人工恢复时先停止所有相关进程；核对 `backup/manifest.json` 中原工作区和配置路径，
根据是否发生数据迁移一起恢复程序、Python 环境和数据。未启动新版时通常不需要恢复数据。
原解释器与 Git 提交记录在计划中，原独立程序另存为 `previous-binary`。
确认状态一致后再处理 `job.json`、`claim` 和 `active.json`，不要仅删除锁后反复重试。

更新 API 沿用控制台登录和同源写保护。健康回执只接受本轮随机令牌，避免把同端口的其他服务
当作更新成功。发布构建和安装脚本属于程序代码，只使用固定官方发布源；不提供自定义下载 URL。

本地生成 Linux 发行包与架构支持见 [Linux 打包与发行](Linux打包与发行.md)。
